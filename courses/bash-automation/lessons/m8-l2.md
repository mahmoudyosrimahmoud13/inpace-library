# Testing scripts, and putting them into service

## Test before you trust

1. `shellcheck backup.sh`: no warnings.
2. `bash -n backup.sh`: syntax check without running.
3. Run with `-n` (dry run), then for real on test data.
4. Test the **failures**: a missing directory, a full disk (a tiny loop-mounted file system), no network for the alert, two runs at once.
5. **Restore** from what it made: `tar xzf backup-...tar.gz -C /tmp/restore` and compare (`diff -r`).

## Automated tests with bats

`bats` (Bash Automated Testing System) runs test files:

```bash
# test/backup.bats
@test "fails without arguments" {
  run ./backup.sh
  [ "$status" -eq 2 ]
}

@test "dry run writes nothing" {
  BACKUP_DEST="$BATS_TEST_TMPDIR" run ./backup.sh -n /etc/hostname
  [ "$status" -eq 0 ]
  [ -z "$(ls "$BATS_TEST_TMPDIR"/backup-* 2>/dev/null)" ]
}
```

```bash
sudo apt install bats
bats test/
```

## Put it into service

```text
/usr/local/bin/backup.sh                (mode 755, owned by root)
/etc/backup.env                         (mode 600: WEBHOOK_URL=..., BACKUP_DEST=...)
/etc/systemd/system/backup.service      (EnvironmentFile=/etc/backup.env, ExecStart=/usr/local/bin/backup.sh /etc /srv)
/etc/systemd/system/backup.timer        (OnCalendar=daily, Persistent=true)
```

Keep the script in Git, with its tests, and deploy the same version everywhere. That's the step from "a script on a server" to "automation you can trust".
