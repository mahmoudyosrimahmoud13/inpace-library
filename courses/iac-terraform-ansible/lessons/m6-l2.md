# Environments, secrets and safety at scale

## Environments

| Approach | How | Notes |
|---|---|---|
| **Folder per environment** (recommended to start) | `envs/staging`, `envs/prod`, each calling the same modules with different variables and its own state | Clear, easy to review, prod changes are visible |
| Workspaces | One folder, `terraform workspace select prod` | Easy to apply to the wrong one by accident |
| Terragrunt | A wrapper that removes repetition across many folders/accounts | Worth it at larger scale |

Separate **AWS accounts** for dev, staging and prod (AWS Organizations) are the strongest boundary: a mistake in dev can't touch prod.

## Secrets in IaC

- Never put secret values in `.tf` or `.tfvars` in Git.
- Let AWS generate and own them: `manage_master_user_password = true` on RDS stores the password in Secrets Manager; Terraform never sees it.
- Remember state may still contain secrets: encrypt and restrict the state bucket.
- Ansible: Vault, or lookups from Secrets Manager / Parameter Store at run time.

## Safety checklist

- `prevent_destroy` and `deletion_protection` on databases, state buckets, DNS zones.
- `plan` output reviewed in every PR; prod applies need approval.
- Policy as code (OPA/Conftest, Checkov, Sentinel) to block things like public S3 buckets or untagged resources.
- Scheduled `terraform plan` to detect drift; alert if it isn't empty.
- `terraform destroy` is only for dev; production removals happen by deleting code in a reviewed PR.
