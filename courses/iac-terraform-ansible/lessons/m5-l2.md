# Ansible secrets, dynamic inventory and testing

## Secrets: Ansible Vault

```bash
ansible-vault create group_vars/prod/vault.yml      # encrypted file
ansible-vault edit group_vars/prod/vault.yml
ansible-playbook site.yml --ask-vault-pass           # or --vault-password-file from your CI secret
```

Convention: secret `vault_db_password` lives in the vault file; a plain `db_password: "{{ vault_db_password }}"` in `vars.yml` makes it greppable. On AWS you can instead read secrets at run time with the `amazon.aws.aws_ssm` or `aws_secret` lookups. Use `no_log: true` on tasks that handle secrets so they don't show in output.

## Dynamic inventory: ask AWS which servers exist

In the cloud, servers come and go. Let the inventory come from tags:

```yaml
# inventory.aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions: [eu-central-1]
filters:
  tag:project: shop
  instance-state-name: running
keyed_groups:
  - key: tags.role
    prefix: role
compose:
  ansible_host: private_ip_address
```

```bash
ansible-inventory -i inventory.aws_ec2.yml --graph
ansible-playbook -i inventory.aws_ec2.yml site.yml --limit role_web
```

No SSH port open? Ansible can connect through **SSM** with the `community.aws.aws_ssm` connection plugin.

## Testing

| Tool | Checks |
|---|---|
| `ansible-playbook --syntax-check` | YAML and structure |
| **ansible-lint** | Bad practices: `shell` where a module exists, missing names, risky permissions |
| `--check --diff` | What would change on real hosts |
| **Molecule** | Spins up a container or VM, applies a role, runs it again to prove idempotence, then runs tests |

Run `ansible-lint` and Molecule in CI on every PR, just like application code.
