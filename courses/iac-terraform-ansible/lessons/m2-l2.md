# State: what Terraform remembers

Terraform keeps a **state file** that maps your code (`aws_instance.web`) to real objects (`i-0abc123`), with their attributes. `plan` = compare code, state and reality.

## Rules for state

| Rule | Why |
|---|---|
| Use a **remote backend** (S3, Terraform Cloud) for anything shared | Your laptop isn't the source of truth; teammates need it |
| Turn on **locking** | Two applies at once corrupt state |
| Turn on **versioning and encryption** for the state bucket | State contains secrets in plain text (database passwords, keys) |
| **Never edit state by hand** | Use the commands below |
| One state per environment (and per big component) | Smaller blast radius, faster plans |

```hcl
terraform {
  backend "s3" {
    bucket       = "acme-terraform-state"
    key          = "shop/prod/terraform.tfstate"
    region       = "eu-central-1"
    encrypt      = true
    use_lockfile = true      # S3 native locking (Terraform 1.10+); older setups use a DynamoDB table
  }
}
```

## State commands

```bash
terraform state list                              # what Terraform manages
terraform state show aws_instance.web             # its recorded attributes
terraform state mv aws_instance.web aws_instance.app   # after renaming in code (or use a moved block)
terraform import aws_s3_bucket.logs acme-logs     # adopt something created by hand (or an import block)
terraform state rm aws_instance.old               # stop managing it, without deleting it
```

Since Terraform 1.5 you can write `import` and `moved` blocks in code, so they go through review and `plan` like everything else.

## Drift

Someone changes a security group in the console. Next `plan` shows Terraform wants to change it back: that's **drift**. Run `terraform plan` on a schedule in CI to catch it early, and make "no console changes in prod" a team rule.
