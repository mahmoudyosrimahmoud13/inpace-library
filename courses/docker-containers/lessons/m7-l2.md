# Capstone: containerize a real app

Take a small app with a database (your own, or any open-source web app with Postgres) and make it run with one command, the way a team would ship it.

## Requirements

1. **Dockerfile**
   - Pinned, slim base image.
   - Dependencies copied and installed before the code (good caching).
   - Multi-stage if the app has a build step.
   - Runs as a non-root user; JSON-form `CMD`; a `HEALTHCHECK`.
   - A `.dockerignore` that keeps out `.git`, `.env` and build junk.
2. **compose.yaml**
   - The app, its database (with a named volume) and anything else it needs (cache, worker).
   - `depends_on` waiting for the database to be **healthy**.
   - Secrets from a `.env` file that isn't committed (commit a `.env.example`).
   - Only the app's port published; the database reachable only inside the Compose network.
3. **compose.override.yaml** for development with live reload.
4. **Security**: `trivy image` shows no fixable critical issues; no `--privileged`, no docker.sock.
5. **Operations**: log size limits, `restart: unless-stopped`, and a backup command for the database written in the README.
6. **CI** (stretch): a GitHub Actions workflow that builds, scans and pushes the image tagged with the commit SHA.

## Prove it

- On a different computer (or after `docker system prune -a`), `git clone` plus `docker compose up -d` brings everything up.
- `docker compose down` then `up` again: the data is still there.
- Kill the app container (`docker kill`): it comes back by itself.
- Image size before and after your optimizations.

## Write it up

A README with: how to run it, the architecture (a Mermaid diagram), the image size, and three decisions you made and why (for example: slim instead of alpine, why the database port isn't published, how secrets are passed).

Then continue the track: GitHub Actions and DevOps CI/CD build on exactly this.
