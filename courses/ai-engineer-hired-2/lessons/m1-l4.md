# Python toolkit and Big-O

Know the cost of every operation you use. Most wrong complexities in interviews come from a hidden O(n) inside a loop.

| Operation | Cost |
|---|---|
| `list.append(x)`, `list.pop()` | O(1) amortized |
| `list.insert(0, x)`, `list.pop(0)`, `x in list` | O(n) |
| `x in set`, `d[key]`, `d[key] = v` | O(1) average |
| `deque.appendleft`, `deque.popleft` | O(1) |
| `heapq.heappush`, `heapq.heappop` | O(log n) |
| `sorted(a)`, `a.sort()` | O(n log n) |
| `bisect.bisect_left(a, x)` | O(log n) |
| `s[i:j]`, `list(a)`, `"".join(parts)` | O(length) |
| `s += ch` in a loop | O(n²) in the worst case: collect parts and join once |

![Measured: x in list grows with n, x in set stays flat](list_vs_set.png)

Measured while writing this lesson: looking for the last item of a 200,000-item list took about 1 ms; in a set it took well under a microsecond, whatever the size. That's the difference between O(n) and O(1).

## Reading constraints

The input size tells you the complexity they expect: n up to about 10³ allows O(n²); up to 10⁵ or 10⁶ needs O(n log n) or O(n); n around 20 hints at O(2ⁿ) (backtracking); a huge n or value range hints at O(log n) (binary search). Space counts too: say what extra memory you use.

Python's recursion limit is about 1,000 calls: for deep recursion (a long linked list, a big grid) use an explicit stack or `sys.setrecursionlimit`.
