# Big-O, and how to solve a problem in an interview

Coding interviews aren't about memorizing answers. They test whether you can take an unfamiliar problem, find an approach, judge how fast it is, and write correct code while explaining your thinking. This course teaches the **patterns** that cover most questions, in Python.

## Big-O: how cost grows

Big-O describes how the work grows as the input (size **n**) grows. It ignores constants and small terms: we care about the shape.

| Big-O | Name | Example | n = 1,000,000 |
|---|---|---|---|
| O(1) | constant | read `a[i]`, look up a dict key | 1 step |
| O(log n) | logarithmic | binary search | ~20 steps |
| O(n) | linear | one loop over the list | 1 million |
| O(n log n) | linearithmic | sorting | ~20 million |
| O(n²) | quadratic | a loop inside a loop | 1 trillion (too slow) |
| O(2ⁿ) | exponential | trying every subset | impossible |

A rough rule: about **10⁸ simple operations per second**. So for n = 10⁵, O(n²) is 10¹⁰: far too slow. O(n log n) is fine. The input limits in a problem often tell you the complexity you need.

| n up to about | Aim for |
|---|---|
| 10 to 12 | O(n!) or O(2ⁿ · n): try everything |
| 20 to 25 | O(2ⁿ) |
| 500 | O(n³) |
| 5,000 | O(n²) |
| 10⁵ to 10⁶ | O(n log n) or O(n) |
| 10⁹ and more | O(log n) or O(1): a formula or binary search |


### Counting it

```python
def has_duplicate(nums):            # O(n²) time, O(1) extra space
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False

def has_duplicate_fast(nums):       # O(n) time, O(n) extra space
    seen = set()
    for x in nums:
        if x in seen:
            return True
        seen.add(x)
    return False
```

This trade (**more memory for less time**) is the most common improvement in interviews.

### Python costs to know

| Operation | Cost |
|---|---|
| `list.append`, `list.pop()` (end), `a[i]` | O(1) |
| `list.insert(0, x)`, `list.pop(0)`, `x in list` | O(n) |
| `x in set`, `d[key]`, `set.add` | O(1) on average |
| `sorted(a)`, `a.sort()` | O(n log n) |
| slicing `a[i:j]` | O(j − i): it copies |
| `s += "x"` in a loop | can be O(n²): build a list and `"".join()` |

## A method for every problem

Use the same steps every time, out loud:

1. **Understand.** Restate the problem. Ask about edge cases: empty input? negatives? duplicates? how big is n?
2. **Examples.** Work one small example by hand, plus an edge case.
3. **Brute force first.** Say the simple solution and its Big-O. It shows you can solve it, and gives you something to improve.
4. **Improve.** Ask: what work am I repeating? Could sorting, a hash map, two pointers or a heap remove it?
5. **Code** clearly, with good names.
6. **Test** by tracing your example through the code, then the edge cases.
7. **State the final time and space complexity.**

Interviewers grade the **process** as much as the answer. A clear brute force plus a good discussion beats silent, buggy "optimal" code.
