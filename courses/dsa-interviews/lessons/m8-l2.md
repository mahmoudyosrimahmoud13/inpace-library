# Interview playbook and pattern map

## Which pattern? A quick map

| If the problem says... | Try |
|---|---|
| Sorted array, find a pair or target | Two pointers, binary search |
| "Have I seen it?", counting, pairs that sum to k | Hash map / set |
| Longest / shortest **contiguous** substring or subarray | Sliding window |
| Sum of a range, many queries | Prefix sums |
| Brackets, nested things, "next greater" | Stack (monotonic) |
| Minimum X such that... with a yes/no check | Binary search on the answer |
| Top k, k-th largest, merge sorted lists, running median | Heap |
| All subsets, permutations, combinations | Backtracking |
| Tree: depth, paths, compare subtrees | DFS recursion |
| Levels, nearest, fewest steps | BFS |
| Grid of cells, islands, regions | DFS / BFS on a grid |
| Prerequisites, order of tasks | Topological sort |
| Count ways, min/max cost, "is it possible" with choices | Dynamic programming |
| Schedules, intervals, "as many as possible" | Sort + greedy |

## The 45-minute interview, minute by minute

| Time | What you do |
|---|---|
| 0–5 | Repeat the problem, ask about input size, empty input, duplicates, negatives |
| 5–10 | Work an example by hand; say the brute force and its Big-O |
| 10–15 | Find the better approach; say it **before** coding and get a nod |
| 15–35 | Code it, talking as you go; good names, small helpers |
| 35–40 | Trace an example through your code; check edge cases |
| 40–45 | State time and space complexity; mention trade-offs or improvements |

## Talking while you code

Say what you're doing and why: "I'll keep a dict from value to index so I can check the complement in O(1)." Silence makes interviewers guess; a clear explanation earns credit even when the code has a bug.

If you get stuck:
- Go back to the brute force and ask what work repeats.
- Try a smaller or sorted version of the input.
- Ask "would a hash map / heap / sort help here?" against the pattern map.
- Say what you're thinking. Interviewers often give a hint when they hear where you are.

## Testing your own code

Before saying "done":
1. Trace your hand example line by line.
2. Run the edge cases: empty, one element, all equal, negatives, the largest input.
3. Look for off-by-one errors in loops and slices.

## A study plan that works

- **Pattern by pattern**, not random problems: 5–8 problems per pattern from this course's lists.
- **Time-box**: 25 minutes on a problem before reading a hint; then rewrite the solution yourself the next day without looking.
- **Spaced repetition**: redo problems you got wrong after 3 days and after a week. (inPace's quizzes and Tempo reminders help here.)
- **Mock interviews** with a friend: one asks, one solves out loud. Swap. Free sites like Pramp also pair you with people.
- About **100 well-understood problems** covering every pattern beats 400 skimmed ones.

## Final project

Solve **one problem per pattern** in the map above (14 problems) in a GitHub repository. For each one, write in its file:
- The pattern and why it fits.
- The brute force and its Big-O.
- Your solution and its Big-O.
- One edge case you tested.

That repository is proof of your practice. Link it on your CV, and use it to revise the week before an interview.
