# Project 7: is it a 9? A rare class

You'll build a "9 or not" detector, where 9s are only 10% of the digits, and see why accuracy misleads and how the
threshold trades precision for recall.

The code is above this text. Save it as `p7_skewed.py`.

## Read the code

- The labels become 1 for a 9, 0 otherwise. A small network with a sigmoid output gives a probability.
- It counts, for five thresholds: accuracy, **precision** (of those called 9, how many are), **recall** (of the real
  9s, how many were found) and **F1** (their harmonic mean).

## Run it

```bash
python p7_skewed.py
```

The real output:

```text
1. 10% of validation digits are 9s. A model that always says 'not a 9' is 90% accurate.

2. The same model at different thresholds:
   threshold  accuracy  precision  recall     F1
         0.1     93.3%      60.0%  100.0%   0.75
         0.3     97.2%      79.5%   97.2%   0.88
         0.5     98.3%      91.7%   91.7%   0.92
         0.7     97.2%     100.0%   72.2%   0.84
         0.9     93.9%     100.0%   38.9%   0.56

   Precision: of the digits called 9, how many are. Recall: of the real 9s, how many were found.
   Raising the threshold buys precision with recall. Pick it for the cost of each mistake.
```

What it shows:

- **"Never a 9" is 90% accurate** and useless. Accuracy hides it.
- **At 0.1 the detector finds every 9**, but 4 in 10 of its alarms are wrong. **At 0.9 every alarm is right**, but it
  misses 6 in 10 nines.
- **0.5 has the best F1** here. In a real product you'd pick by cost: missing a fraudulent payment and blocking a
  good one cost different amounts.

## Make it yours

1. Find the threshold with the best F1 on validation data in steps of 0.05, then report precision and recall on the
   test set at that threshold.
2. Train with `class_weight={0: 1, 1: 9}` in `fit`. How do precision and recall at 0.5 change?

## What to take away

- On rare classes, report precision and recall, not accuracy.
- The threshold is a business decision; F1 is a starting point.
