# Source systems: what they keep, and what they forget

## CRUD forgets, logs remember

An order at Inkwell changes over a week:

| When | What the app does | What the `orders` table shows afterwards |
|---|---|---|
| Mon 10:02 | INSERT order 42, status `placed` | 42, placed |
| Tue 09:15 | UPDATE status = `shipped` | 42, shipped |
| Thu 14:40 | UPDATE status = `delivered` | 42, delivered |

On Friday, the table only knows "42 is delivered". The question "how long do orders take to ship?" can't be answered
from it, because UPDATE overwrote Monday and Tuesday. Three ways to keep the history:

| Way | How | Cost |
|---|---|---|
| **Insert-only table** | The app writes a new row per change | Bigger tables; "current state" needs a query |
| **Change data capture from the database log** | A tool reads the log the database already writes (Debezium, cloud CDC services) | Setup and access to the log |
| **Frequent snapshots** | Copy the whole table every hour | Misses changes between copies; heavy on big tables |

Today's project builds Inkwell's database with a **change log filled by triggers**, so you can do CDC tomorrow.

## Four kinds of time

| Time | Meaning | Inkwell example |
|---|---|---|
| **Event time** | When it happened at the source | 21:14, a visitor taps "Buy" on the train |
| **Ingestion time** | When it landed in our systems | 08:30 next day, the phone came back online |
| **Process time** | When we processed it | 02:00, the nightly job |
| **Processing time** | How long processing took | 4 minutes |

If you count "sales per day" by ingestion time, the 21:14 sale lands on the wrong day. Report by **event time**, and
expect some events to arrive **late**.

## Questions to ask a source system's owner

- How do I get the data: a read replica, an export, an API, a CDC feed?
- Do rows change after they're written? Is there an `updated_at` I can trust? Are deletes soft or hard?
- What times does a record carry, and in which time zone?
- How will you tell me before the schema changes? (This is what a **data contract** writes down.)
- How much data per day, and how will that grow?

## What to take away

- Ask whether a source keeps history; if not, capture changes before they're overwritten.
- Queues hand messages over once; streams keep a log you can replay.
- Report by event time, and plan for late data.
