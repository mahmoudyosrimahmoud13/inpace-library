# Project 10, part 1: the SQL models

Today Inkwell gets a real warehouse, `inkwell_data/warehouse.duckdb`, built by a tested pipeline. Part 1 is the
models: one SQL file per table. Part 2 (next lesson) is the runner and the tests.

The files are shown above this text. Save them into `inkwell/models/` with the same names.

## The staging models: clean, no business logic

- **`stg_orders.sql`**: the latest version of each order (the `QUALIFY row_number()` pattern from yesterday), with
  text times turned into real timestamps.
- **`stg_order_lines.sql`**: `DISTINCT`, because a re-run batch could land the same lines twice.
- **`stg_books.sql`**: the newest snapshot.
- **`stg_customer_changes.sql`**: every CDC change, typed.
- **`stg_events.sql`**: one row per `event_id` (duplicates removed) and a flag `arrived_late`.

`{raw:orders}` is a placeholder: the runner replaces it with "read every Parquet file under `lake/raw/orders/`".

## The model: dimensions and facts

- **`dim_customer.sql`**: the type 2 dimension from project 9. `WINDOW w AS (...)` names the window once so both
  `lead()` calls share it. It also adds `is_deleted` for closed accounts.
- **`dim_book.sql`** and **`dim_date.sql`** (every day from the first order to the last, so days with no sales still
  appear in reports).
- **`fct_sales.sql`**: grain = one row per order line, joined to the customer version valid at order time. It's a
  `LEFT JOIN` on purpose: if a sale finds no customer version, the row stays with an empty `customer_key`, and a
  **test** catches it. An inner join would silently drop the sale.
- **`fct_events.sql`**: marked `-- materialized: incremental, unique_key: event_id`.

## The mart

- **`mart_daily_sales.sql`**: one row per day for the owner: orders, revenue, buyers, average order value.
  Cancelled orders are excluded *in the join condition*, so a day with only cancelled orders still shows up, with 0.

## The first comment line of each file

`-- depends_on: stg_orders, stg_order_lines, dim_customer` is how a model declares its inputs. Staging models have
none: they read raw files. Open each file and check its dependencies match what its `FROM` and `JOIN` lines use. A
missing dependency is a classic bug: the model may run before its input is ready.

## What to take away

- One file per model, one `SELECT` per file, dependencies declared at the top.
- Staging cleans; the model holds the business logic; marts serve questions.
