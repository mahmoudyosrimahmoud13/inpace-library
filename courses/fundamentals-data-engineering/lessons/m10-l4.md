# Project 10, part 2: the runner, the tests, and publishing safely

The code above is the runner, `p10_transform.py`. Save it in `inkwell/`. The tests are short; create the folder
`inkwell/tests/` and save each one as its own file:

```sql
-- tests/unique_order_id.sql: fails if an order appears twice in staging
SELECT order_id, count(*) FROM stg_orders GROUP BY 1 HAVING count(*) > 1

-- tests/sale_has_customer.sql: fails if a sale found no customer version
SELECT * FROM fct_sales WHERE customer_key IS NULL

-- tests/status_values.sql: fails on any status the business didn't define
SELECT DISTINCT status FROM stg_orders WHERE status NOT IN ('placed', 'shipped', 'delivered', 'cancelled')

-- tests/one_current_customer_row.sql: fails if a customer has zero or several current rows
SELECT customer_id FROM dim_customer GROUP BY 1 HAVING sum(CAST(is_current AS INTEGER)) <> 1

-- tests/book_exists.sql: every sale points to a book we know
SELECT f.* FROM fct_sales f LEFT JOIN dim_book b USING (book_key) WHERE b.book_key IS NULL

-- tests/amounts_positive.sql
SELECT * FROM fct_sales WHERE qty <= 0 OR unit_price <= 0
```

## Read the runner

- **`read_models()`** reads every `.sql` file, finds `depends_on` and `materialized` in the comments, and replaces
  `{raw:...}` with a Parquet reader.
- **`TopologicalSorter`** (from Python's standard library) turns the dependencies into a build order: a DAG.
- **WRITE.** Every model is built into a schema called `staging`. `SET search_path = 'staging,main'` makes models
  find each other there first.
- **Incremental models.** `fct_events` keeps everything it has stored in `main`. The runner stages only the **new**
  rows (`event_id NOT IN` what's stored) and shows old plus new to the tests.
- **AUDIT.** Every test runs. Any rows returned means failure: the script logs which tests failed and exits with
  code 1, **without publishing**.
- **PUBLISH.** Only when every test passes: full-refresh tables are copied to `main`, new incremental rows are
  appended, and the `staging` schema is dropped.

## Make a test fail, on purpose

Create `tests/zz_fails.sql` containing `SELECT 1 AS broken` and run again. The run stops after the audit, says which
test failed, and exits with an error; the tables in `main` are untouched. Delete the file afterwards.

A more realistic one: in `models/fct_sales.sql`, change `LEFT JOIN dim_customer` to `JOIN dim_customer` and break the
time condition (`<` to `<=` on `valid_from`). Which tests catch it, and which don't? What does that tell you about the
tests you still need?

## Make it yours

1. Add a test that the revenue in `mart_daily_sales` equals the revenue in `fct_sales` (not counting cancelled
   orders). A test that compares totals across layers catches a whole family of join bugs.
2. Add a "freshness" test: fail if the newest order in `stg_orders` is more than 2 days older than today's date.
   (It will fail on this simulated data. Why is that the right result?)

## What to take away

- A pipeline is a DAG of models plus tests.
- Write, audit, publish: users never see data that failed its tests.
- Incremental loads keep re-runs cheap and safe.
