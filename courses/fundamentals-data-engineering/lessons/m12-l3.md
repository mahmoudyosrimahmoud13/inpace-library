# Project 12, part 1: privacy, least privilege and tested backups

Inkwell is hiring a part-time analyst. She needs sales data, not customers' names and emails. And the owner asks
what happens if the laptop with the warehouse dies.

The code is above this text. Save it as `p12_secure.py`. Run project 10 first.

## Read the code

- **The key.** `INKWELL_PII_KEY` comes from the environment. Without it the script uses a development key and says so
  loudly: fine for learning, never for real data.
- **`pseudonym()`** is an HMAC-SHA256 of the email with the key, cut to 16 characters. The same email always gives
  the same pseudonym (so the analyst can count repeat customers), and nobody without the key can match it to an email.
- **The analyst's database.** A separate file, `analyst.duckdb`. The script builds a temporary map from customer key to
  pseudonym, then `ATTACH`es the warehouse **read-only** and copies only safe columns into a `sales` table: order,
  pseudonym, city, genre, title, date, status, quantity, amount. Then it **drops the map**, so the analyst's file can't
  link pseudonyms back to keys.
- **The PII check** lists every column handed over and fails the whole step if a name looks personal (`email`,
  `name`, `phone`, `address`), or if a text value contains `@`. If it fails, the file is deleted: nothing half-safe is
  left behind.
- **The backup.** `EXPORT DATABASE` writes every table as Parquet into `backups/<date-time>/`. Then the test that
  matters: `IMPORT DATABASE` into an **empty in-memory database** and compare the row count of every table.
- **Retention.** Only the newest 7 backups are kept.

## Run it

Set a key first (pick any long random text), then run:

```bash
# Windows PowerShell
$env:INKWELL_PII_KEY = "change-me-to-a-long-random-secret"
# macOS and Linux
export INKWELL_PII_KEY="change-me-to-a-long-random-secret"

python p12_secure.py
```

The real output:

```text
analyst.duckdb ready: 15 columns, no personal data (PII check passed)
Backup 20261124-065154-490: 11 tables exported and restored with the same row counts
[p12] secured  analyst_columns=15  backup=20261124-065154-490  tables=11  deleted_old_backups=0
```

What the analyst sees (the first two rows of `sales`, read with DuckDB):

```text
order_id | customer_pseudonym | city | genre | title | date_key | status | qty | amount
1 | fcf7978bb8f81f60 | Alexandria | Self-help | Atomic Habits | 2026-03-01 | delivered | 1 | 15.0
1 | fcf7978bb8f81f60 | Alexandria | Fiction | The Alchemist | 2026-03-01 | delivered | 1 | 10.0
```

No names, no emails, and still everything she needs to count customers, cities and genres.

## Make it yours

1. Run the script twice with two different keys. Do the pseudonyms change? What does that mean for the analyst's
   reports if someone changes the key, and how would you rotate a key safely?
2. Add a `masked_email` column (first letter, stars, domain) to the analyst's `sales` table and run again. What does
   the PII check do? Is it right?
3. Break a backup on purpose: after the export, delete one Parquet file from the newest backup folder and run only
   the restore part. Make sure the script refuses it.
4. Write Inkwell's **one-page security policy**, modelled on the book's example: credentials, devices, data, backups.

## What to take away

- Give each audience the smallest safe dataset, in its own place.
- Keyed pseudonyms keep data useful and people protected.
- A backup counts only once you've restored it.
