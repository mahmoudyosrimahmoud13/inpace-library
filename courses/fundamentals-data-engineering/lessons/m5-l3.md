# Project 5: Inkwell's source systems

Real data engineers don't build the source systems. But to learn ingestion you need a source that behaves like a real
one: updates that overwrite, deletes, late and duplicate events, broken records. So today you build Inkwell's two
sources and simulate a week of business.

The code is above this text. Save it as `p05_source_system.py`. From now on, every project builds on the data it makes.

## Read the code

**The shop database** (`inkwell_data/source/shop.db`, SQLite, the most common database in the world):

- `SCHEMA` creates the app's tables: `customers`, `books`, `orders`, `order_lines`. Every table has a primary key.
  Customers and orders carry `created_at` and `updated_at`; customers have `deleted_at` for **soft deletes** (the row
  stays, marked as deleted).
- `TRIGGERS` copy every insert and update of customers and orders into `change_log`, as a JSON snapshot of the row.
  This plays the part of the database's own log that a CDC tool reads.
- `simulate_day()` does a day of CRUD: new customers sign up (INSERT), two customers move city (UPDATE), every fourth
  day someone closes their account (soft DELETE), open orders move `placed -> shipped -> delivered` or get
  `cancelled` (UPDATE), and 8 to 15 new orders arrive with 1 to 3 books each (INSERT).

**The click events** (`inkwell_data/source/events/events-YYYY-MM-DD.jsonl`, insert-only):

- every order gets four events (two page views, add to cart, purchase), plus 20 to 40 visitors who only look;
- each event has an `event_id` and its **event time**;
- three events a day arrive **a day late**, in the next day's file; two arrive **twice**; and the last line of every
  file is **broken** JSON.

Each run continues from the last simulated day (kept in the `meta` table). The random generator is seeded with the
date, so your data will match the output below.

```python
import sqlite3
db = sqlite3.connect("inkwell_data/source/shop.db")
print(db.execute("SELECT status, count(*) FROM orders GROUP BY status").fetchall())
print(db.execute("SELECT op, row_json FROM change_log WHERE table_name='orders' AND row_id=1").fetchall())
```

The second query shows order 1's whole life, which the `orders` table itself no longer remembers.

## Make it yours

1. Find a customer who moved city. Compare their row in `customers` with their rows in `change_log`.
2. Open an events file. Find the broken last line, and an `event_id` that appears twice.
3. Write a short **data contract** for the `orders` table as if you were agreeing it with the app team: columns and
   types, what `updated_at` means, how deletes work, how much notice they'll give before changing the schema.

## What to take away

- Real sources update, delete, duplicate, arrive late and break. Your pipeline must expect all of it.
- A change log keeps the history that UPDATE throws away.
