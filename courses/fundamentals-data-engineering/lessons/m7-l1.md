# Read: Chapter 7, Ingestion

Ingestion moves data from source systems into storage. It sounds simple, and it's where most pipelines break. Read
the whole chapter; the considerations here are what interviewers ask about.

## Key engineering considerations

Read each, and write one question you'd ask before building:

- **Bounded versus unbounded data**: the authors' mantra, *all data is unbounded until it's bounded*.
- **Frequency**: batch, micro-batch, real time.
- **Synchronous versus asynchronous** ingestion: what happens downstream when one step fails?
- **Serialization and deserialization**.
- **Throughput and scalability**: bursts, backlogs, and source systems that can't keep up.
- **Reliability and durability**: what's the cost of losing data, and of preventing it?
- **Payload**: kind, shape, size, **schema and data types**, **schema changes**, schema registries, metadata.
- **Push, pull and poll** patterns.

## Batch ingestion

**Snapshot versus differential (incremental)** extraction; file-based export; **ETL versus ELT**; inserts, updates and
batch size (why many small inserts hurt a warehouse); data migration.

## Message and stream ingestion

Schema evolution, **late-arriving data**, **ordering and multiple delivery** (*at-least-once* means duplicates),
**replay**, time to live, message size, **error handling and dead-letter queues**, consumer pull and push, location.

## Ways to ingest data

A long tour. Read *Direct database connection* (ODBC and JDBC), **change data capture** (**batch-oriented CDC**,
querying an `updated_at` column for rows changed since the last run, versus **continuous CDC**, reading every change
from the database log), APIs, message queues, **managed data connectors** (the "don't build what you can buy" argument
again), object storage, EDI, file exports, the shell, SSH, SFTP and SCP, webhooks, web interfaces, web scraping,
transfer appliances, data sharing. Skim the ones you'll never use, and note *Practical issues with common file formats* (CSV again).

## Whom you'll work with, and the undercurrents

Upstream and downstream stakeholders, then the undercurrents. Read **data management** (schema changes, privacy:
note the warning that hashing without a **salt** may not protect people) and **DataOps** carefully: monitor uptime,
latency and data volume from day one. The authors tell of an ingestion failure that went unnoticed for six months.

## After reading

For one source you know, choose: snapshot or incremental? push, pull or poll? What would you do with a record you
can't read?

## What to take away

- Incremental ingestion needs a reliable marker of change, and a stored bookmark of how far you got.
- At-least-once delivery means duplicates; plan to remove them.
- Bad records go to a dead-letter queue, not into the lake and not into the bin.
