# Project 6: four storage formats, measured

Inkwell is planning its data lake. Before choosing a file format, measure. You'll save the same table as CSV, JSON
lines and Parquet with three compression codecs, and compare size and query speed. Then you'll build a **partitioned**
lake and watch a query skip the folders it doesn't need.

The code is above this text. Save it as `p06_storage.py`.

## Read the code

- **`make_history()`** creates a table of a million order lines over five years (simulated: Inkwell's own week of
  data is too small to measure anything). Each line has a date, customer, genre, book, quantity, price and city.
  `setseed(0.6)` makes the random numbers the same on every run.
- For each format, `COPY history TO ... (FORMAT ...)` writes the file, and the script times **one typical analytics
  question**: revenue per genre. It runs the question once to warm up (the first read fills the operating system's
  cache), then times the second run.
- `PARTITION_BY (year, month)` writes one folder per month, named `year=2024/month=3`. This naming style is called
  **Hive partitioning**, and nearly every lake tool understands it.
- The script then times a one-month query against a whole-table query, and checks the **query plan** (`EXPLAIN`) for
  the file filter.
- At the end it deletes the big CSV and JSON files to free disk space.

## Run it

```bash
python p06_storage.py
```

It needs about 300 MB of free disk for a minute. On a small laptop, use `python p06_storage.py --rows 300000`.
The real output with `--rows 300000` (your times will differ; compare the rows, not the absolute numbers):

```text
300,000 order lines

Format            Size MB  Write ms  Query ms
CSV                  14.2       123        74
JSON lines           40.9       131       114
Parquet snappy        3.2        45         4
Parquet gzip          2.3       187         4
Parquet zstd          2.2        46         3

Partitioned lake: 60 month folders, 4.5 MB
  one month (reads 1 folder):       4 ms
  everything (60 folders):        14 ms
  The plan's file filter: yes
```

What the numbers say:

- **JSON lines is the biggest**, nearly 3 times the CSV: every line repeats every column name.
- **Parquet is 4 to 6 times smaller than CSV, and about 20 times faster** to query, because it reads two columns, not
  eight, and doesn't have to parse text.
- **gzip** compresses a little better than snappy but **writes about 4 times slower**. **zstd** gets gzip's size at
  snappy's speed, which is why many teams now default to it.
- The partitioned query reads 1 of 60 folders.

## Make it yours

1. Run with `--rows 2000000` if you have the disk space. Do the ratios stay the same?
2. Change `QUESTION` to `SELECT * FROM {src} WHERE line_id = 12345` (fetch one whole record). You might expect the
   row formats to win now. They don't: Parquet keeps the minimum and maximum of each column for every block of rows
   ("row group statistics"), so it can skip most of the file. Look up how that works, and when it stops helping
   (hint: what if the rows weren't sorted by `line_id`?).
3. Add `PARTITION_BY (city)` as a second lake. Which questions would it speed up, and which would it slow down?
4. Write **ADR 4**: the format and compression you choose for Inkwell's lake, with your measurements.

## What to take away

- Measure formats on your own data and your own questions before choosing.
- Parquet with snappy or zstd is the sensible default for analytics files.
- Partition by what people filter on.
