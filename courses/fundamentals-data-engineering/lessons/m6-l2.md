# Rows, columns, and where data lives

## Row-based versus columnar

The same three orders, stored two ways:

```text
Row-based (CSV, JSON lines, Avro): one record after another
  1, 2026-03-01, Cairo, Tech, 32.0
  2, 2026-03-01, Giza,  Fiction, 12.0
  3, 2026-03-02, Cairo, Classic, 9.5

Columnar (Parquet, ORC): one column after another
  id:     1, 2, 3
  date:   2026-03-01, 2026-03-01, 2026-03-02
  city:   Cairo, Giza, Cairo
  genre:  Tech, Fiction, Classic
  price:  32.0, 12.0, 9.5
```

"Revenue by genre" needs two columns. A columnar file lets the engine read **only those two**, and similar values sit
next to each other, so they **compress** far better. That's why analytics systems store columns. Row formats win when
you read or write whole records, one at a time, which is what apps do.

| | CSV | JSON lines | Parquet |
|---|---|---|---|
| Layout | Rows, text | Rows, text | Columns, binary |
| Schema inside the file | No (just a header) | Names on every line, no types | Yes, with types |
| Compression | Whole file only | Whole file only | Per column, built in |
| Good for | Exchanging with people and old systems | APIs, logs, nested data | Analytics, lakes |

## File, block and object storage

| | File storage | Block storage | Object storage |
|---|---|---|---|
| Looks like | Folders and files | A raw disk | A flat key-value store of whole objects |
| Examples | Network drives, Amazon EFS | The disk under a VM or database | Amazon S3, Google Cloud Storage, Azure Blob |
| Change part of a file | Yes | Yes | No: rewrite the whole object |
| Scale and price | Medium | Fast, more expensive | Nearly unlimited and cheap |
| Data engineering use | Shared files, small teams | Databases, VM disks | **Data lakes** |

## Partitioning: storage that helps queries skip data

A **partitioned** lake splits data into folders by a column you often filter on:

```text
lake/history/year=2024/month=3/data_0.parquet
lake/history/year=2024/month=4/data_0.parquet
...
```

A query for March 2024 opens one folder instead of sixty. Partition by what people filter on (usually a date), and
keep partitions big enough: thousands of tiny files are slow too.

## Separating compute from storage

Old warehouses kept data on the same machines that queried it: to store more, you bought more compute, and the
other way round. Modern systems keep data in object storage and start query engines only when needed. You pay for
storage all the time and for compute only while it runs, and several engines can read the same data. Today's project
does this on a small scale: Parquet files on disk, and DuckDB as the engine that comes and goes.

## Hot, warm and cold

| | How often read | Typical home | Cost to store | Cost to read |
|---|---|---|---|---|
| Hot | Many times a day | Memory, SSD, warehouse | High | Low |
| Warm | About once a month | Standard object storage | Medium | Medium |
| Cold | Rarely, kept for compliance | Archive storage classes | Very low | High, and slow |

## What to take away

- Columnar formats read only the columns a query needs and compress well.
- Object storage plus partitioned Parquet is a simple, cheap, fast data lake.
- Match the storage tier to how often data is read.
