# Project 8: query plans, pruning, a join that lies, and windows

Today you query the lake you built and learn to see what the engine does. Part A uses project 6's partitioned
history; part B uses the events you ingested in project 7.

The code is above this text. Save it as `p08_queries.py`. Run projects 6 and 7 first.

## Read the code

- **`SRC`** reads every Parquet file of the partitioned lake. `hive_partitioning = true` turns the folder names
  (`year=2024/month=3`) into columns you can filter on.
- **`timed()`** runs a query once to warm up, then three times, and keeps the fastest time. Timing a single run is
  misleading: caches and other programs on your laptop add noise.
- **A1** prints the plan with `EXPLAIN`, without running the query.
- **A2** times `SELECT *` against two columns. **A3** times a filter on `order_date` against a filter on the partition
  columns.
- **A4** joins 2024's order lines with a small `cities` table in which Cairo appears twice.
- **B** counts purchases per 6-hour **tumbling window** by **event time** with `time_bucket()`, using
  `count(DISTINCT event_id)` so duplicate deliveries don't count twice. It then counts late events (event day
  earlier than the file's day) and duplicates.

What to notice:

- **A1**: the plan reads 3 columns (not 10), and `Scanning Files: 1/60`. The engine skipped 59 folders before reading
  a single row.
- **A2**: two columns are about 3 times faster than ten.
- **A3**: the filter on the partition columns is faster. DuckDB is clever enough to use statistics inside the files
  for the `order_date` filter too, but it still has to open every folder.
- **A4**: about 10,000 more lines after the join, and DuckDB raised no error. Every revenue total built on that join
  would be wrong.
- **B**: duplicates and late events are real in your data. Counting by event time and distinct `event_id` gives the
  right numbers.

## Make it yours

1. Fix A4 two ways: remove the duplicate Cairo row, or pick one region per city before joining
   (`SELECT city, min(region) AS region FROM cities GROUP BY city`). Show the row count matches.
2. Change B to **sliding** windows: 6 hours long, starting every 3 hours. Hint: generate the window starts with
   `range()`, then join events where `event_time >= start AND event_time < start + INTERVAL 6 HOUR`.
3. Count **sessions**: per customer, a new session starts when more than 30 minutes passed since their previous event.
   Hint: `lag(event_time) OVER (PARTITION BY customer_id ORDER BY event_time)`.
4. Run `EXPLAIN ANALYZE` on A1's query instead of `EXPLAIN`. What extra information do you get?

## What to take away

- `EXPLAIN` shows how much will be read before you pay for reading it.
- A wrong join gives a confident wrong number. Check counts.
- Event-time windows with de-duplication give honest counts from messy streams.
