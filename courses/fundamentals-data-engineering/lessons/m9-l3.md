# Project 9: three models of Inkwell's sales

The owner asks: **"Which cities buy which genres?"** You'll answer it from three models of the same raw data and see
where they agree and where they don't.

The code is above this text. Save it as `p09_model.py`. Run project 7 first. Everything goes into a scratch
database, `inkwell_data/p09.duckdb`, so you can explore freely. Tomorrow you'll turn the best of it into a tested
pipeline.

## Read the code

**1. Normalized.** Rebuild the app's tables from the raw zone:

- `orders`: ingestion stored *every version* of each order it saw. `row_number() OVER (PARTITION BY order_id ORDER BY
  updated_at DESC)` numbers the versions newest first; keeping `rn = 1` keeps the latest. You'll see this
  "latest version" pattern everywhere.
- `customers`: the latest change per customer from the CDC data. `QUALIFY` filters on a window function, like
  `HAVING` filters on an aggregate.

**2. Star schema.**

- `dim_customer` is a **type 2** dimension straight from the CDC changes: each change starts a new version;
  `lead(changed_at)` (the next change's time) ends it; the last version gets `valid_to = 9999-12-31` and
  `is_current = true`. `row_number()` gives each version a **surrogate key**.
- `dim_book` and `dim_date` (one row per day of the year, with weekday and weekend flag).
- `fact_sales`: grain = one row per order line. The key line is the join to `dim_customer` **by time**: the order's
  `created_at` must fall between the version's `valid_from` and `valid_to`. That picks the customer as they were
  when they ordered.

**3. One big table.** `obt_sales` joins everything once.

Then the script checks that **total revenue is the same in all three** (if not, a join is wrong), and shows where
"city today" and "city when they bought" disagree.

## Make it yours

1. Write the **grain** of `fact_sales` as a comment at the top of its `CREATE TABLE`.
2. Add a **type 1** customer dimension (one row per customer, current city) and answer the question with it. Which of
   the earlier results does it match?
3. Make `dim_book` type 2 as well: what would you need from ingestion to know when a book's price changed?
4. Open `p09.duckdb` in DuckDB's command line or a database tool (DBeaver is free) and draw the star schema: tables,
   keys and the grain.

## What to take away

- Check totals across models: matching totals mean your joins are sound.
- A time-aware join to a type 2 dimension ties every fact to the right version.
- Different models answer different questions; document which question each report answers.
