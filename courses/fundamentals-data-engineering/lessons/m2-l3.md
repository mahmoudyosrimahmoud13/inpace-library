# Project 2: the whole lifecycle in one small file

The owner's first question: **"How much did we sell each day?"** Before building anything big, answer it end to end
with the smallest possible pipeline. One function per lifecycle stage, so you can see every stage at once.

The code is above this text. Save it as `p02_lifecycle.py` in your `inkwell` folder.

## Read the code, stage by stage

- **`generate()`**: plays the shop's website. It writes one JSON line per order into `landing/`, a folder the source
  system drops files into. It uses a random generator seeded with the date, so the same day always gives the same
  orders. Line 7 of every file has `"price": null` on purpose: real sources send broken records.
- **`ingest()`**: copies files from `landing/` into `raw/`. The **file name is the key**: copying the same file
  again overwrites it, so running ingestion twice never doubles the data. That property has a name, **idempotent**:
  running a step once or many times gives the same result. You'll use it every day of this course.
- **`store()`**: opens a DuckDB database file. DuckDB reads the raw JSON files where they lie, like a query engine on
  a data lake.
- **`check_quality()`**: an undercurrent (data management). It counts records we can't trust.
- **`transform()`**: the business logic. Revenue is `price * qty`, bad rows are left out, results go per day.
- **`serve()`**: writes `daily_sales.csv`, which the owner can open in her spreadsheet, and prints it.
- The last line calls **`log()`** from `common.py` (DataOps): every run adds a line to `inkwell_data/logs/runs.jsonl`.

## Run it

```bash
python p02_lifecycle.py
```

The real output:

```text
Daily sales (report saved to daily_sales.csv):
  2026-03-01   19 orders     761.83
  2026-03-02   19 orders     682.97
  2026-03-03   19 orders     683.66
[p02] lifecycle run finished  files=3  bad_records=3  finished=2026-11-24T04:28:44Z
```

Twenty orders a day were generated, but the report shows 19: the broken one was kept out, and counted in
`bad_records=3` (one per day). Run it again: **the numbers don't change**. That's idempotent ingestion at work.

## Make it yours

1. Break idempotency on purpose: in `ingest()`, give each copy a new name, for example
   `RAW / f"{src.stem}-{now_utc()}.jsonl"`. Run twice. What happens to the revenue? Put it back.
2. Add a second quality rule: an order with `qty` above 10 is suspicious. Count those too.
3. Add a column to the report: average order value (revenue divided by orders).
4. Open `inkwell_data/logs/runs.jsonl`. What would you want an alert to say if `bad_records` jumped to 15?

## What to take away

- Even the smallest pipeline has all five stages.
- Keep raw data as it arrived; clean it in transformation.
- Idempotent steps make re-running safe, and you will re-run things.
