# Environments, approvals and promotion

**GitHub Environments** (`staging`, `production`) give each deploy target:

| Feature | Use |
|---|---|
| Environment secrets and variables | Prod credentials only available to jobs targeting prod |
| **Required reviewers** | A human approves before the job starts |
| Wait timer | e.g. 10 minutes after staging before prod |
| Deployment branches/tags | Only `main` or `v*` tags may deploy to production |
| Deployment history | Who deployed what, when, with links |

```yaml
  deploy-staging:
    needs: image
    environment: staging
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh staging ghcr.io/acme/shop@${{ needs.image.outputs.digest }}
      - run: ./smoke-test.sh https://staging.shop.example.com
  deploy-prod:
    needs: deploy-staging
    environment:
      name: production
      url: https://shop.example.com
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh production ghcr.io/acme/shop@${{ needs.image.outputs.digest }}
```

## Promotion, not rebuilds

The **same digest** moves staging -> production. Rebuilding for prod means prod runs something nobody tested.

## Config per environment

Keep config outside the image: environment variables, Parameter Store paths (`/shop/staging/...` vs `/shop/prod/...`), Kubernetes ConfigMaps, or Helm values files per environment.

## Smoke tests

After every deploy, a short script hits the health endpoint and one or two real pages/API calls. If it fails, stop the pipeline (and roll back, Day 6).
