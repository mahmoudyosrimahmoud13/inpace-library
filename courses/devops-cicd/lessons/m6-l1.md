# Rollback and safe database changes

## Rollback options, fastest first

1. **Turn off the feature flag.**
2. **Shift traffic back** (blue-green switch, canary to 0%).
3. **Redeploy the previous digest** (`kubectl rollout undo`, previous launch template version, `git revert` in GitOps).
4. **Roll forward** with a fix: only when it's small and quick.

Make rollback **one command or one click**, and practise it. A rollback nobody has tried fails at 3 a.m.

## Databases: the hard part

Code rolls back in seconds; data doesn't. During a rolling or canary deploy, **old and new code run against the same database**. So every schema change must work with both.

### Expand and contract

| Step | Deploy | Example: rename `fullname` to `name` |
|---|---|---|
| 1. Expand | Migration adds new things only | Add column `name` (nullable) |
| 2. Dual write | App writes both, reads old | Write `fullname` and `name` |
| 3. Backfill | Batch job | `UPDATE ... SET name = fullname WHERE name IS NULL` in batches |
| 4. Switch reads | App reads new | Read `name` |
| 5. Contract | Later release removes old | Drop `fullname` |

Each step is its own deploy, and each can roll back safely.

## Migration rules

- Migrations run **before** the new code (a pipeline step or init job), are versioned in Git (Alembic, Flyway, Liquibase, Rails/Django migrations) and run once.
- Avoid long locks on big tables: add indexes `CONCURRENTLY` (PostgreSQL), add columns without volatile defaults, batch updates.
- **Back up before** risky migrations, and know the restore time.
