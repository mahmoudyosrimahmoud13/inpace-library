# Branching and trunk-based development

How a team branches decides how hard CI is.

| Model | How | Good for | Pain |
|---|---|---|---|
| **Trunk-based** | Short-lived branches (hours to 2 days), merged to `main` behind tests; unfinished features hidden by **feature flags** | Most teams doing CI/CD | Needs discipline and flags |
| **GitHub flow** | Branch, PR, review, merge to main, deploy main | Web apps, small teams | Same as trunk-based, a bit looser |
| **Git flow** | `develop`, `release/*`, `hotfix/*`, `main` | Software with versioned releases to customers | Long-lived branches, painful merges, slow feedback |

## Rules that make CI work

- **Small PRs**: under ~400 lines changed reviews well; huge PRs get rubber-stamped.
- **Protected main**: required status checks, at least one review, no force pushes, linear history if you like.
- **Main is always deployable**. If it breaks, fixing it is the team's top priority (or revert).
- **Feature flags** separate *deploying* code from *releasing* a feature: merge dark, turn on for 5% of users, then everyone.

```bash
gh api repos/:owner/:repo/branches/main/protection --method PUT --input protection.json
gh pr create --fill && gh pr checks --watch
```

## Versioning

**Semantic versioning** (`MAJOR.MINOR.PATCH`) for things others depend on; release by tagging (`git tag v1.4.2`), and let the pipeline build releases from tags. For web services, the **commit SHA** is often the real version: every image is tagged with it.

**Conventional commits** (`feat:`, `fix:`, `chore:`) let tools generate changelogs and version bumps automatically.
