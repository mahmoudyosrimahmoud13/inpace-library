# State: making things change

**State** is data that changes over time and should update the page when it does: the list of tasks, which filter is chosen, whether a menu is open.

## `useState`

```tsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Clicked {count} times</button>;
}
```

- `useState(0)` gives the current value and a function to change it.
- Calling `setCount` tells React: "this changed, draw this component again".
- A normal variable (`let count = 0`) would reset on every render and never update the page.

With TypeScript, the type is inferred from the starting value. When it can't be (an empty array, or `null` at first), say it:

```tsx
const [tasks, setTasks] = useState<Task[]>([]);
const [selected, setSelected] = useState<Task | null>(null);
```

## Rules of hooks

Functions starting with `use` are **hooks**. Two rules:
1. Call them only at the **top level** of a component (not inside `if`, loops or nested functions).
2. Call them only from components or other hooks.

React relies on hooks being called in the same order every render.

## Never change state directly

```tsx
tasks.push(newTask);      // ❌ React doesn't notice; the page doesn't update
setTasks(tasks);          // ❌ same array, React thinks nothing changed

setTasks([...tasks, newTask]);  // ✅ a new array
```

React compares the **old and new value**. Always give it a new array or object:

| Change | How |
|---|---|
| Add | `setTasks([...tasks, t])` |
| Remove | `setTasks(tasks.filter(t => t.id !== id))` |
| Update one | `setTasks(tasks.map(t => t.id === id ? { ...t, done: !t.done } : t))` |
| Change a field of an object | `setUser({ ...user, name: "Sara" })` |

## Updating from the previous value

State updates are applied **after** your function finishes. If the new value depends on the old one, pass a function:

```tsx
setCount(c => c + 1);
setTasks(prev => [...prev, newTask]);
```

This is always correct, even when several updates happen quickly.

## Where should state live?

Put state in the **closest common parent** of every component that needs it. If `TaskList` and `Progress` both need the tasks, the tasks live in `App`, and both get them as props.

```tsx
export default function App() {
  const [tasks, setTasks] = useState<Task[]>([]);
  const toggle = (id: number) =>
    setTasks(prev => prev.map(t => (t.id === id ? { ...t, done: !t.done } : t)));

  return (
    <>
      <Progress done={tasks.filter(t => t.done).length} total={tasks.length} />
      <TaskList tasks={tasks} onToggle={toggle} />
    </>
  );
}
```

This is called **lifting state up**.

## Don't store what you can calculate

```tsx
const [tasks, setTasks] = useState<Task[]>([]);
const [doneCount, setDoneCount] = useState(0);   // ❌ can get out of sync

const doneCount = tasks.filter(t => t.done).length; // ✅ calculated every render
```

If a value can be worked out from other state or props, calculate it. Fewer pieces of state means fewer bugs.
