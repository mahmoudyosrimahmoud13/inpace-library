# TypeScript in practice

## Generics: types that take a type

Some functions work the same for any type. **Generics** keep the type information flowing through:

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}

const n = first([1, 2, 3]);        // n: number | undefined
const s = first(["a", "b"]);       // s: string | undefined
```

You'll mostly **use** generics rather than write them: `useState<Task[]>([])`, `Promise<Task>`, `Array<string>`, `Record<string, number>`.

## Utility types you'll use every week

```ts
type Task = { id: number; title: string; done: boolean; due?: string };

type NewTask   = Omit<Task, "id">;            // everything except id
type TaskPatch = Partial<Task>;               // every field optional
type Preview   = Pick<Task, "id" | "title">;  // only these fields
type ById      = Record<number, Task>;        // an object map: id → Task
```

They let you describe "a task before it's saved" or "an update to a task" without copying the type by hand.

## Typing data from the outside world

TypeScript can't check what a server sends. You **declare** what you expect:

```ts
async function loadTasks(): Promise<Task[]> {
  const res = await fetch("/api/tasks");
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return (await res.json()) as Task[];
}
```

`as Task[]` is a promise you make to the compiler, not a check. For important data, validate it at runtime (a small `isTask(x)` function, or a library like Zod). Inside your app, the types then keep everything honest.

## `tsconfig.json`: the settings that matter

Every TypeScript project has a `tsconfig.json`. You'll rarely touch it, but know these:

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "ES2022",
    "module": "ESNext",
    "jsx": "react-jsx",
    "noUncheckedIndexedAccess": true
  }
}
```

- `strict`: all the important checks. Always on.
- `jsx`: lets `.tsx` files contain JSX (React's HTML-like syntax).
- `noUncheckedIndexedAccess`: `arr[5]` is treated as maybe `undefined`. Annoying at first, catches real bugs.

## Reading errors like a pro

TypeScript errors are long because they explain the whole path. Read them **from the bottom up**: the last line is usually the real mismatch.

```
Type '{ id: number; title: string; }' is not assignable to type 'Task'.
  Property 'done' is missing in type '{ id: number; title: string; }' but required in type 'Task'.
```

The second line is the fix: you forgot `done`.

## Common beginner traps

| Trap | Better |
|---|---|
| Sprinkling `any` to silence errors | Fix the type, or use `unknown` and narrow |
| `as` everywhere | Narrow with `if` checks; keep `as` for data from outside |
| Writing types for every variable | Let inference work; type parameters and data shapes |
| Turning `strict` off | Never. The errors are the point |

You now know enough TypeScript to write React apps: basic types, object types, unions and narrowing, generics you'll meet in libraries, utility types, and how to type outside data. Tomorrow, React.
