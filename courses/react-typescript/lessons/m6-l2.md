# Fast and accessible

## When does a component render again?

A component re-renders when **its state changes**, when **its parent re-renders**, or when a **context it reads** changes. Re-rendering is usually cheap: React compares the result and touches the real page only where something changed.

So the first rule of performance: **don't optimize until something feels slow.** Then measure with the React DevTools Profiler (a browser extension) to find what's actually slow.

## Common real fixes

**1. Keys.** Correct, stable keys (Day 2) avoid rebuilding whole lists.

**2. Keep state close to where it's used.** A text box whose state lives at the top of the app makes the whole app re-render on every keystroke. Move that state into the form component.

**3. Expensive calculations: `useMemo`.**

```tsx
const stats = useMemo(() => computeStats(tasks), [tasks]); // recomputed only when tasks change
```

**4. Skip re-rendering a heavy child: `memo`.**

```tsx
const TaskRow = memo(function TaskRow({ task, onToggle }: RowProps) { ... });
```

`memo` only helps if the props are actually the same between renders. A new arrow function every render breaks it, which is what `useCallback` is for:

```tsx
const toggle = useCallback((id: number) => dispatch({ type: "toggle", id }), []);
```

(The React Compiler, newer in React 19, can add these automatically. Know what they do anyway.)

**5. Long lists.** Thousands of rows? Show only the visible ones with a virtualization library (TanStack Virtual).

**6. Load less JavaScript up front.** Split rarely used pages into separate files:

```tsx
const Stats = lazy(() => import("./pages/Stats"));
<Suspense fallback={<p>Loading…</p>}><Stats /></Suspense>
```

## Accessibility: an app everyone can use

About one in six people lives with a disability, and many more use keyboards, small screens or bright sunlight. Most accessibility comes from **using the right HTML**.

| Do | Instead of |
|---|---|
| `<button onClick>` | `<div onClick>` (no keyboard, no role) |
| `<a>` / `<Link>` to go somewhere | a button that navigates |
| `<label htmlFor>` for every input | placeholder as the only label |
| Real headings in order (`h1`, `h2`, `h3`) | big bold `div`s |
| `alt` text on meaningful images, `alt=""` on decorative ones | no `alt` |
| Visible focus outlines | `outline: none` with nothing else |

Extra care for React apps:
- **Announce changes**: an error message with `role="alert"`, a status line with `aria-live="polite"` ("Task added").
- **Move focus** sensibly when you open a dialog (and back when it closes). The native `<dialog>` element does much of this for you.
- **Colour isn't enough**: a done task needs more than a green colour (a tick, a line through).
- **Contrast**: text at least 4.5:1 against its background.

## Test it yourself

1. Unplug the mouse: can you do everything with Tab, Shift+Tab, Enter, Space and Escape?
2. Run **Lighthouse** (in Chrome's DevTools) for accessibility and performance scores and fixes.
3. Install the **axe DevTools** extension for more detailed checks.
4. Try a screen reader for five minutes (NVDA on Windows, VoiceOver on Mac: Cmd+F5). It changes how you build.
