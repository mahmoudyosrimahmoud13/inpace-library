# Project 5: ship the inspector

You'll wrap everything in one function that returns plain data, test it on the photo in nine conditions, and
measure its speed.

The code is above this text. Save it as `p5_ship.py`.

## Read the code

- **`inspect(img, mm_per_px)`** accepts color or gray photos of any size. It resizes to the width the pipeline was
  tuned on (384 pixels), runs the watershed counter, scales the diameters back, and returns a dictionary: the count,
  every diameter, the median, and millimetres when you give a calibration.
- **`variants()`** makes the same photo worse in ways real cameras do: darker, brighter, uneven light, sensor noise,
  out of focus, turned, a higher resolution, heavy JPEG compression.
- With a file name, the script prints `inspect()`'s JSON for that photo: `python p5_ship.py my_photo.png`.

## Run it

```bash
python p5_ship.py
```

The real output:

```text
1. inspect() on the photo:
   {"count": 24, "median_diameter_px": 45.0, "median_diameter_mm": 22.5}

2. Robustness: the same 24 coins in worse conditions
   as is                  count 24 ok   median diameter  45.0 px      21 ms
   darker (-40)           count 24 ok   median diameter  44.8 px      22 ms
   brighter (+40)         count 24 ok   median diameter  45.0 px      21 ms
   uneven light           count 24 ok   median diameter  44.8 px      27 ms
   sensor noise           count 24 ok   median diameter  45.0 px      32 ms
   out of focus           count 24 ok   median diameter  44.5 px      28 ms
   turned 90 degrees      count 24 ok   median diameter  44.5 px      29 ms
   twice the resolution   count 24 ok   median diameter  90.0 px      29 ms
   JPEG quality 20        count 24 ok   median diameter  45.0 px      27 ms

   9 of 9 conditions give the right count. Make it harder (the exercises) until something breaks: that's your next test, found before a user finds it.
```

What it shows:

- **All nine conditions give 24**, in about 20 ms each.
- **Diameters stay stable** (44.5 to 45 pixels) except at twice the resolution, where they double, as they should.
  Pixels aren't millimetres: a real product needs a calibration (a ruler or a known coin in the frame).
- Passing all your tests means your tests are too easy. Make them harder until something breaks.

## Looking back

You built a vision product the way it's usually built: classic image processing first (it's fast, explainable and
often enough), deep learning where it adds something (the CNN beat the brightness rule), segmentation to fix what
contours couldn't, a detector graded with the standard metrics, and robustness tests before shipping.

## Make it yours

1. Add harder conditions: a 30-degree rotation, half the resolution, a shadow across half the photo, coins on a
   bright background (invert the image). Which breaks first, and why?
2. Serve `inspect()` with FastAPI: `POST /inspect` with an uploaded image, returning the JSON.
3. Take five phone photos of real coins and run them. What would you change before calling it a product?

## What to take away

- Ship a function with plain inputs and outputs.
- Test on worse conditions on purpose, and keep those tests.
- Calibrate before you report real-world units.
