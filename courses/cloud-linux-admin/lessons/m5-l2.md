# Patching fleets with Systems Manager

`dnf update` over SSH on 40 servers doesn't scale and leaves no record. **SSM Patch Manager** does it by policy.

| Piece | Is |
|---|---|
| **Patch baseline** | Which updates are approved: e.g. security and bugfix, auto-approved 7 days after release |
| **Patch group** | Instances chosen by tag (`Patch Group = web-prod`) |
| **Maintenance window** | When patching may run: Sundays 02:00-04:00, 25% of instances at a time |
| **Compliance** | Report of which instances are missing what |

```bash
aws ssm describe-instance-patch-states --instance-ids i-0abc --query 'InstancePatchStates[].[InstanceId,MissingCount,FailedCount,InstalledPendingRebootCount]'
aws ssm list-compliance-summaries
```

Or the simple start: **Quick Setup → Patch Manager** scans daily and installs weekly for all managed instances.

## Two strategies

| Patch in place | Replace with a new image |
|---|---|
| Patch Manager updates running servers | Build a new patched AMI (Day 6), roll it out with an instance refresh |
| Fine for long-lived servers | The cloud-native way for Auto Scaling groups |
| Needs reboots for kernels | No drift: every server is identical |

Either way: **staging first**, then production; and kernel updates need a reboot (or live patching) to take effect: check `needs-restarting -r` (RHEL family) or `/var/run/reboot-required` (Ubuntu).
