# EBS in practice: attach, grow, snapshot

## Add a data disk

```bash
aws ec2 create-volume --availability-zone eu-central-1a --size 20 --volume-type gp3 --encrypted
aws ec2 attach-volume --volume-id vol-0abc --instance-id i-0123 --device /dev/sdf
```

On the instance (Nitro instances show EBS as NVMe devices, so names differ from what you asked for):

```bash
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,SERIAL     # SERIAL shows the vol- ID
sudo mkfs.xfs /dev/nvme1n1
sudo mkdir -p /data
echo "UUID=$(sudo blkid -s UUID -o value /dev/nvme1n1) /data xfs defaults,nofail 0 2" | sudo tee -a /etc/fstab
sudo mount -a && df -h /data
```

Use the **UUID** and **nofail** in fstab: device names can change between boots, and `nofail` stops a missing disk from blocking boot.

## Grow a disk without downtime

```bash
aws ec2 modify-volume --volume-id vol-0abc --size 40       # can't shrink, only grow
# on the instance:
sudo growpart /dev/nvme0n1 1          # grow the partition (root disks have one)
sudo xfs_growfs -d /                  # XFS
# or: sudo resize2fs /dev/nvme0n1p1   # ext4
```

## Snapshots you can trust

- Snapshots are **crash-consistent**: like pulling the power. Fine for most file systems; for databases, use the database's own backup or freeze writes (`fsfreeze`) first.
- Automate with **Data Lifecycle Manager** (by tag, keep N) or **AWS Backup** (Day 4).
- A backup you never restored is a hope, not a backup: create a volume from a snapshot and mount it once a month.
