# Rolling out changes with instance refresh

With golden AMIs, updating servers means **replacing** them:

1. Create a new **launch template version** pointing at the new AMI.
2. Start an **instance refresh** on the Auto Scaling group.

```bash
aws ec2 create-launch-template-version --launch-template-name shop --source-version '$Latest' \
  --launch-template-data '{"ImageId":"ami-0new..."}'
aws autoscaling start-instance-refresh --auto-scaling-group-name shop-asg \
  --preferences '{"MinHealthyPercentage":90,"InstanceWarmup":120,"CheckpointPercentages":[25,100],"AutoRollback":true}'
aws autoscaling describe-instance-refreshes --auto-scaling-group-name shop-asg
```

| Setting | Does |
|---|---|
| MinHealthyPercentage | Never let healthy capacity drop below this during the roll |
| InstanceWarmup | Time a new instance gets before counting as healthy |
| Checkpoints | Pause at 25% so you can watch metrics |
| AutoRollback | Go back to the previous version if the refresh fails |

## Make replacement safe

- **Connection draining** (deregistration delay) on the target group lets in-flight requests finish.
- **Lifecycle hooks** run a script before termination (flush logs, leave a cluster).
- The app must be **stateless** and start fast, or refreshes are slow and risky.

This is the same idea as a Kubernetes rolling update, at the VM level, and the deployment strategies course (DevOps & CI/CD) builds on it.
