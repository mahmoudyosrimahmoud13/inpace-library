## الاختبار: فكّر كمختبِر

حين يُطلب منك اختبار شيء ("اختبر قلمًا"، "اختبر هذه الدالة")، اعمل بترتيب:

1. من يستخدمه، ولماذا؟ (قلم للأطفال يُختبر بشكل مختلف عن قلم لروّاد الفضاء.)
2. الحالات العادية.
3. الحالات الحدّية: فارغ، عنصر واحد، كبير جدًا، سالب، مكرر، نوع خاطئ.
4. الفشل: ماذا يحدث مع مدخل سيئ، أو حين يفشل شيء يعتمد عليه؟

ولكودك في المقابلة، تجد القائمة نفسها أغلب الأخطاء. و`assert` في Python تصنع اختبارات سريعة:

```python
def second_largest(nums):
    """The second-largest distinct value, or None."""
    distinct = sorted(set(nums))
    return distinct[-2] if len(distinct) >= 2 else None

tests = [([3, 1, 4, 1, 5], 4), ([5, 5, 5], None), ([], None), ([7], None), ([-2, -9], -9), ([2, 2, 1], 1)]
for nums, expected in tests:
    assert second_largest(nums) == expected, (nums, second_largest(nums))
print(f"all {len(tests)} tests pass")
```

```output
all 6 tests pass
```

## قواعد البيانات: SQL يجب أن تستطيع كتابته

اعرف `SELECT` و`WHERE` و`JOIN` (inner وleft) و`GROUP BY` مع `COUNT` و`SUM`، و`HAVING`. تأتي Python بـ SQLite، فتستطيع
التدرب بلا تثبيت أي شيء:

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE students (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE enrollments (student_id INTEGER, course TEXT);
INSERT INTO students VALUES (1, 'Mona'), (2, 'Omar'), (3, 'Sara');
INSERT INTO enrollments VALUES (1, 'Math'), (1, 'Physics'), (2, 'Math');
""")
query = """
SELECT s.name, COUNT(e.course) AS courses
FROM students s LEFT JOIN enrollments e ON e.student_id = s.id
GROUP BY s.id
ORDER BY courses DESC, s.name
"""
for row in db.execute(query):
    print(row)
```

```output
('Mona', 2)
('Omar', 1)
('Sara', 0)
```

الـ `LEFT JOIN` يُبقي Sara، التي ليس لها تسجيلات؛ والـ `JOIN` العادي (inner) كان سيُسقطها. واعرف أيضًا معنى
**normalization** (كل معلومة تُخزَّن مرة واحدة، في جدولها)، ولماذا قد تفعل **denormalization** أحيانًا (نسخ البيانات
لتسريع القراءة، على حساب إبقاء النسخ متطابقة). والـ **index** يجعل البحث في عمود سريعًا، على حساب كتابة أبطأ.

## الـ threads والـ locks: الـ race condition

الـ threads تتشارك الذاكرة. وحين يغيّر اثنان منها القيمة نفسها في الوقت نفسه، قد تضيع تحديثات. والـ **lock** يسمح لـ thread
واحدة فقط بدخول الجزء الحرج في كل مرة.

يضيع التحديث لأن `count += 1` هي في الحقيقة ثلاث خطوات: قراءة، إضافة، كتابة. هذه هي المشكلة، مع الخطوات الثلاث مكتوبة
صراحةً، والـ threads مجبرة على التبادل في أسوأ لحظة:

```python
import threading

count = 0
both_have_read = threading.Barrier(2)

def unsafe_add():
    global count
    value = count              # 1. read
    both_have_read.wait()      # both threads have read before either writes: the worst timing
    count = value + 1          # 2. add and 3. write

threads = [threading.Thread(target=unsafe_add) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print("two increments without a lock:", count)

count = 0
lock = threading.Lock()

def safe_add():
    global count
    with lock:                 # only one thread at a time runs this block
        value = count
        count = value + 1

threads = [threading.Thread(target=safe_add) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print("two increments with a lock:   ", count)
```

```output
two increments without a lock: 1
two increments with a lock:    2
```

بدون الـ lock، تقرأ الـ thread الأولى والثانية 0 وتكتب كلتاهما 1: يضيع تحديث. وفي البرامج الحقيقية يكون التوقيت السيئ
نادرًا، وهذا ما يجعل هذه الأخطاء صعبة الاكتشاف. واعرف أيضًا الـ **deadlock**: thread تمسك lock تحتاجها الأخرى، والعكس،
فتنتظران إلى الأبد. وأخذ الـ locks دائمًا بالترتيب نفسه يمنعه.
