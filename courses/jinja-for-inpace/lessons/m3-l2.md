# Translation with the i18n extension

The `jinja2.ext.i18n` extension adds `{% trans %}` and `_()`. inPace plugs in its own `gettext`:

```python
env.install_gettext_callables(gettext, lambda s, p, n: gettext(s if n == 1 else p), newstyle=False)
env.globals["_"] = gettext
```

In templates:

```jinja
<h1>{% trans trimmed %}Tempo's island{% endtrans %}</h1>
<button aria-label="{{ _('Switch light or dark mode') }}">...</button>
{% trans count=n %}One plant{% pluralize %}{{ count }} plants{% endtrans %}
```

- `trimmed` collapses whitespace and line breaks, so a long sentence over several lines still matches one key.
- inPace's `gettext` looks the English text up in `locales/ar.json`, and also tries **patterns** for sentences with
  values in them (`"{n} days"`), translating the inner parts too. Missing text falls back to English.

## A design question to think about

The current language is kept in a module-level dict, `CURRENT["lang"]`, set at the start of `page()`. That's fine
for a one-person local app where requests don't overlap in a harmful way, but on a busy multi-user server two
requests in different languages could clash. The production answer is a **context variable**
(`contextvars.ContextVar`) or passing the language into the render call. Expect this exact kind of question:
"what would break if this ran for many users?"
