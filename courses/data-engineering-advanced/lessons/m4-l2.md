# dbt project structure and dimensional modeling

## Layers

```
models/
  staging/       stg_*   one-to-one with sources: rename, cast, light cleaning
  intermediate/  int_*   joins and business logic building blocks
  marts/         fct_*, dim_*   what analysts and dashboards query
```

- Only **staging** models read from `source()`. Everything else uses `ref()`.
- Staging models are views. Marts are tables, or incremental for big facts.

## Kimball dimensional modeling

| Table | Holds | Example |
|---|---|---|
| **Fact** | Events or measurements, many rows, numeric measures | `fct_trips` (fare, distance, duration) |
| **Dimension** | Descriptive context, fewer rows | `dim_zones`, `dim_vendors`, `dim_date` |

The **star schema** has facts in the middle, joined to dimensions by keys. It gives simple SQL for BI tools and fast aggregations.

## Grain

**Define the grain first**: "one row per trip". Mixing grains (trips and daily totals in one table) causes double counting.

## Incremental facts

```sql
{{ config(materialized='incremental', unique_key='trip_id') }}
select ... from {{ ref('int_trips_unioned') }}
{% if is_incremental() %}
where pickup_at > (select max(pickup_at) from {{ this }})
{% endif %}
```

> **Key idea:** staging cleans, marts model. Facts hold the measures at a declared grain, and dimensions describe them.
