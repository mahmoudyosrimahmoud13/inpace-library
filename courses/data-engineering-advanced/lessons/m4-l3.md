# dbt seeds, macros, tests and deployment

## Seeds

Small static CSVs in `seeds/` (for example `taxi_zone_lookup.csv`) loaded with `dbt seed`. Use them for lookup tables that rarely change, not for real data.

## Macros (Jinja)

Reusable SQL logic:

```sql
{% macro get_payment_type_description(col) %}
  case {{ col }}
    when 1 then 'Credit card'
    when 2 then 'Cash'
    else 'Unknown'
  end
{% endmacro %}
```

Packages like `dbt_utils` add common macros (`generate_surrogate_key`, `date_spine`).

## Tests

```yaml
models:
  - name: fct_trips
    columns:
      - name: trip_id
        tests: [unique, not_null]
      - name: pickup_zone_id
        tests:
          - relationships: {to: ref('dim_zones'), field: zone_id}
      - name: payment_type
        tests:
          - accepted_values: {values: [1, 2, 3, 4, 5, 6]}
```

Also use **singular tests** (SQL that returns failing rows) and **source freshness** checks.

## Docs

`dbt docs generate` builds a site with descriptions and the lineage graph.

## Deployment

- **Environments**: dev schema per developer, prod schema for the scheduled job.
- `dbt build` = run + test + seed + snapshot, in DAG order.
- **CI**: on every pull request, build only changed models and their children (`state:modified+`) in a temporary schema.
- Orchestrate prod runs from Kestra or Airflow after ingestion finishes.

> **Key idea:** tests and docs live next to the models, and CI runs them on every change.
