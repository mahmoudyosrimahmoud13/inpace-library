# Stream processing fundamentals

## Batch vs streaming

| | Batch | Streaming |
|---|---|---|
| Data | Bounded (yesterday's files) | Unbounded (events keep coming) |
| Latency | Minutes to hours | Seconds or less |
| Complexity | Lower | Higher: state, ordering, late data |

Use streaming only when the business really needs low latency (fraud, alerts, live dashboards). Many "real-time" needs are fine with micro-batches every 5 minutes.

## Time

- **Event time**: when it happened (on the device).
- **Processing time**: when your system saw it.
They differ because of network delays and offline devices. **Always aggregate on event time.**

## Windows

| Window | Example |
|---|---|
| Tumbling | Fixed and non-overlapping: count per 1 minute |
| Hopping/Sliding | Overlapping: last 5 minutes, updated every minute |
| Session | Activity separated by a gap of inactivity |

## Late data and watermarks

A **watermark** says "I don't expect events older than X anymore". Events later than the watermark are dropped or sent to a side output. It's a trade-off between completeness and latency.

## Delivery guarantees

| Guarantee | Meaning |
|---|---|
| At most once | Can lose events |
| At least once | Can duplicate events, so consumers must be idempotent |
| Exactly once | Needs transactions and idempotent sinks end to end |

> **Key idea:** streaming is about time. Aggregate on event time, handle late data with watermarks, and design for duplicates.
