# Ingestion: from an API to a database

## Extract patterns

| Source | Pattern |
|---|---|
| REST API | Paginate, respect rate limits, retry on 429 and 5xx |
| Files (CSV, Parquet) | Download, validate, store the raw copy |
| Database | Incremental query on `updated_at`, or CDC from the WAL or binlog |

## Full vs incremental loads

- **Full**: reload everything every run. Simple, but slow and costly as data grows.
- **Incremental**: load only what's new since the last **watermark** (max `updated_at` or id). Store the watermark (in a KV store or state table). Handle late updates with a small overlap window plus a merge.

## Staging then merge

```
source -> staging table (truncate + load this run) -> MERGE into final table
```

Staging keeps each run isolated, makes it easy to validate before publishing, and gives idempotent merges.

## Schema and data quality at the door

- Fix data types explicitly; don't let pandas guess (`tpep_pickup_datetime` as a timestamp, IDs as integers).
- Normalize nested JSON into tables, or keep the raw JSON plus parsed columns.
- Add load metadata: `_loaded_at`, `_source_file`, `_run_id`.
- Fail fast on broken contracts (missing columns, null keys).

## Tools

dlt (used in the Zoomcamp workshop), Airbyte, Fivetran, or custom Python. Choose a tool for common SaaS sources, and write code for odd internal APIs.

> **Key idea:** load incrementally into staging, validate, then merge idempotently.
