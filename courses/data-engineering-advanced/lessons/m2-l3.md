# Scheduling, backfills and idempotency

## Backfills

You deploy a monthly pipeline in November, but you need January to October too. A **backfill** runs the flow once per past schedule date, each with its own `trigger.date`. This only works if the flow uses the **logical date**, not "now".

## Idempotency: the most important rule

**Running the same run twice must give the same result.** Retries and backfills re-run things all the time.

| Not idempotent | Idempotent |
|---|---|
| `INSERT INTO trips SELECT * FROM staging` | `DELETE` that month, then insert, in one transaction |
| Append a file to `latest.csv` | Write to `trips/2026-10.parquet` (overwrite) |
| Counter `+= 1` | Recompute the value from the source |

Common patterns:
- **Delete and insert** by partition or date.
- **MERGE / upsert** on a unique key:

```sql
MERGE INTO trips t
USING staging s ON t.unique_row_id = s.unique_row_id
WHEN NOT MATCHED THEN INSERT (...) VALUES (...);
```

- Build a **deterministic row ID** (for example a hash of the key columns) so duplicates are detectable.

## Scheduling tips

- Schedule **after** the source is ready, and add a sensor or check rather than guessing.
- Limit concurrency on backfills so you don't overload the source API or database.
- Set retries with backoff for network steps, **not** for steps that fail on bad data.

> **Key idea:** design every task to be safely re-runnable for a given date. Then retries and backfills are free.
