# Terraform primer: infrastructure as code

## Why infrastructure as code

Clicking through a cloud console doesn't scale and can't be reviewed. With **Terraform** you describe buckets, datasets and clusters in files, keep them in git, review changes, and recreate everything with one command.

## The workflow

| Command | What it does |
|---|---|
| `terraform init` | Downloads providers (GCP, AWS) |
| `terraform plan` | Shows what **would** change |
| `terraform apply` | Makes the changes |
| `terraform destroy` | Removes everything this config created |

## Key concepts

- **Provider**: plugin for a platform (`google`, `aws`).
- **Resource**: one thing to create (`google_storage_bucket`).
- **Variable**: input you can change per environment.
- **State** (`terraform.tfstate`): Terraform's record of what exists. **Never edit it by hand, and never commit it with secrets.** Teams store it remotely (a GCS or S3 backend) with locking.

## The video's example, simplified

```hcl
provider "google" {
  project = var.project
  region  = var.region
}

resource "google_storage_bucket" "data_lake" {
  name          = "${var.project}-data-lake"
  location      = var.region
  force_destroy = true
  lifecycle_rule {
    condition { age = 30 }
    action    { type = "Delete" }
  }
}

resource "google_bigquery_dataset" "dw" {
  dataset_id = "trips_data_all"
  location   = var.region
}
```

## Credentials

- Use a **service account** with the minimum roles needed.
- Point Terraform at it with `GOOGLE_APPLICATION_CREDENTIALS`. Keep the key file **out of git**.

> **Key idea:** `plan` before every `apply`, keep state remote, and treat infrastructure changes like code reviews.
