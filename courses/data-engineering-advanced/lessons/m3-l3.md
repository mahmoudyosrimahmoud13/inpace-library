# BigQuery internals: partitioning, clustering and cost

## How BigQuery stores and bills

- **Columnar storage** (Capacitor): a query reads only the columns it names.
- **On-demand pricing**: you pay for **bytes scanned**. `SELECT *` on a wide table is expensive. `LIMIT` does **not** reduce bytes scanned.
- Compute (Dremel) is separate from storage, and queries run on thousands of workers.

## Partitioning

Splits a table by **date/timestamp, ingestion time, or integer range**.

```sql
CREATE OR REPLACE TABLE trips_partitioned
PARTITION BY DATE(tpep_pickup_datetime) AS
SELECT * FROM trips;
```

A filter on the partition column **prunes** partitions, so far fewer bytes are scanned. Limit: 4,000 partitions per table, so don't partition by a high-cardinality key.

## Clustering

Sorts data **within** each partition by up to 4 columns.

```sql
CREATE OR REPLACE TABLE trips_pc
PARTITION BY DATE(tpep_pickup_datetime)
CLUSTER BY VendorID, PULocationID AS
SELECT * FROM trips;
```

- Helps filters and aggregations on those columns.
- BigQuery re-clusters automatically, at no cost.

| Use partitioning when | Use clustering when |
|---|---|
| You filter by date most of the time | You filter on high-cardinality columns |
| You need partition-level deletes or expiry | Partitions would be tiny (under about 1 GB) |
| You want an exact cost estimate before running | Many column combinations are filtered |

## Best practices

- Select only the columns you need. Preview tables instead of `SELECT * LIMIT`.
- Always filter on the partition column. You can enforce this with `require_partition_filter`.
- Put the **largest table first** in joins, and denormalize with nested/repeated fields where it makes sense.
- Check bytes in the dry-run estimate before running big queries.

> **Key idea:** in BigQuery, cost = bytes scanned. Partition by date, cluster by common filters, and never `SELECT *` on big tables.
