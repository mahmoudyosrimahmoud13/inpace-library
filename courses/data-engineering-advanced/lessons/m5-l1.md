## When you need Spark

When data doesn't fit on one machine, or a SQL warehouse isn't the right place (complex Python logic, ML features, huge file transformations). If a warehouse SQL query can do it, that's usually simpler.

## Architecture

| Part | Role |
|---|---|
| Driver | Your program: builds the plan, schedules tasks |
| Executors | Worker processes that run tasks on data partitions |
| Cluster manager | YARN, Kubernetes, standalone, or managed (Dataproc, Databricks) |

## Lazy evaluation

- **Transformations** (`select`, `filter`, `join`, `groupBy`) only build a plan.
- **Actions** (`count`, `show`, `write`) trigger execution.
- The **Catalyst optimizer** rewrites the plan, for example pushing filters down into Parquet reads.

```python
df = spark.read.parquet("gs://lake/raw/taxi/yellow/2026/*")
daily = (df.filter(df.trip_distance > 0)
           .groupBy(F.to_date("tpep_pickup_datetime").alias("day"))
           .agg(F.sum("total_amount").alias("revenue")))
daily.write.mode("overwrite").partitionBy("day").parquet("gs://lake/marts/daily_revenue")
```

## Partitions

- Data is split into **partitions**, and one task processes one partition.
- Too few means idle cores. Too many tiny ones means scheduling overhead and small files.
- `repartition(n)` does a full shuffle. `coalesce(n)` only reduces partitions, without a full shuffle.

> **Key idea:** Spark builds a lazy plan and runs it in parallel over partitions. Keep data columnar and filter early.
