# Spark internals: shuffles, joins and skew

## The shuffle

`groupBy`, `join`, `distinct` and `repartition` need rows with the same key on the same executor, so data is **written to disk and sent over the network**. Shuffles are the main cost in most Spark jobs.

A `groupBy` runs in two stages:
1. **Partial aggregation** in each partition (like a combiner).
2. **Shuffle** by key, then the final aggregation.

## Join strategies

| Strategy | When | Cost |
|---|---|---|
| **Broadcast hash join** | One side is small (under about 10 MB by default, adjustable) | No shuffle of the big side |
| Sort-merge join | Both sides large | Both sides shuffled and sorted |

```python
from pyspark.sql.functions import broadcast
trips.join(broadcast(zones), trips.PULocationID == zones.LocationID)
```

## Data skew

One key (for example a single huge customer) gets most rows, so one task runs for an hour while the others finish in seconds. Fixes:
- **Adaptive Query Execution** (`spark.sql.adaptive.enabled=true`) splits skewed partitions automatically.
- **Salting**: add a random suffix to the hot key, aggregate, then aggregate again.
- Broadcast the small side to avoid the shuffle entirely.

## Reading the Spark UI

- **Stages** are split at shuffles. Look at the shuffle read/write size.
- **Task time distribution**: a max far above the median means skew.
- **Spill** (memory or disk): partitions are too big, so increase the partition count.

> **Key idea:** minimize shuffles, broadcast small tables, and watch for skew in the Spark UI.
