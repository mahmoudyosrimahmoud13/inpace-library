## Testing: think like a tester

Asked to test something ("test a pen", "test this function"), work in an order:

1. Who uses it, and for what? (A pen for children is tested differently from a pen for astronauts.)
2. The normal cases.
3. The edge cases: empty, one item, very large, negative, duplicates, wrong types.
4. Failure: what happens with bad input, or when something it depends on fails?

For your own interview code, the same list finds most bugs. Python's `assert` makes quick tests:

```python
def second_largest(nums):
    """The second-largest distinct value, or None."""
    distinct = sorted(set(nums))
    return distinct[-2] if len(distinct) >= 2 else None

tests = [([3, 1, 4, 1, 5], 4), ([5, 5, 5], None), ([], None), ([7], None), ([-2, -9], -9), ([2, 2, 1], 1)]
for nums, expected in tests:
    assert second_largest(nums) == expected, (nums, second_largest(nums))
print(f"all {len(tests)} tests pass")
```

```output
all 6 tests pass
```

## Databases: SQL you should be able to write

Know `SELECT`, `WHERE`, `JOIN` (inner and left), `GROUP BY` with `COUNT` and `SUM`, and `HAVING`. Python includes
SQLite, so you can practise without installing anything:

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE students (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE enrollments (student_id INTEGER, course TEXT);
INSERT INTO students VALUES (1, 'Mona'), (2, 'Omar'), (3, 'Sara');
INSERT INTO enrollments VALUES (1, 'Math'), (1, 'Physics'), (2, 'Math');
""")
query = """
SELECT s.name, COUNT(e.course) AS courses
FROM students s LEFT JOIN enrollments e ON e.student_id = s.id
GROUP BY s.id
ORDER BY courses DESC, s.name
"""
for row in db.execute(query):
    print(row)
```

```output
('Mona', 2)
('Omar', 1)
('Sara', 0)
```

The `LEFT JOIN` keeps Sara, who has no enrollments; an inner `JOIN` would drop her. Also know what **normalization**
means (each fact stored once, in its own table), and why you'd sometimes **denormalize** (copying data to make reads
faster, at the cost of keeping copies in step). An **index** makes lookups on a column fast, at the cost of slower writes.

## Threads and locks: the race condition

Threads share memory. When two threads change the same value at the same time, updates can be lost. A **lock** lets
only one thread into a critical section at a time.

The lost update happens because `count += 1` is really three steps: read, add, write. Here is that problem, with the
three steps spelled out and the threads forced to switch at the worst moment:

```python
import threading

count = 0
both_have_read = threading.Barrier(2)

def unsafe_add():
    global count
    value = count              # 1. read
    both_have_read.wait()      # both threads have read before either writes: the worst timing
    count = value + 1          # 2. add and 3. write

threads = [threading.Thread(target=unsafe_add) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print("two increments without a lock:", count)

count = 0
lock = threading.Lock()

def safe_add():
    global count
    with lock:                 # only one thread at a time runs this block
        value = count
        count = value + 1

threads = [threading.Thread(target=safe_add) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print("two increments with a lock:   ", count)
```

```output
two increments without a lock: 1
two increments with a lock:    2
```

Without the lock, both threads read 0 and both write 1: one increment is lost. In real programs the bad timing is rare,
which makes these bugs hard to find. Also know **deadlock**: two threads each hold a lock the other needs, and both wait
forever. Taking locks always in the same order prevents it.
