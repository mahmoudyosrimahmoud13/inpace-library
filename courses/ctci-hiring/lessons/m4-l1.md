# Read: technical questions (Part VII)

Read **Part VII** today. It's the most important part of the book for coding interviews: it tells you how to prepare,
what you need to know, and how to work through a problem you've never seen.

## Sections to read closely

- *How to prepare* and *What you need to know*: the core list of data structures and algorithms. Mark anything you
  can't implement from memory; days 5 and 6 cover them.
- *Walking through a problem*: the step-by-step flow for one interview question. The next lesson practises it.
- The five **Optimize & Solve** techniques, and *Best conceivable runtime (BCR)*. These are tools for when your first
  solution is too slow:

| Technique | Ask yourself |
|---|---|
| #1 Look for BUD | Where are the **B**ottlenecks, the **U**nnecessary work, the **D**uplicated work? |
| #2 DIY (Do it yourself) | How would I solve a big, real example by hand, without a computer? |
| #3 Simplify and generalize | Can I solve an easier version first, then extend it? |
| #4 Base case and build | Can I solve it for n = 1, then build each bigger case from the smaller one? |
| #5 Data structure brainstorm | Would a hash map, a heap, a stack or a tree make this easy? |
| BCR | What's the fastest any solution could possibly be? (For example, you must look at every item at least once.) |

## Sections to read once

- *Handling incorrect answers* and *Don't give up!*: interviews are about how you handle difficulty.
- *When you've heard a question before*: say so. Pretending is easy to spot and looks dishonest.
- *The 'perfect' language for interviews*: use the language you know best, as long as the interviewer accepts it.
- *What good coding looks like*: note what the book asks for. In short, interviewers want code that works, is
  reasonably fast, and is easy to read: clear names and small helper functions count.

## After reading

Close the book and write the Optimize & Solve techniques from memory, with one sentence each. Keep that page next to you
while you practise this week.

## What to take away

- Part VII gives a step-by-step flow for any technical question, and five techniques for optimizing.
- BCR tells you when to stop optimizing: you can't beat the best conceivable runtime.
- Good interview code is correct, clear and well organized, not clever.
