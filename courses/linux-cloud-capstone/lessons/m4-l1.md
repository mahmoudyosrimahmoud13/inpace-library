# Observability and SLOs

Apply the Observability and SRE course to your project.

## Telemetry

| Signal | Implementation |
|---|---|
| Host metrics | node_exporter or CloudWatch agent: CPU, memory, disk, network |
| App metrics | request counter and latency histogram by route and status |
| Logs | JSON with `service`, `version`, `env`, `trace_id`, shipped to Loki or CloudWatch Logs, retention set |
| Traces | OpenTelemetry auto-instrumentation plus one custom span, sampled, errors always kept |
| Deploy events | Annotations on dashboards from the pipeline |

## SLOs (write them in `docs/slo.md`)

```text
Journey: create and open a short link
SLI 1 availability: share of requests to / and /api/links without 5xx, measured at the ALB
SLI 2 latency:      share of those requests served in under 300 ms
SLOs: 99.5% and 99% over 28 days
Error budget policy: <25% left -> only small changes with canary; exhausted -> freeze features, reliability work
```

## Alerts

- Page: fast and slow burn-rate alerts on both SLOs, each with a runbook link.
- Ticket: disk predicted full, certificate expiry under 14 days, backup missing, error budget under 25%, drift detected.

## Dashboard

As code in the repo: SLO status and budget, RED by route, deploy annotations, hosts, database (connections, slow queries), ALB (5xx, target response time).

## Done means

You can answer, from the dashboard alone and within one minute: "Are users OK right now? Did the last deploy change anything? How much error budget is left?"
