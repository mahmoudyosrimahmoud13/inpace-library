# Design document and decisions

Real teams write a short design before building. Yours goes in the repo as `docs/design.md`.

## Sections

1. **Goal and users**: what the service does, who uses it, the main user journey.
2. **Requirements**:
   - Functional: the 3-5 things it must do.
   - Non-functional: SLO targets (e.g. 99.5% availability, p95 under 300 ms), RPO/RTO, cost limit per month, security rules.
3. **Architecture diagram** (Mermaid in Markdown is fine) and a short walk through one request.
4. **Decisions** with alternatives (ADRs, below).
5. **Risks** and what you'll do about each.

## Architecture Decision Records

One short file per important choice:

```markdown
# ADR 003: Run the app on EC2 Auto Scaling, not Kubernetes

## Context
One small service, a team of one, limited budget, track focuses on Linux servers.

## Decision
EC2 Auto Scaling group with golden AMIs built by Packer + Ansible, behind an ALB.

## Alternatives considered
- EKS: more to learn and run, higher fixed cost (control plane).
- ECS Fargate: simpler, but hides the Linux layer this project should show.

## Consequences
We own patching (Patch Manager / new AMIs); scaling is per instance; rolling deploys via instance refresh.
```

## Decisions you must record

- Compute (EC2 ASG, ECS, or Kubernetes).
- How servers get configured (baked AMI or Ansible on boot).
- Admin access (Session Manager, no SSH port).
- Secrets (Secrets Manager / Parameter Store).
- Deploy strategy and rollback.
- Telemetry stack (Prometheus/Grafana/Loki or CloudWatch).

Good engineers are judged by their reasoning as much as their results. The "alternatives" and "consequences" sections are what interviewers ask about.
