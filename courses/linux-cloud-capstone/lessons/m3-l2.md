# Infrastructure pipeline and drift

The `infra` repo gets its own workflow, separate from the app.

```yaml
on:
  pull_request: {paths: ["infra/**"]}
  push: {branches: [main], paths: ["infra/**"]}
  schedule: [{cron: "0 6 * * *"}]      # daily drift check
```

| Event | Jobs |
|---|---|
| Pull request | fmt, validate, tflint, Checkov/Trivy config scan, plan for each environment posted as a PR comment |
| Push to main | apply staging; then apply prod after environment approval |
| Schedule | plan prod with `-detailed-exitcode`; exit code 2 means drift: open an issue or notify |

```bash
terraform plan -detailed-exitcode -input=false -lock=false
# 0 = no changes, 1 = error, 2 = changes present (drift)
```

## Ownership boundaries

| Changed by | What |
|---|---|
| Infra pipeline | VPC, security groups, ALB, ASG settings, RDS, IAM |
| App pipeline | Which image digest runs (launch template version or parameter), migrations |
| Nobody by hand | Anything in prod. Console access is read-only, with a break-glass role for emergencies, logged in CloudTrail |

Use `ignore_changes` in Terraform for the attributes the app pipeline owns (e.g. the launch template version the ASG uses, or desired capacity), so the two pipelines don't fight.

## Done means

You can show three PRs: an app change, an infra change, and a deliberate drift caught by the schedule.
