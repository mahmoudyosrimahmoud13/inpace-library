# The application pipeline

The `app` repo's pipeline, following the DevOps & CI/CD course.

## Stages

| Stage | Contains | Gate |
|---|---|---|
| PR checks | lint, unit tests, integration tests against PostgreSQL in a service container | Required to merge |
| Security | secret scan, dependency scan, SAST, image scan | Fails on fixable critical/high |
| Package | build once, tag by commit SHA, push to ECR or GHCR, SBOM | Only on main |
| Staging | deploy the digest (new launch template version + instance refresh, or your platform's equivalent), run migrations first, smoke test | Automatic |
| Production | same digest, environment approval, rolling with checkpoints, smoke test, notify | Required reviewer |

## Deploying to EC2 from CI

One clear option for this project:

1. The AMI contains the runtime; the app ships as a **container image**.
2. A launch template version sets user data (or an SSM parameter `/app/prod/image`) to the new digest.
3. An instance refresh replaces instances; each pulls and runs that digest at boot.
4. Rollback = point back to the previous digest and refresh again (write a script: `./rollback.sh prod`).

(If you chose ECS or Kubernetes in your ADR, use that platform's rolling update or GitOps instead.)

## Must-haves

- **OIDC** roles per environment, trust policies limited to repo and environment.
- Actions **pinned by SHA**, top-level `permissions: contents: read`.
- `concurrency` so two prod deploys never overlap.
- Migrations follow **expand and contract**.

## Done means

A PR merged to main reaches production in under 30 minutes with one approval click, and a rollback takes one command and under 10 minutes.
