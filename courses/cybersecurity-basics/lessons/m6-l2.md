# Logs, detection and incident response

Prevention fails sometimes. What decides the damage is **how fast you notice** and **how well you respond**.

## What to log

Log security-relevant events, with time, user, IP address and result:
- Logins: successes, failures, MFA prompts, password resets.
- Permission denied errors (often the first sign of someone probing).
- Admin actions: new users, role changes, configuration changes.
- Unusual volumes: many requests from one IP, many failed logins.

Never log **passwords, session tokens, full card numbers or secret keys**. Logs get copied to many places.

Keep logs **somewhere the attacker can't easily delete them** (a separate log server or service), with synchronized clocks.

## Reading logs on Linux

```bash
# failed SSH logins
sudo journalctl -u ssh --since "1 hour ago" | grep "Failed password"

# which IPs failed most
sudo journalctl -u ssh --since today | grep "Failed password" \
  | grep -oE "from [0-9.]+" | sort | uniq -c | sort -rn | head

# web server: who requested the most
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
```

What you'd see during a brute-force attempt:

```
Failed password for invalid user admin from 203.0.113.7 port 51234 ssh2
Failed password for invalid user oracle from 203.0.113.7 port 51240 ssh2
Failed password for root from 203.0.113.7 port 51251 ssh2
```

**fail2ban** watches these logs and blocks IPs automatically:

```bash
sudo apt install fail2ban
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd
```

## Detection at scale

Companies send logs from every system into a **SIEM** (Security Information and Event Management; for example Wazuh, which is free, Splunk or Microsoft Sentinel) and write **rules** that raise alerts: "10 failed logins then a success from a new country", "an admin account created at 3 a.m.". A **SOC** (security operations centre) team watches those alerts. SOC analyst is the most common entry-level security job.

## Incident response

When something goes wrong, follow a plan (the NIST lifecycle):

1. **Preparation**: contacts, backups, logging and this plan, ready **before** anything happens.
2. **Detection and analysis**: is it real? What's affected? Since when?
3. **Containment**: stop it spreading: disconnect the machine, disable the account, block the IP. Don't wipe evidence yet.
4. **Eradication**: remove the cause: malware, the attacker's accounts, the vulnerability.
5. **Recovery**: restore from clean backups, reset credentials, watch closely.
6. **Lessons learned**: a blameless review: what happened, what helped, what to change.

### If your own account is hacked

1. From a **clean** device, change the password and sign out all sessions.
2. Turn on MFA (or re-register it) and check recovery email and phone number.
3. Check for rules or apps the attacker added: email forwarding rules, connected apps, new SSH keys.
4. Warn your contacts if messages were sent in your name.
5. Change the same password anywhere you reused it (and stop reusing it).

## Write things down

During an incident, keep a timeline: what you saw, when, and what you did. It helps the investigation, the report, and next time's plan.
