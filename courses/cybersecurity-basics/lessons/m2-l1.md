# Passwords, MFA and passkeys

## What makes a password strong

Length beats complexity. `correct-horse-battery-staple` is far stronger than `P@ssw0rd1`, and easier to remember. What matters:

- **Long**: at least 12 to 15 characters; passphrases of 4 to 5 random words are great.
- **Unique**: never reused. Reuse is what credential stuffing exploits.
- **Not guessable**: no names, birthdays, football teams or keyboard patterns.

You can't remember dozens of unique passwords, and you shouldn't try. Use a **password manager** (Bitwarden is free and open source; KeePassXC works offline). Remember one strong master passphrase; it generates and fills the rest.

Check if your email was in a known leak at **haveibeenpwned.com**.

## Multi-factor authentication (MFA)

MFA asks for something **in addition** to the password, so a stolen password alone isn't enough.

| Factor | Strength | Notes |
|---|---|---|
| SMS code | Weak | SIM-swap attacks and phishing can steal it, but still far better than nothing |
| Authenticator app (TOTP) | Good | Google Authenticator, Aegis, Authy: 6-digit codes that change every 30 seconds |
| Push approval | Good | Beware "MFA fatigue": never approve a login you didn't start |
| Security key / passkey | Best | Can't be phished: it checks the real website address |

Turn MFA on first for: **email** (it resets everything else), **banking and payment apps**, **social media**, **GitHub and cloud accounts**. Save the **recovery codes** somewhere safe and offline.

## Passkeys

A **passkey** replaces the password with a key pair stored on your phone or computer, unlocked by your fingerprint, face or PIN. The website keeps only the **public** key, so a database leak gives attackers nothing useful, and a fake website can't trick your device into signing in. Use them wherever they're offered.

## How websites should store passwords

A site must **never** store your password itself. It stores a **hash**: a one-way fingerprint.

```
"sunshine"  --hash-->  a3f1c9...   (same input always gives the same output)
```

At login, the site hashes what you typed and compares. But plain fast hashes (MD5, SHA-256) are not enough:

- Attackers have huge lists of hashes of common passwords (**rainbow tables**).
- Fast hashes let a graphics card try **billions of guesses per second**.

So developers use:
1. A **salt**: random data added to each password before hashing, stored next to the hash. Same password, different hash for every user; precomputed tables become useless.
2. A **slow password hash**: **Argon2id**, **bcrypt** or **scrypt**, designed to make each guess expensive.

```python
# pip install argon2-cffi
from argon2 import PasswordHasher
ph = PasswordHasher()
stored = ph.hash("correct horse battery staple")   # includes its own salt and settings
ph.verify(stored, "correct horse battery staple")  # True, or raises an error
```

If you ever build a login: use your framework's built-in password hashing, add rate limiting and MFA, and never write your own crypto.

## Account recovery is part of security

"Forgot password" flows are often the weakest link: security questions anyone can look up ("mother's maiden name"), or reset links that never expire. Recovery should be at least as strong as login.
