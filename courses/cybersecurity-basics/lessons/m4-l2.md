# The OWASP Top 10: access control and injection

**OWASP** (the Open Worldwide Application Security Project) publishes the **Top 10**: the most important web application security risks, based on data from real applications. Every web developer and security analyst is expected to know it.

| # | Risk (2021 list) |
|---|---|
| A01 | Broken access control |
| A02 | Cryptographic failures |
| A03 | Injection (including XSS) |
| A04 | Insecure design |
| A05 | Security misconfiguration |
| A06 | Vulnerable and outdated components |
| A07 | Identification and authentication failures |
| A08 | Software and data integrity failures |
| A09 | Security logging and monitoring failures |
| A10 | Server-side request forgery (SSRF) |

(Check owasp.org/Top10 for the newest edition; the themes stay much the same.)

## A01: Broken access control

The number-one risk. The app lets people do or see things they shouldn't.

**IDOR** (insecure direct object reference): the server trusts an id from the request.

```python
# ❌ any logged-in user can read any invoice by changing the number in the address
@app.get("/invoices/{invoice_id}")
def get_invoice(invoice_id: int, user = Depends(current_user)):
    return db.get_invoice(invoice_id)

# ✅ the query itself requires the invoice to belong to this user
@app.get("/invoices/{invoice_id}")
def get_invoice(invoice_id: int, user = Depends(current_user)):
    inv = db.get_invoice(invoice_id, owner_id=user.id)
    if not inv:
        raise HTTPException(404)
    return inv
```

Other forms: admin pages that are only "hidden" (not protected), a `role=admin` field the user can send, actions checked in the browser but not on the server.

**Defence**: deny by default; check permissions **on the server, for every request**, ideally in one shared place; test with two users trying to reach each other's data.

## A03: Injection

Injection happens when **data is mixed into a command** (SQL, a shell command, HTML) and the data is treated as part of the command.

### SQL injection

```python
# ❌ the input becomes part of the SQL
name = request.args["name"]
db.execute(f"SELECT * FROM users WHERE name = '{name}'")
```

If someone sends `x' OR '1'='1`, the query becomes `... WHERE name = 'x' OR '1'='1'`, which matches every user. Worse inputs can read other tables or delete data.

```python
# ✅ a parameterized query: the database receives the SQL and the data separately
db.execute("SELECT * FROM users WHERE name = %s", (name,))
```

With parameters, the input is **always** data, never code, whatever it contains. ORMs (SQLAlchemy, Django) do this for you, as long as you don't build raw SQL strings yourself.

### Command injection

```python
# ❌ filename = "a.txt; rm -rf ~"
os.system(f"convert {filename} out.png")

# ✅ pass a list of arguments, no shell
subprocess.run(["convert", filename, "out.png"], check=True)
```

### The general rule

Never build commands by joining strings with user input. Use the API that keeps code and data separate: parameterized queries, argument lists, templating that escapes by default. Validate input too (allow-lists: "only digits", "only these 3 values"), but separation is the real fix.

## A06: Vulnerable components

Your app is mostly other people's code (npm, pip packages). Keep dependencies updated, remove unused ones, and let tools warn you: **Dependabot** on GitHub, `npm audit`, `pip-audit`.
