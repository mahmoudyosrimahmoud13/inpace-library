# Authentication flaws, SSRF and misconfiguration

## A07: Identification and authentication failures

Common mistakes in login systems:

| Mistake | Fix |
|---|---|
| No limit on login attempts | Rate limiting, temporary lockouts, CAPTCHA after failures |
| Passwords stored badly | Argon2id / bcrypt with salts (Day 2) |
| "Wrong password" vs "No such user" messages | One message: "Email or password is wrong" |
| Reset tokens that are guessable or never expire | Long random tokens, single use, expire in minutes |
| Session ID not changed after login | Issue a new session on login (prevents session fixation) |
| No MFA option | Offer TOTP or passkeys, require them for admins |
| JWTs accepted without checking the signature, or with `alg: none` | Use a maintained library and always verify |

Best advice: **don't build authentication from scratch.** Use your framework's built-in system or a proven service, and spend your effort on authorization checks.

## A10: Server-side request forgery (SSRF)

Some features make the **server** fetch a URL the user gives: "import a picture from this link", webhooks, link previews. An attacker gives an internal address instead:

```
http://localhost:8080/admin
http://169.254.169.254/latest/meta-data/    (cloud metadata: may expose credentials)
http://10.0.0.5:6379/                        (an internal Redis)
```

The server can reach places the attacker can't, and fetches them on the attacker's behalf.

**Defences**:
- Allow-list the domains the feature really needs.
- Block private and local address ranges **after** resolving the name (attackers use DNS tricks).
- Don't follow redirects blindly; don't return raw responses to the user.
- In the cloud, require IMDSv2 (AWS) so metadata needs a special token.

## A05: Security misconfiguration

Often the easiest bugs to find, and to fix:

- **Debug mode in production**: detailed error pages leak code, paths and secrets.
- **Default passwords** on admin panels, databases and routers.
- **Directory listing** turned on; `.git` folder or `.env` file served by the web server.
- Public cloud storage buckets.
- Missing security headers (Day 4).
- Unnecessary services, sample apps and old admin tools left installed.

Defence: a **hardening checklist** for every new server or service, configuration kept in code (Terraform, Ansible, Docker) so it's reviewed and repeatable, and regular scans.

## Secrets management

Keys, passwords and tokens leak constantly through Git.

- Never commit secrets. Keep them in environment variables or a secrets manager (GitHub Actions secrets, AWS Secrets Manager, Vault).
- Commit a `.env.example` with fake values; add `.env` to `.gitignore`.
- Turn on **GitHub secret scanning** and push protection.
- If a secret is committed, **rotate it immediately**. Deleting the commit isn't enough: it may already be copied.

## A08 and A09 briefly

- **Software and data integrity**: verify what you install and deploy: signed packages and images, checked downloads, protected CI pipelines.
- **Logging and monitoring failures**: if nothing records logins, permission errors and admin actions, you can't detect or investigate an attack. That's tomorrow.
