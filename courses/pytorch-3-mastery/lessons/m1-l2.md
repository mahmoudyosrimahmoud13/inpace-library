# torch.compile and efficient models

## torch.compile

PyTorch normally runs eagerly: each operation is launched from Python, one at a time. `torch.compile` (PyTorch 2.0 onwards) captures the model's operations into a graph and generates optimised code, **fusing** many small operations into fewer kernels. One line, often a sizeable speed-up on GPUs, especially for models with many element-wise operations.

```python
import time
import torch
from torch import nn

class MLPBlock(nn.Module):
    def __init__(self, d):
        super().__init__()
        self.fc1, self.fc2, self.norm = nn.Linear(d, 4 * d), nn.Linear(4 * d, d), nn.LayerNorm(d)

    def forward(self, x):
        return x + self.fc2(torch.nn.functional.gelu(self.fc1(self.norm(x))))

model = nn.Sequential(*[MLPBlock(256) for _ in range(4)]).eval()
x = torch.randn(64, 256)
compiled = torch.compile(model)               # nothing happens yet

with torch.inference_mode():
    t = time.perf_counter(); compiled(x); first = time.perf_counter() - t      # first call compiles: slow
    t = time.perf_counter(); compiled(x); second = time.perf_counter() - t
    print(f"first call {first:.2f} s (compiling), second call {second * 1000:.1f} ms")
    print(torch.allclose(model(x), compiled(x), atol=1e-4))                     # same results
```

What to know:

- The **first call compiles** (seconds to minutes). It pays off for training runs and long-lived servers, not short scripts.
- A change in input shape can trigger a **recompile**; `dynamic=True` or `torch._dynamo.mark_dynamic` help with varying sizes.
- Parts it can't capture (data-dependent Python control flow, some libraries) cause **graph breaks**: it still works, just less optimised. `TORCH_LOGS="graph_breaks"` shows where.
- Modes: `mode="reduce-overhead"` (CUDA graphs, small batches), `mode="max-autotune"` (longer compile, tries more kernels).

## Efficient building blocks

| Technique | What it saves |
|---|---|
| `F.scaled_dot_product_attention` | uses FlashAttention-style kernels: much less memory and time for attention |
| `torch.backends.cuda.matmul.allow_tf32 = True` or `torch.set_float32_matmul_precision("high")` | fast TF32 matmuls on recent NVIDIA GPUs |
| `model.to(memory_format=torch.channels_last)` | faster convolutions on GPUs with tensor cores |
| fused optimizers: `AdamW(..., fused=True)` | one kernel for the whole update on CUDA |
| **activation checkpointing** (`torch.utils.checkpoint`) | memory: recompute activations in backward instead of storing them |

```python
from torch.utils.checkpoint import checkpoint

block = MLPBlock(256)
x = torch.randn(64, 256, requires_grad=True)
y = checkpoint(block, x, use_reentrant=False)     # activations inside the block are not stored
y.sum().backward()                                # they're recomputed here
print(x.grad.shape)
```

Activation checkpointing trades about one extra forward pass of compute for a large memory saving, which is how big models fit on fewer GPUs.

## Memory on a GPU

`torch.cuda.max_memory_allocated()` reports peak usage; `torch.cuda.memory_summary()` breaks it down. Most memory in training goes to activations (scale with batch size and sequence length), weights, gradients and optimizer state (Adam keeps two extra numbers per weight), roughly in that order for big batches.
