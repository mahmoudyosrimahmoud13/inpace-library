# Databases at scale: replication, sharding and CAP

## Replication

Keep copies of the database on several machines. A common setup is **one primary for writes, several replicas for
reads**. Gains: more read capacity and survival when one machine dies. Cost: replicas can be a little behind
(**replication lag**).

## Sharding (partitioning)

Split the data across machines, for example users A-M on shard 1 and N-Z on shard 2, or by a hash of `user_id`.
Gains: more write capacity and storage. Costs: queries across shards are harder, and a bad key creates a **hot shard**.

## CAP theorem

When the network between machines breaks (a **partition**), a distributed system must choose:

- **Consistency:** every read sees the latest write, even if some requests must fail.
- **Availability:** every request gets an answer, even if it might be slightly stale.

Banking leans to consistency; a social media like counter leans to availability.

## Queues

A **message queue** (Kafka, RabbitMQ, SQS) lets one service hand work to another without waiting. It smooths spikes
and lets parts fail without losing work. In our design, finished chunks could go on a queue for the transcoders.
