# API design

The **API** is the contract between clients and your servers. Design it from the user's actions:

```text
POST /streams                    -> start a stream, returns stream_id and an ingest URL
GET  /streams/{id}               -> stream info: title, status, available qualities
GET  /streams/{id}/manifest      -> the playlist file the video player reads
POST /streams/{id}/end           -> stop the stream
```

Good habits:

- Name resources with nouns (`/streams`), and let the HTTP method be the verb.
- Return IDs, not whole objects, where clients can fetch details later.
- Think about **pagination** for lists and **idempotency** for actions that may be retried (so a retried "start"
  doesn't create two streams).
