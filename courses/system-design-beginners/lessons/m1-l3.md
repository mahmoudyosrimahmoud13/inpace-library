# Requirements for a live streaming service

Every design starts with **requirements**, never with boxes. There are two kinds:

- **Functional requirements:** what the system does. *Stream a live match. Viewers can pick a quality. Viewers can
  pause and go back a little.*
- **Non-functional requirements:** how well it does it. *Low latency, millions of viewers at once, keeps working when
  a server dies.*

**Fault tolerance** means the system keeps serving users when parts fail. The usual tools are **redundancy** (more
than one copy of every important server and every piece of data) and **no single point of failure** (no one box
whose death takes everything down).

## Ask before you draw

In an interview, spend the first minutes asking: *How many users? Read-heavy or write-heavy? How fresh must the data
be? Which features are in scope?* The answers change the design.
