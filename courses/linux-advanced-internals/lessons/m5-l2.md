# User namespaces and capabilities

## Root is really a bundle of powers

Since Linux 2.2, root's power is split into about 40 **capabilities**. A process can hold just the ones it needs.

| Capability | Allows |
|---|---|
| `CAP_NET_BIND_SERVICE` | Bind ports below 1024 |
| `CAP_NET_ADMIN` | Configure interfaces, routes, firewall |
| `CAP_NET_RAW` | Raw sockets (`ping`) |
| `CAP_SYS_ADMIN` | A huge grab-bag: mount, many admin calls. "The new root" |
| `CAP_CHOWN`, `CAP_DAC_OVERRIDE` | Change owners; ignore file permissions |
| `CAP_SYS_PTRACE` | Trace other processes |
| `CAP_SYS_TIME` | Set the clock |

```bash
grep Cap /proc/$$/status            # your shell's capability sets (hex)
capsh --decode=000001ffffffffff     # turn hex into names
getcap /usr/bin/ping                # file capabilities: ping = cap_net_raw
sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/myserver   # bind port 80 without being root
```

In systemd units:

```ini
[Service]
User=web
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
NoNewPrivileges=yes
```

The service runs as an ordinary user that can bind port 80, and can never gain any other privilege.

## SUID, the old way

A file with the **setuid** bit runs as its **owner** (often root), whoever starts it: `passwd` has to write `/etc/shadow`. Every SUID-root binary is a potential door to root, so keep the list short:

```bash
find / -xdev -perm -4000 -type f 2>/dev/null
```

## User namespaces

A user namespace maps IDs: UID 0 **inside** can be UID 100000 **outside**.

```bash
unshare --user --map-root-user bash   # no sudo needed!
id                                    # uid=0(root) inside
touch /etc/test                       # Permission denied: outside, you're still you
exit
```

Inside, the process holds full capabilities, but **only over resources its namespace owns**. This is how rootless Podman and rootless Docker work: "root" in the container is your normal user on the host, so a container escape lands as an ordinary user, not root.
