# Boot troubleshooting and crash investigation

## Where in the boot did it stop?

| You see | Stage | Usual cause | Fix |
|---|---|---|---|
| Nothing / "no bootable device" | Firmware | Boot order, dead disk | Firmware settings, check disk |
| `grub>` or `grub rescue>` prompt | Bootloader | Missing or broken grub.cfg | Rescue USB, reinstall GRUB |
| Kernel panic: "VFS: unable to mount root fs" | Kernel / initramfs | Wrong `root=`, missing driver in initramfs | Boot old kernel, `update-initramfs -u` / `dracut -f` |
| Dropped to `(initramfs)` or emergency shell | Early userspace | Root disk not found, RAID/LVM/crypt not assembled | Check `blkid`, assemble manually, fix config |
| "You are in emergency mode" | systemd | Bad `/etc/fstab` entry, failed mount | `journalctl -xb`, fix fstab, `mount -a`, reboot |
| Hangs at a service | systemd | A service waiting for network or a mount | `systemctl list-jobs` from another TTY (Alt+F2) |

## The emergency shell routine

```bash
journalctl -xb -p err            # what failed this boot
systemctl --failed
mount -o remount,rw /            # root is often read-only here
vi /etc/fstab                    # comment out or fix the bad line
systemctl daemon-reload && mount -a
systemctl default                # continue booting (or reboot)
```

## Kernel crashes

- **Oops**: the kernel hit a bug but kept running (something may be broken). Shows in `dmesg` with a call trace.
- **Panic**: the kernel stopped. Nothing is logged to disk after it.

To keep evidence from panics, set up **kdump**: a small spare kernel that boots after a crash and saves memory to `/var/crash`.

```bash
sudo apt install linux-crashdump      # Ubuntu (Red Hat: kexec-tools, enable kdump.service)
kdump-config show
```

Also useful: `kernel.panic = 10` (sysctl) reboots 10 seconds after a panic instead of hanging forever.

## Application crashes: core dumps

```bash
coredumpctl list                      # crashes systemd caught
coredumpctl info PID                  # signal, executable, stack trace
coredumpctl gdb PID                   # open the dump in gdb
```

## Hung machines

If the screen and SSH are frozen but the kernel is alive, the **magic SysRq** keys still work (if enabled: `sysctl kernel.sysrq`): Alt+SysRq+`t` dumps tasks, then the classic safe reboot sequence `r e i s u b`. On cloud VMs, the provider's serial console shows kernel messages even when SSH is dead.
