# Project 1: Pedal & Co.'s first tools

From today to day 5 you build one app: the support desk of **Pedal & Co.**, a small bike shop. Each day adds what
that day's lessons taught: tools today, an agent and tickets tomorrow, then approvals, memory and policies, and
finally a tested workflow.

The project folder is above this text. Save all its files in one folder and run, once:

```bash
pip install -U langchain langgraph langchain-ollama pytest
python shop.py
```

`shop.py` creates `shop.db`, a SQLite database with five products and four orders, and holds the shop's five
policies as text. The model comes from the `PEDAL_MODEL` environment variable, `ollama:qwen3` by default. Any
`provider:model` that supports tool calling works.

## Read the code

- **`get_order`** and **`check_stock`** are ordinary Python functions with the `@tool` decorator. The model never
  sees the code. It sees the name, the arguments and the docstring, which is why the docstrings say exactly what
  each tool does and what its input looks like ("like A1002", "part of the name").
- Both tools return **JSON text**, and a clear sentence when there's nothing to find, so the model can explain it
  instead of guessing.
- **`bind_tools`** tells the model which tools exist. Its reply then carries `tool_calls`, the tools it wants run
  with their arguments. Your code runs them.

## Run it

```bash
python p1_tools.py
```

The real output, with the small `qwen2.5:1.5b` model (set `PEDAL_MODEL=ollama:qwen2.5:1.5b`; all projects show
this model, so you can compare with bigger ones):

```text
Model: ollama:qwen2.5:1.5b

1. The tools, as the model sees them:
   get_order['order_id']: Look up one order by its id (like A1002): the product, its status, and...
   check_stock['product']: How many of a product are in stock and its price. `product` can be par...

2. Which tool does the model ask for?
   'Where is my order A1002?' -> get_order({'order_id': 'A1002'})
      ran it: {"id": "A1002", "product": "Helmet, size M", "price": 59.0, "status": "shipped", "placed": "2026-11-18", "delivered": null}
   'Do you have helmets in stock?' -> check_stock({'product': 'helmet'})
      ran it: [{"name": "Helmet, size M", "price": 59.0, "in_stock": 12}]
   'What are your opening hours?' -> no tool
```

What it shows:

- The model picks the right tool and fills in the arguments: `A1002`, and `helmet` from "helmets".
- For opening hours there's no tool, so it asks for none. (Day 4 adds the shop's policies, which include the hours.)
- The model only **asks**. Nothing runs until your code calls the tool, which is where you'll add checks and
  approvals.

## Make it yours

1. Add a tool `list_orders(email)` that returns a customer's orders. What should it refuse to return, and why?
2. Rewrite `check_stock`'s docstring to be vague ("checks products"). Does the model still choose it for "Do you have
   lights?"
3. Ask "Is my order A1002 in stock?". Which tool does it pick, and is that wrong?

## What to take away

- A tool is a function plus a description written for the model.
- The model chooses and fills in; your code runs and decides.
