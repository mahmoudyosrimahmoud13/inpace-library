# Test, trace and ship your agent

An agent that works in a demo can still fail on real users. Three habits make it production-ready.

## 1. Unit-test the parts without a model

Tools are plain functions, so test them like any code. For the agent loop, LangChain provides fake chat models that return scripted messages, so you can test your graph, middleware and policies without calling a paid API:

```python
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain.messages import AIMessage

class FakeToolModel(GenericFakeChatModel):
    def bind_tools(self, tools, **kwargs):     # the fake doesn't need real tool binding
        return self

script = [
    AIMessage(content="", tool_calls=[{"name": "refund", "args": {"order_id": "A-17", "amount": 500.0}, "id": "c1"}]),
    AIMessage(content="A manager will follow up about your refund."),
]
test_agent = create_agent(FakeToolModel(messages=iter(script)), tools=[refund], middleware=[cap_refunds])
out = test_agent.invoke({"messages": [{"role": "user", "content": "Refund $500"}]})
assert "Blocked" in out["messages"][2].content       # the policy stopped the tool
print("policy test passed")
```

## 2. Evaluate behaviour with real models

Build a set of 30 to 100 real or realistic inputs with what *should* happen: the right tool, the right category, a refusal, an approval request. Run it on every prompt or model change and compare scores with the last run. Check rules in code where you can (right tool called? valid category?) and use a model as judge only for things code can't check, after checking the judge against your own labels.

## 3. Trace everything

A trace records every model call, tool call, input, output, latency and token count of a run. LangSmith (LangChain's hosted platform) shows LangChain and LangGraph traces with almost no setup: set `LANGSMITH_TRACING=true` and an API key in the environment. Open-source options such as Langfuse or Arize Phoenix work too, and OpenTelemetry can send traces to the same place as the rest of your system. Read 20 real traces a week: that's where new failure types show up.

## Shipping checklist

```text
[ ] tools validated, read-only by default, risky ones behind approval
[ ] budgets: model calls, tool calls, timeouts
[ ] a production checkpointer (Postgres or SQLite), not InMemorySaver
[ ] PII redacted in prompts and traces
[ ] an eval set that runs in CI
[ ] tracing on, with a weekly review
[ ] a fallback model or a clear error message when the provider is down
```
