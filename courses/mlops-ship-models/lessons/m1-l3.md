# Project 1: a training script you can rerun and trust

You'll turn "train a model" into a script with fixed settings, catch a leak, see how much a random split flatters a
model, and check that training twice gives the same model.

The code is above this text. Save it as `p01_train.py`, next to `common.py` and the `data` folder.

## Read the code

- **`common.py`** is shared by every project:
  - `load()` reads `data/hour.csv`, makes a `time` column, and adds `last_week_avg` with `add_history()`: the
    average hourly count over the 7 days before each hour. It tells the model how busy the system has been lately,
    so the model can follow demand as it grows. It's known at prediction time.
  - `FEATURES` lists what the model may use. There's no month or season: with one year of training data, they only
    teach the model last year's level for each month (you'll measure this on day 3).
  - `between(df, start, end)` selects a time window; `score()` returns MAE (average error in bikes), RMSE (which
    punishes big misses more) and bias (positive: predicts too many).
- **`SETTINGS`** holds every choice in one dictionary: the time windows, the model's settings and the random seed.
- **`baseline(train)`** learns the average count per hour of the day, for working days and days off.
- **`make_model()`** builds a gradient boosted trees model with a **Poisson loss**, which suits counts (never below
  zero, and spread grows with the level).
- **`train()`** trains on 2011 and returns the model and both windows. It skips the first week, which has no history.

## Run it

```bash
python p01_train.py
```

The real output:

```text
Data: 17,379 hours from 2011-01-01 to 2012-12-31, 3,292,679 rentals

1. casual + registered == cnt in 100% of rows. With them as features:
   MAE 1.8 bikes: too good to be true, because at prediction time nobody knows them yet

2. How good is it? Depends how you test:
   random 80/20 split           MAE  25.6   (future hours leak into training)
   train 2011, test Jan-Feb 2012 MAE  28.0   RMSE  45.9   bias -17.5
   baseline (hour x workday)     MAE  39.2   RMSE  59.0   bias +5.4
   trained on 8,484 hours in 0.6 s

3. Train twice with the same settings: identical predictions = True
   settings and scores saved to p01_result.json
```

What it shows:

- **The leak gives an error of under 2 bikes.** It would be worth nothing in production: nobody knows tomorrow's
  `casual` and `registered` counts.
- **The random split says 25.6; the honest test says 28.0.** A random split lets the model see hours from the same
  days it's tested on. On real future data it does worse, and only the time split tells you that.
- **The model beats the baseline**, 28.0 against 39.2. But its bias is -17.5: it predicts too few bikes in 2012,
  because demand grew past anything in 2011. Keep that in mind; it comes back on day 8.
- **Training twice gives identical predictions**, because the seed is fixed.

## Make it yours

1. Move `train_end` to `2011-07-01`, and `valid_end` to `2011-09-01`. Is the model still better than the baseline?
2. Remove `last_week_avg` from `FEATURES`. What happens to the bias in 2012, and why?
3. Change `seed` and train three times. How much does MAE move? That's the noise in your comparisons.
4. Read the data's `README` on the UCI site and find one more column that would leak, or explain why none does.

## What to take away

- Put every setting in one place, and fix the seed.
- Test on the future, against a baseline. Suspect any result that's too good.
- A leak is a feature you won't have at prediction time.
