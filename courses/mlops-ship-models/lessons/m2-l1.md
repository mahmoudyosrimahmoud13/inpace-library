# Data checks and data versions

In ML, data is an input to the build, just like code. Two habits follow from that: **check** every batch before
it's used, and **version** every dataset a model was trained on.

## Check before you train (or predict)

Bad data rarely crashes anything. A weather feed switches to Celsius and temperatures of 21.5 arrive where the model
expects 0 to 1; a job loads the same day twice; a sensor sends nothing. The model trains or predicts anyway, and
quietly gets worse. So every pipeline starts with a **validation step** that stops on:

- **Schema**: the expected columns exist, with numeric types where needed.
- **Ranges**: values inside known limits (hours 0 to 23, normalized weather 0 to 1, counts not negative).
- **Missing values** where none are allowed.
- **Duplicates**: the same hour twice.
- **Business rules**: here, casual plus registered must equal the total.

Write the rules down once and run them everywhere: in training, in the pipeline, before batch predictions. Tools like
Great Expectations, Pandera and Pydantic do this at scale; the idea is the same.

## Version the data

To reproduce a model you need the exact data it saw. Data is too big for git, so tools like **DVC** split the job:

1. Store each version of a file in a **content-addressed store**: a folder (or cloud bucket) where each file's name
   is the hash of its contents. The same contents always get the same name, so nothing is stored twice.
2. Commit a small **lock file** to git that says which hash the project uses now.

Checking out an old commit then tells you exactly which data to fetch. And every training run can record the data's
hash, so any model can be traced back to its data. You'll build that mechanism in a few lines, so DVC holds no
mystery.
