# Project 4: a pipeline that reruns only what changed

You'll write the pipeline as four declared steps and a runner with a cache, then change one thing at a time and see
which steps run.

The code is above this text. Save it as `p04_pipeline.py`.

## Read the code

- **The four step functions** each take their input files, an output file and the settings they use:
  `step_validate` (project 2's rules, stopping on any problem), `step_features`, `step_train` and `step_evaluate`
  (the model's and the baseline's scores on the validation window, as `metrics.json`).
- **`STEPS`** declares, for each step: the function, its input files, its output file, and the names of the settings
  it uses.
- **`run_pipeline()`** merges `SETTINGS` with `params.json` (if it exists). For each step it hashes the function's
  source code (`inspect.getsource`), the settings it uses and the bytes of its inputs. Same key and the output exists:
  skip. Otherwise run, and save the new key in `pipeline_out/state.json`.
- `python p04_pipeline.py run` runs the pipeline once with your `params.json`: that's what CI will call. Without
  `run`, it runs the demonstration below.

## Run it

```bash
python p04_pipeline.py
```

The real output:

```text
1. First run: everything runs
   validate: ran (0.0 s) | features: ran (0.0 s) | train: ran (0.6 s) | evaluate: ran (0.0 s)
   MAE 28.0 (baseline 39.2)
2. Run again, nothing changed
   validate: skipped | features: skipped | train: skipped | evaluate: skipped
3. Change a training setting in params.json
   validate: skipped | features: skipped | train: ran (1.0 s) | evaluate: ran (0.0 s)
   MAE 27.4
4. Change only the validation window: training is reused
   validate: skipped | features: skipped | train: skipped | evaluate: ran (0.0 s)
   MAE 36.8 on 2,176 hours
5. A bad file arrives
   Stopped at validate: ['temp: 1 values outside [0, 1], e.g. 30.0']
   data restored; the model from step 4 is still in pipeline_out/model.pkl, untouched
```

What it shows:

- The second run skips everything: nothing changed.
- **A training setting reruns training and evaluation only.** Validation and features are reused.
- **A new validation window reruns only evaluation**: training doesn't use `valid_end`, so its key didn't change. The
  score is higher (worse) because March 2012 was busier than anything in the training data (more on that on day 5).
- **A bad file stops the pipeline at the first step**, and the last good model stays untouched.

## Make it yours

1. Edit one line inside `step_features` (even a comment) and run again. Which steps rerun, and why is that right?
2. Make the runner print a **graph** of the steps and their files, and make `evaluate` depend on two inputs so the
   order matters.
3. Add a `report` step that writes a one-page Markdown summary of `metrics.json`.
4. Rewrite the pipeline as a `dvc.yaml` with `dvc repro`, and compare.

## What to take away

- Declare each step's inputs, settings and output; hash them to decide what to rerun.
- A failing step stops the pipeline and leaves good outputs alone.
- Settings in a reviewed file make model changes visible.
