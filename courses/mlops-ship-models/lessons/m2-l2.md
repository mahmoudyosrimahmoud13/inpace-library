# Project 2: check every batch, and version the data

You'll write validation rules and watch them catch a broken batch, then build a small DVC-style data store with
snapshots and checkout.

The code is above this text. Save it as `p02_data.py`.

## Read the code

- **`RULES`** maps each numeric column to its allowed range.
- **`validate(df)`** returns a list of problems, empty when the batch is fine. It checks for missing columns first
  (nothing else makes sense without them), then types and ranges (a missing value counts as out of range), duplicated
  hours, and the casual + registered = total rule.
- **`file_hash()`** is the first 16 characters of the file's SHA-256: its content address.
- **`snapshot(path, note)`** copies the file to `.datastore/<hash>` (only if that hash isn't there yet) and records
  the hash in `data.lock.json`, with a short history.
- **`checkout(name, hash, to)`** copies any stored version back.
- The demonstration breaks a copy of 500 rows in four ways, then snapshots a working copy of the data, adds a day,
  snapshots again, and checks the first version out.

## Run it

```bash
python p02_data.py
```

The real output:

```text
1. The real data: no problems
2. A broken batch:
   - temp: 1 values outside [0, 1], e.g. 21.5
   - hum: 1 values outside [0, 1], e.g. nan
   - cnt: 1 values outside [0, ...], e.g. -4
   - 1 duplicated hours
   - casual + registered != cnt in some rows
   A batch without 'hum': ["missing columns: ['hum']"]

3. Versioning the data
   v1 = e03de4ee4ef4dc37, v2 = 4f4861ed22c4b6b7, snapshot again without changes = 4f4861ed22c4b6b7 (same, no new copy)
   data.lock.json: [{'hash': 'e03de4ee4ef4dc37', 'rows': 17379, 'note': 'two years of hours'}, {'hash': '4f4861ed22c4b6b7', 'rows': 17403, 'note': 'one more day arrives'}]
   checkout v1 -> hash e03de4ee4ef4dc37, 17,379 rows: back exactly
   store: ['4f4861ed22c4b6b7', 'e03de4ee4ef4dc37'], 2.3 MB
```

What it shows:

- The real data passes. The broken batch fails five ways: Celsius, a gap, a negative count, a duplicate, and a total
  that no longer adds up (the negative count broke that rule too).
- **Two versions, two hashes.** Snapshotting unchanged data gives the same hash and stores nothing new.
- **Checkout brings v1 back exactly**: the same hash and the same rows. (If git changed the file's line endings on
  Windows, your hashes will differ from these, but they'll behave the same.)

## Make it yours

1. Add a rule: no gap of more than 6 hours between consecutive rows. How many gaps does the real data have? Should the
   pipeline stop, or warn?
2. Split problems into **errors** (stop) and **warnings** (log and continue). Which of today's rules are which?
3. Make `snapshot()` also save a small **profile** of the data (row count, mean of each column) next to the hash.
   Compare the profiles of two versions.
4. Install DVC (`pip install dvc`), run `dvc init` and `dvc add data/hour.csv`, and compare its `.dvc` file with
   your `data.lock.json`.

## What to take away

- Validate every batch, in every pipeline, and stop on errors.
- Content-addressed storage plus a lock file in git: that's data versioning.
- Record the data's hash with every model.
