# Project 7: CI that blocks bad models

You'll write the tests and the GitHub Actions workflow, run the same steps locally, and watch a harmless-looking
change get blocked.

The code is above this text: `tests/test_bikecast.py`, `.github/workflows/ci.yml`, `check_quality.py`,
`quality.json` and `p07_ci.py`.

## Read the code

- **`tests/test_bikecast.py`** (pytest):
  - The `client` fixture trains a model once per test session, saves it in MLflow's format in a temporary folder,
    points `MODEL_URI` at it, and imports the service, so tests never depend on your local registry.
  - The tests: data checks pass, training is reproducible, the model beats the baseline by at least 10%,
    **serving features equal training features** for a real hour, `/health` and `/predict` work (and 3 am predicts
    fewer bikes than 8 am), four kinds of bad input get a 422, and batch limits hold.
- **`.github/workflows/ci.yml`**: on every push and pull request, check out the code, set up Python 3.12 with a pip
  cache, install, run the tests, run `python p04_pipeline.py run`, run the quality gate, and upload the model and
  metrics as an artifact you can download from the run's page.
- **`check_quality.py`** reads `pipeline_out/metrics.json` and `quality.json`, prints PASS or FAIL for each limit,
  and exits with code 1 if any failed. That exit code is what makes CI red.
- **`p07_ci.py`** reads the workflow file and runs its `run:` steps here, in order, stopping at the first failure,
  so you can see what CI will do before you push. Then it sets `max_iter` to 15 in `params.json`, as someone might to
  "speed up training", and runs it again.

## Run it

```bash
python p07_ci.py
```

The real output:

```text

   ok   Run the training pipeline      2.0 s   MAE 28.0 (baseline 39.2)
   ok   Quality gate                   0.0 s   
          PASS  MAE 28.0 <= 35.0
          PASS  MAE is 72% of the baseline's (limit 85%)
          PASS  |bias| 17.5 <= 25.0

2. Someone 'speeds up training' with max_iter = 15 in params.json:
   ok   Unit and service tests        11.0 s   10 passed in 9.22s
   ok   Run the training pipeline      1.4 s   MAE 65.4 (baseline 39.2)
   FAIL Quality gate                   0.0 s   
          FAIL  MAE 65.4 <= 35.0
          FAIL  MAE is 167% of the baseline's (limit 85%)
          PASS  |bias| 0.4 <= 25.0
   => BLOCKED
```

What it shows:

- On the current code, all ten tests pass, the pipeline trains, and the gate passes: the change could be merged.
- **The "faster" model still passes every test** (tests check the code, and the code is fine) **but fails the gate**:
  its error is worse than the baseline's. Without the gate, it would have been merged.

## On GitHub

Create a repository, push your folder, and open the **Actions** tab: the workflow runs on its own. Then push the
`max_iter: 15` change on a branch and open a pull request: GitHub marks it failed and shows the gate's FAIL lines in
the log.

## Make it yours

1. Add a CI job that builds the Docker image on pushes to `main` only (`if: github.ref == 'refs/heads/main'`).
2. Make the tests faster: train the fixture's model with `max_iter: 50`. How much time do you save, and do all tests
   still mean something?
3. Add a test that the model is **monotonic in one sensible way**: more rain (`weathersit` from 1 to 3) never
   predicts more bikes, all else equal. Does it hold?
4. Make the gate also compare with the last model on `main` (download its `metrics.json` artifact) and fail if the new
   one is more than 5% worse.

## What to take away

- Test data, reproducibility, quality, skew and the API, not only functions.
- A quality gate with limits in a file turns "is the model good?" into a red or green build.
- Run CI's steps locally first; push when they pass.
