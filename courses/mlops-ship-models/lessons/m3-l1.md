# Experiment tracking

You'll train dozens of models: different settings, features, data. A week later, nobody remembers which one scored
27.4 or what produced it. **Experiment tracking** records every training run automatically:

- **Parameters**: the settings you chose.
- **Metrics**: the scores, and how long it took.
- **Tags**: the data version and the git commit, so the run can be reproduced.
- **Artifacts**: files the run produced, above all the model itself.

## MLflow

MLflow is the most widely used open-source tracker. Its parts:

- **Tracking**: `mlflow.start_run()` opens a run; `log_params`, `log_metrics`, `set_tags` and `log_model` record
  things into it. Runs belong to an **experiment** (a named group, like "bikecast").
- **A backend store** holds parameters and metrics. You'll use a local SQLite file, `mlflow.db`; teams point it at a
  shared server.
- **The UI**: `mlflow ui --backend-store-uri sqlite:///mlflow.db` shows every run in a sortable table, with charts
  and comparisons.
- **The model registry**, for day 5.

`mlflow.search_runs()` returns the runs as a pandas table, so you can query your experiments with code.

## Logging a model safely

A saved scikit-learn model is not only numbers. Classic Python pickles can run code when they're loaded, so loading a
model file from someone else can be as risky as running their script. MLflow now saves scikit-learn models with
**skops**, which only loads types it knows are safe, and asks you to name any others you trust. Treat model files
like code: load only what you or your pipeline produced.

## What to compare

Compare runs on the **same validation data**, and look at more than one number. MAE says how far off on average;
bias says in which direction. A model with slightly better MAE and much worse bias may be the wrong choice for
planning how many bikes to put out.
