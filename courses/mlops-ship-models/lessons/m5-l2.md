# Project 5: a registry with a quality gate and rollback

You'll register three versions of Bikecast, promote one through a gate, reject another, and roll back and forward
with one call each.

The code is above this text. Save it as `p05_registry.py`.

## Read the code

- **`train_and_register()`** trains with the given settings and logs the model with `registered_model_name`, which
  registers it as the next version. It adds a description, and **no alias**: being registered isn't being in
  production.
- **`gate()`** loads the champion (`models:/bikecast@champion`) and the candidate (`models:/bikecast/<version>`),
  scores both on the same window, and passes only if the candidate's MAE is at least 2% lower and its bias no larger.
- **`promote()`** moves `previous` to the current champion, then `champion` to the new version.
- The main part deletes any old `bikecast` registration (so the demonstration starts clean), then: version 1,
  trained on 2011, becomes champion. Version 2 is trained up to April 2012. Version 3 has the same data but only 20
  trees. Both challengers face April 2012, which no model trained on.

## Run it

```bash
python p05_registry.py
```

The real output (the first lines are MLflow's own messages):

```text
Successfully registered model 'bikecast'.
Created version '1' of model 'bikecast'.
1. Version 1 registered and made champion
Registered model 'bikecast' already exists. Creating a new version of this model...
Created version '2' of model 'bikecast'.
2. Version 2, trained on three more months: champion MAE 68.8, challenger 42.5, bias +11.6 -> PROMOTE
Registered model 'bikecast' already exists. Creating a new version of this model...
Created version '3' of model 'bikecast'.
3. Version 3, only 20 trees: champion MAE 42.5, challenger 93.0, bias -50.0 -> REJECT

   The registry now:
   version 1: trained on 2011              aliases: previous
   version 2: trained up to April 2012     aliases: champion
   version 3: a rushed model: 20 trees     aliases: -

4. Production loads 'models:/bikecast@champion' -> version 2. Code never names a version.
5. Something's wrong in production? Roll back: champion -> version 1, one call, no redeploy
   (and forward again to version 2)
```

What it shows:

- **Version 1 is badly off in April 2012** (MAE 68.8): demand grew beyond what it saw.
- **Version 2, with three more months of data, passes** the gate and becomes champion.
- **Version 3 fails**: it's twice as bad as the new champion. Without the gate, someone in a hurry could have shipped
  it.
- The service always loads `@champion`. Rolling back is moving the alias to `previous`.

In the MLflow UI, the **Models** page shows the versions, their descriptions and aliases.

## Make it yours

1. Add a third gate rule: the challenger's MAE on **weekends** alone must not be worse than the champion's by more
   than 5%. Does version 2 still pass?
2. Add a `challenger` alias: set it when a version is registered, and remove it after the gate decides.
3. Log the gate's result (both scores and the decision) as tags on the candidate's model version, so the registry
   records why it was promoted or rejected.
4. What could go wrong if two people run `promote()` at the same moment? How would you prevent it?

## What to take away

- Register versions; point aliases at them; never hard-code a version in the service.
- Promote only through a gate, on recent data neither model saw.
- Rollback is one alias move, so practise it before you need it.
