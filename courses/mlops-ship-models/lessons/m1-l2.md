# What MLOps is

A model in production is a small part of a larger system. Around it sit the data that feeds it, the code that
trains it, the service that answers requests, the tests that guard it, and the monitoring that tells you when it
stopped being right. **MLOps** is the practice of building and running that system so that models can be changed
often and safely.

## Why ML is harder to ship than ordinary code

- **Behaviour comes from data, not only code.** The same code trained on different data is a different model. So you
  version data and models, not only code.
- **Failures are silent.** A web page that breaks returns an error. A model that goes wrong returns a number that
  looks fine. You only find out by measuring, often days later when the true answers arrive.
- **The world moves.** Demand grows, customers change, a sensor is replaced. A model is a snapshot of the past,
  and it decays.
- **It's easy to fool yourself.** Leaked features and random splits on time data make a model look far better than
  it will be.

## The lifecycle

1. **Data**: collect, check, version.
2. **Train**: reproducible runs, tracked with their settings, data version and scores.
3. **Evaluate**: on data the model will really face, against a baseline and against the current model.
4. **Register and release**: a versioned model, promoted only through a gate, with a way back.
5. **Serve**: an API or a batch job, computing features exactly as training did.
6. **Monitor**: inputs, outputs and, when labels arrive, errors.
7. **Retrain**: on a schedule or when monitoring says so, and back to step 3.

Each day of this course builds one step for Bikecast.

## Two rules for today

**Split by time.** If the model will predict the future, test it on a period after its training data. A random split
lets it learn from hours right next to the ones it's tested on, including later ones, and the score is too good.

**Beat a baseline.** Before any model, compute the simplest sensible prediction (here, the average for this hour on
working days or days off). If your model can't beat it clearly, it isn't worth deploying. Baselines also catch bugs:
a model far *better* than expected is usually leaking.

A **leak** is a feature that contains the answer, or something only known after the fact. In this data, `casual` and
`registered` add up exactly to the count you're predicting.
