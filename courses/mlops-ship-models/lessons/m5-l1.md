# The model registry: versions, a gate, and rollback

Experiment tracking records every run. Most runs are throwaways. The **model registry** is where the few that matter
get names and version numbers, and where you decide which one serves real traffic.

## Versions and aliases

Registering a model gives it the next version number: `bikecast` version 1, 2, 3. Versions never change; you add new
ones. To say which version does what, you point **aliases** at them:

- `champion`: the version in production.
- `previous`: the one before it, kept for rollback.
- `challenger`: a candidate being evaluated.

The service loads `models:/bikecast@champion`. It never names a version. **Releasing** a model is moving the alias;
**rolling back** is moving it back. No code changes, no redeploy of the service code, and the history stays complete.

## A gate before promotion

A new version only becomes champion if it passes a **gate**, a test written in code, not a judgment call at 6 pm:

- Compare the challenger with the current champion **on the same recent data**, which neither trained on.
- Require a real improvement (here, at least 2% lower MAE), so noise doesn't flip the champion back and forth.
- Check that it isn't worse in other ways (here, bias), and add any other rule that matters to you: speed, size,
  errors for a group of users.

## Why recent data

A model's validation score from training time is about the past. The question for promotion is how it does on the
weeks it's about to face. Hold out the most recent weeks, and compare both models there.
