# Project 3: track every run with MLflow

You'll log a baseline and ten models to MLflow, find the best with a query, log that model with its signature, and
load it back by run id.

The code is above this text. Save it as `p03_experiments.py`.

## Read the code

- The environment variables at the top switch off MLflow's progress bars, hints and usage reporting, so the output
  stays readable.
- **`mlflow.set_tracking_uri("sqlite:///mlflow.db")`** keeps everything in one local file.
- **`TRUSTED`** names the one model type skops should accept: the trees inside the gradient boosting model you
  trained yourself.
- **`git_commit()`** asks git for the current commit. (It says "not a git repository" until you run `git init`.)
- **`run()`** opens a run and records the settings, the feature list, the data hash (from project 2) and the commit;
  trains with project 1's `train()`; and records MAE, RMSE, bias and training time. With `log_model=True` it also
  saves the model with a **signature** (the input columns and types it expects) and an input example.
- The main part logs the baseline, a 3 × 3 grid of learning rates and tree sizes, and one run that adds month and
  season back. Then it queries all runs, sorted by validation MAE, retrains the best settings with the model logged,
  and loads that model back with `runs:/<run id>/model`.

## Run it

```bash
python p03_experiments.py
mlflow ui --backend-store-uri sqlite:///mlflow.db
```

What it shows:

- **Settings matter less than you'd think**: nine runs span 27.4 to 30.2. The baseline is far behind at 39.2.
- **Adding month and season makes the model much worse**: 46.5, with a bias of -43. With one year of training data,
  "January" means "January 2011 demand", and 2012 was far busier. This is what the feature list in `common.py` is
  about, and now you have the evidence on record.
- Every run carries its data version and commit, so you can rebuild any of them.
- The logged model, loaded back by run id, gives exactly the same score.

Open the UI, click the best run, and look at the **Artifacts** tab: the model, its `requirements.txt`, its signature
and the input example are all there.

## Make it yours

1. Add `max_iter` (100, 300, 600) to the grid. Use the UI's chart view to plot MAE against it.
2. Log a **plot** as an artifact: predicted against actual for the validation window (`mlflow.log_figure`).
3. Use `mlflow.autolog()` instead of logging by hand, and compare what it records with what `run()` records.
4. Commit your code, rerun, and check that the `git_commit` tag now shows a real commit.

## What to take away

- Log parameters, metrics, data version, code version and the model, for every run.
- Query runs with code; compare on the same data and on more than one metric.
- Model files can carry code: load only what you trust.
