# CI/CD for models: tests that matter

**Continuous integration (CI)** runs checks on every push and pull request, on a clean machine, so a change can only
be merged when they pass. For an ML project, the checks go beyond unit tests.

## What to test

| Test | Catches |
|---|---|
| Data checks pass on the training data | A broken file committed or fetched |
| Training is reproducible | Hidden randomness, so results can't be compared |
| The model beats the baseline by a margin | A bug that makes the model useless but not broken |
| Serving features equal training features | Training/serving skew |
| The API answers, and refuses bad input | Broken endpoints, missing validation |
| Batch limits are enforced | Requests that could exhaust the service |

Tests must be **fast** (minutes, not hours) and **deterministic**. Train on a small, fixed slice of data if the full
training is slow.

## The quality gate in CI

After the tests, CI runs the training pipeline and a **quality gate**: a script that reads the new model's metrics
and exits with an error if they fall below limits written in a file (`quality.json`). The limits are absolute (MAE
under 35), relative (under 85% of the baseline's error) and about direction (bias within 25 bikes). Changing a limit
is then a visible, reviewed change, not a silent one.

The gate in CI is different from day 5's promotion gate: CI asks "is this change safe to merge?" on a fixed
validation window; promotion asks "is this model better than production now?" on the latest data.

## CD

**Continuous delivery** takes it further: after a merge to `main`, build the image, register the model, run the
promotion gate, deploy to a staging service, and wait for a person (or more checks) before production. Start with CI;
add delivery steps one at a time.

## GitHub Actions

A workflow is a YAML file in `.github/workflows/`. It lists **triggers** (`on: push`), **jobs** that run on fresh
machines (`runs-on: ubuntu-latest`) and **steps**: actions others wrote (`actions/checkout`, `actions/setup-python`)
and your own commands (`run:`). A step that exits with an error fails the job, and GitHub shows a red cross on the
commit and the pull request.
