# Pipelines: steps, inputs, outputs, and caching

A training pipeline is a fixed sequence of steps, each reading the outputs of earlier ones: validate the data, build
features, train, evaluate. Written as one script, it works until it doesn't: you change one setting and wait for
everything to rerun, or you forget a step and evaluate an old model.

## A step declares what it depends on

Write each step as a function with **declared** inputs (files), settings and an output file. Then a runner can:

- run steps **in order** (a chain here; a graph, or **DAG**, when steps branch),
- **skip** a step whose inputs, settings and code haven't changed since its last run, reusing its output,
- **stop** at the first failure, leaving earlier outputs as they were.

The skip decision is a **cache key**: a hash of the step's code, the settings it uses, and the contents of its input
files. If the key matches the last run and the output exists, the output is still right. This is how Make, DVC
pipelines (`dvc repro`), and the caching in Airflow, Prefect, Dagster and Kubeflow work.

## Why only the settings a step uses

If the training step hashed *all* settings, changing the validation window would retrain the model for nothing. Each
step lists the settings it reads, so a change reruns exactly the steps that depend on it, and the ones after them.

## Settings in a file

Keep the settings that change most often in a small file, `params.json`, under git. A change to the model becomes a
one-line diff that anyone can review, and CI (day 7) can run the pipeline on it.

## Orchestrators

Real pipelines also need schedules, retries, alerts, parallel steps and machines with GPUs. That's what
orchestrators like Airflow, Prefect, Dagster or Kubeflow add. Learn the idea on a small runner first; it's the same
idea in all of them.
