# Project 6: a prediction service, tested and packaged

You'll serve the champion with FastAPI, send it good and bad requests, measure its speed, and export the model for a
Docker image.

The code is above this text: `serve.py` is the service, `p06_serve.py` exercises it, and `Dockerfile` with
`requirements-serve.txt` packages it. Run project 5 first: the service loads its champion.

## Read the code

**`serve.py`**:

- Reads its settings from environment variables: `MODEL_URI` (by default `models:/bikecast@champion`; in Docker, the
  exported folder), `HISTORY_CSV` and `PREDICTION_LOG`.
- Loads the model and the history of observed counts **once**, at start-up, not per request.
- **`Hour`** is the request body as a Pydantic model: the time, holiday, and weather values with their allowed
  ranges.
- **`features()`** computes exactly the training features. `weekday` follows the data's convention (0 is Sunday;
  Python's own `dayofweek` starts at Monday, a classic source of skew), and `last_week_avg` is the mean count over
  the 7 days before the hour. With too little history it refuses.
- **`/health`** says the service is up and which model version it runs. **`/predict`** takes 1 to 500 hours,
  predicts, rounds to whole bikes, logs each prediction with its features, and returns them with the time taken.

**`p06_serve.py`** uses FastAPI's `TestClient` to call the service in-process: a known hour, bad inputs, a week in
one batch, and 50 single requests for latency. Then it exports the champion to `./model`.

**`Dockerfile`** starts from `python:3.12-slim`, installs only `requirements-serve.txt`, copies the code, the history
and `model/`, sets `MODEL_URI=/app/model`, runs as an ordinary user, and starts `uvicorn`.

## Run it

```bash
python p06_serve.py
```

The real output:

```text
1. {'status': 'ok', 'model_version': '2'}
2. 8 am on 1 May 2012: predicted 535 bikes, actually 557
3. Bad input -> 422: weathersit: Input should be less than or equal to 4; temp: Input should be less than or equal to 1
   Too early for history -> 422: Not enough history before 2011-01-02 08:00:00 to compute last_week_avg
4. A batch of 168 hours (the first week of May) in 56 ms, MAE 36.2
5. 50 single requests: median 7.4 ms, p95 10.2 ms
6. Every prediction is logged for monitoring: 219 lines in p06_predictions.jsonl
7. Champion exported to ./model for the Docker image: ['MLmodel', 'conda.yaml', 'model.skops', 'python_env.yaml', 'requirements.txt']
```

What it shows:

- A prediction within 22 bikes of the real count, from version 2 (the champion).
- Bad values are refused with the reason, before they reach the model.
- A whole week (168 hours) in one request takes about 50 ms: batch requests are much cheaper per hour.
- A single request takes under 10 ms, and every prediction is logged.

## Run it for real

```bash
uvicorn serve:app --port 8000
```

Open http://127.0.0.1:8000/docs: FastAPI draws a page where you can try `/predict` from the browser.

Then the container (with Docker installed, after the export above):

```bash
docker build -t bikecast:2 --build-arg MODEL_VERSION=2 .
docker run --rm -p 8000:8000 bikecast:2
```

The same `/health` and `/predict` now answer from the container. How this was tested: the image's exact contents
(the same files, a clean environment with only `requirements-serve.txt`, and the image's start command) answered
`{"status":"ok","model_version":"2"}` and predicted 535 bikes for 8 am on 1 May 2012. The `docker build` itself
couldn't be run in testing, because it downloads the base image from Docker Hub. If it fails for you, the usual
causes are a missing `./model` folder (run `python p06_serve.py` first) or no network during the build.

## Make it yours

1. Add a **batch** script that reads a CSV of hours, calls `/predict` in chunks of 500, and writes the predictions
   next to them.
2. Add `/predict` input logging of the **raw request** too, and a request id returned in a header.
3. Run the service with `--workers 2` and measure throughput with 1,000 requests from a small script using threads.
4. Make the image smaller: compare the size with and without `mlflow-skinny` (load the model with `skops` directly).

## What to take away

- Same feature code in training and serving, and a test that proves it.
- Validate inputs at the door; log every prediction with its model version.
- One fixed model per image, with only serving dependencies.
