# Serving: online, batch, and containers

A registered model is a file. Serving turns it into answers. There are two shapes:

- **Online (real time)**: an HTTP API answers one request at a time, in milliseconds. Bikecast's app asks "how many
  bikes at 8 am?" and gets a number.
- **Batch**: a job predicts many rows at once on a schedule and writes the results somewhere (tomorrow's 24 hours,
  for every station, at midnight). Cheaper and simpler when nobody waits for the answer.

Bikecast's API does both: `/predict` takes a list of 1 to 500 hours.

## Same features, same code

The most common serving bug is **training/serving skew**: the service computes a feature slightly differently from
training (a different time zone, a different weekday numbering, an average over a different window). Nothing
crashes; the model just gets wrong inputs. Defences:

- Compute features in **shared code** used by both training and serving.
- Write a **test** that sends a known hour to the service and compares its features with the training data's.

## Check what comes in

Every request is untrusted. Validate types and ranges at the door (FastAPI does this with Pydantic models) and return
a clear 422 error instead of a nonsense prediction. Also refuse requests you can't answer well, like an hour with no
history before it.

## Log what goes out

Write every prediction, with its inputs and the model version, to a log. Monitoring (day 8) needs it, and so does
debugging: "why did it say 40 bikes on Tuesday?"

## Containers

A **Docker image** packs the code, the libraries and the model into one file that runs the same way everywhere. Two
habits:

- Put **one fixed model** in the image (exported from the registry), and tag the image with the model version. The
  image is then an exact, testable release.
- Install **only what serving needs**: no training tools, no MLflow server, no notebooks. Smaller images build, ship
  and start faster and have fewer security holes. Don't run as root inside.
