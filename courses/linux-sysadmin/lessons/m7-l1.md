# Watching resources and fixing a full disk

## The quick health check

```bash
uptime                         # load average vs nproc
free -h                        # memory: look at 'available'
df -h; df -i                   # disk space and inodes
top / htop                     # who uses CPU and memory now
vmstat 1 5                     # r (run queue), si/so (swap), wa (waiting on I/O)
iostat -xz 1 3                 # per-disk load (package sysstat); %util near 100 = disk is the bottleneck
ss -s                          # connection counts
```

| Symptom | Likely resource | Look at |
|---|---|---|
| Everything slow, load high, CPU idle | Disk I/O | `vmstat` wa, `iostat`, `iotop` |
| Load high, CPU 100% | CPU | `top`, sorted by CPU |
| Processes killed at random | Memory | `journalctl -k | grep -i oom`, `free -h` |
| Writes fail, "No space left on device" | Disk space or inodes | `df -h`, `df -i` |

## A full disk, step by step

```bash
df -h                                          # which file system?
sudo du -xh / --max-depth=1 2>/dev/null | sort -h | tail   # -x: stay on that file system
sudo du -xh /var --max-depth=2 2>/dev/null | sort -h | tail
sudo find / -xdev -type f -size +500M -exec ls -lh {} + 2>/dev/null
```

Usual culprits and safe fixes:

| Culprit | Fix |
|---|---|
| Huge logs in `/var/log` | Fix logrotate; truncate a live log with `sudo truncate -s 0 file` (don't `rm` it while open) |
| Journal | `sudo journalctl --vacuum-size=500M` |
| Package cache | `sudo apt clean` / `sudo dnf clean all` |
| Old kernels | `sudo apt autoremove` |
| Docker images and volumes | `docker system df`, `docker system prune` (read what it will delete) |
| Deleted but still open files | `sudo lsof +L1`, then restart that process |

When `df` says full but `du` can't find it, it's almost always the last row.

## Keep an eye on it

Simple and effective: a cron job or timer that runs `df` and alerts above 85%. The Observability course replaces this with proper monitoring.
