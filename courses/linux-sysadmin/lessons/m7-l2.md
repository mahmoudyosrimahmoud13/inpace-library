# Backups that actually restore

A backup you haven't restored is a hope, not a backup.

## The 3-2-1 rule

- **3** copies of your data
- on **2** different kinds of storage
- **1** copy off-site (another building, another cloud account)

And add: at least one copy that ransomware or a wrong command can't change (immutable or offline).

## Tools

| Tool | Good for |
|---|---|
| `rsync` | Copy changes only, to another disk or server |
| `tar` | One archive file of a directory |
| Database dumps (`pg_dump`, `mysqldump`) | Consistent database backups. **Never** just copy a running database's files |
| LVM / cloud snapshots | Fast point-in-time copies of a whole volume |
| restic, borg | Deduplicated, encrypted, versioned backups to many targets |

```bash
# Mirror a directory to a backup disk (only changes are copied):
rsync -aH --delete /srv/data/ /backup/data/
#   -a keep permissions, times, links   --delete remove files deleted at the source

# Over SSH to another server:
rsync -az -e ssh /srv/data/ backup@backuphost:/backups/web01/

# A dated archive:
sudo tar czf /backup/etc-$(date +%F).tgz /etc

# A database:
sudo -u postgres pg_dump -Fc mydb > /backup/mydb-$(date +%F).dump
```

Careful with trailing slashes in rsync: `src/` copies the **contents**, `src` copies the directory itself.

## The restore test

```mermaid
flowchart LR
  A["Back up on a schedule (timer)"] --> B["Copy off-site"]
  B --> C["Every month: restore to a scratch machine"]
  C --> D["Check: files open, app starts, row counts match"]
  D --> E["Write down how long it took"]
```

The time it takes to restore is your real recovery time. Knowing it before a disaster is the whole point.

## What to back up on a server

- Application data and databases (most important).
- `/etc` (your configuration).
- Anything you can't rebuild from a package or from Git. If you can rebuild the server from code (Ansible, the IaC course), you mostly back up **data**.
