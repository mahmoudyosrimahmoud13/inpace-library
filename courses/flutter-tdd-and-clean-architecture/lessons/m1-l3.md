## What to watch for

Focus on why the second use case exposes duplication and why the course introduces a common use-case contract. The lesson is as much about API consistency and refactoring as it is about Dart syntax.

## Callable classes

Dart classes can implement a `call` method:

```dart
class GetRandomNumberTrivia {
  Future<void> call() async {
    // ...
  }
}
```

That means an instance can be invoked like a function:

```dart
final useCase = GetRandomNumberTrivia();
await useCase();
```

This works especially well for use cases because their names already describe actions.

## A shared UseCase contract

If every use case exposes a different method such as `execute`, `run`, `perform`, or `call`, the presentation layer has to remember unnecessary differences.

A shared abstraction can establish a consistent API:

```dart
abstract class UseCase<Type, Params> {
  Future<Either<Failure, Type>> call(Params params);
}
```

A use case with no parameters can use a special parameter type such as `NoParams`.

The important principle is not the exact generic signature. It is the consistent contract.

## Refactoring through duplication

TDD does not mean you must avoid duplication at every moment. During implementation, duplication can reveal a pattern that is worth extracting.

A healthy sequence is:

```text
Make behavior work
    ↓
Observe duplication
    ↓
Identify the common abstraction
    ↓
Refactor
    ↓
Let tests protect the behavior
```

Tests provide confidence while the internal structure changes.

## Stable boundaries

Notice how the use cases depend on the repository abstraction:

```text
UseCase
   |
   v
Repository contract
   ^
   |
Repository implementation
```

The use case does not need to know whether the implementation eventually uses an HTTP API, a database, or a fake repository.

## Practical architectural judgment

Clean Architecture should not become a collection of classes created merely to satisfy a diagram. A class deserves to exist when it represents a meaningful responsibility or boundary.

In a larger application, use cases can provide a useful vocabulary for application operations. In a tiny application, excessive abstraction can also create unnecessary complexity. Advanced developers should understand both sides.

## Summary

This lesson turns the initial domain implementation into a more consistent structure. Callable use cases, shared contracts, and refactoring demonstrate how TDD can support architectural evolution rather than merely verify finished code.
