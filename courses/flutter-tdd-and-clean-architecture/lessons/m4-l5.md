## What to watch for

Watch how the final UI consumes BLoC states and dispatches events. The important architectural idea is that the UI becomes a rendering layer rather than the place where application logic lives.

## UI as a state renderer

A Flutter widget should primarily answer:

```text
Given the current state, what should the user see?
```

For example:

```text
Initial → "Start searching!"
Loading → progress indicator
Loaded → trivia text
Error → error message
```

The widget does not need to know why a request failed.

## Connecting BLoC to the UI

A BLoC provider makes the BLoC available to descendant widgets.

A state listener or builder can react to emitted states.

Conceptually:

```dart
BlocBuilder<NumberTriviaBloc, NumberTriviaState>(
  builder: (context, state) {
    // render based on state
  },
);
```

The controls dispatch events:

```dart
context.read<NumberTriviaBloc>().add(
  GetTriviaForRandomNumber(),
);
```

This creates a clean boundary between user interaction and application logic.

## Splitting widgets

The course separates UI responsibilities into smaller widgets.

This is useful because large widget trees are difficult to reason about and test.

A page can coordinate the screen while smaller widgets handle focused presentation responsibilities.

## Keyboard and layout behavior

Text input introduces practical UI concerns. When the keyboard appears, available screen height decreases.

A layout that assumes a fixed height may overflow.

Wrapping content in a scrolling widget can allow the UI to adapt to the reduced viewport.

This illustrates an important distinction:

```text
Architecture = separation of responsibilities

UI engineering = responsive behavior and usability
```

Good architecture does not automatically produce good UI. Both concerns still require deliberate design.

## Testing the final architecture

Once the layers are connected, you can test each boundary independently:

```text
Entity/use case → unit tests
Repository       → unit tests with mocks
Data source      → unit tests with mocked infrastructure
BLoC             → state-transition tests
Widget           → widget tests
App               → integration tests
```

This creates multiple levels of confidence rather than relying on one huge test.

## Modern Flutter considerations

The course is based on an older Flutter/Dart ecosystem, so some package APIs and syntax shown in the videos may differ from current Flutter versions.

Preserve the architectural principles while adapting deprecated APIs, package versions, null-safety syntax, and testing libraries to the current project.

Do not blindly copy old syntax into a modern application.

## Final summary

The finished application demonstrates a complete flow:

```text
UI
 ↓
BLoC
 ↓
Use Case
 ↓
Repository
 ↓
Data Source
 ↓
External API / Cache
```

TDD provides executable specifications at each boundary, while Clean Architecture keeps those boundaries understandable and replaceable.

The real outcome is not a Number Trivia app. It is the ability to structure a larger Flutter application so that business logic remains testable and infrastructure remains replaceable.
