## What to watch for

Watch how the BLoC is tested using streams and mocked use cases. Focus on the relationship between an incoming event and the sequence of states emitted afterward.

## Reactive flow

A BLoC can be viewed as a state transformation system:

```text
Event + Current State
          ↓
        BLoC
          ↓
     New States
```

For example:

```text
GetTriviaForConcreteNumber(42)
          ↓
        Loading
          ↓
   TriviaLoaded
```

If the use case fails:

```text
GetTriviaForConcreteNumber(42)
          ↓
        Loading
          ↓
     ErrorState
```

## Why streams matter

BLoC is naturally suited to asynchronous operations because state changes can be emitted over time.

The UI can subscribe to the state stream and rebuild according to the current state.

## Testing state sequences

A BLoC test should verify behavior such as:

```text
Given a valid event
When the use case succeeds
Then states are:
Loading → Loaded
```

Another test can verify:

```text
Given a valid event
When the use case fails
Then states are:
Loading → Error
```

This is much more useful than testing private implementation details.

## Mocking use cases

The BLoC should not call the real repository in its unit tests.

Instead, mock the use case:

```dart
when(mockGetConcreteTrivia(any))
    .thenAnswer((_) async => Right(trivia));
```

This isolates the BLoC test from networking, persistence, and repository logic.

## Either and presentation

When the use case returns `Either`, the BLoC decides how the two outcomes map to UI states.

```text
Left(Failure)
    ↓
Error state

Right(NumberTrivia)
    ↓
Loaded state
```

This demonstrates why explicit result types can be useful across architecture boundaries.

## Summary

BLoC tests focus on observable state transitions. Dependencies are mocked, events are dispatched, and emitted states are asserted in sequence.
