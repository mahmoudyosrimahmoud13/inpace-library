## What to watch for

Pay attention to why the course avoids treating a device's Wi-Fi or mobile-data status as proof of internet access.

## Network availability versus internet access

A device may be connected to Wi-Fi but unable to reach the internet.

Examples include:

- a router with no upstream connection;
- captive portals;
- broken DNS;
- VPN problems;
- a network that blocks the requested service.

Therefore, a network interface being active is not necessarily equivalent to successful internet access.

## Hiding third-party packages

The application defines:

```dart
abstract class NetworkInfo {
  Future<bool> get isConnected;
}
```

The concrete implementation can use a third-party package.

This gives the rest of the application a stable abstraction:

```text
Repository
    ↓
NetworkInfo contract
    ↓
NetworkInfoImpl
    ↓
Third-party connectivity library
```

If the package changes, the repository contract does not need to change.

## Why test a simple class?

It may seem unnecessary to test a class that only forwards one property.

But the class creates a boundary around third-party code. That boundary becomes valuable when the library is replaced or its behavior needs to be controlled in tests.

## Testing external dependencies

The test can mock the third-party connectivity abstraction rather than relying on the actual device's network.

This keeps tests:

- deterministic;
- fast;
- repeatable;
- independent of the environment.

## Summary

Network information is another example of dependency isolation. The application depends on its own `NetworkInfo` abstraction rather than coupling business code to a connectivity package.
