## What to watch for

Focus on the use of contracts for remote and local data sources and on the relationship between exceptions and failures.

## Data-source contracts

The repository should not depend directly on a concrete HTTP client or SharedPreferences implementation.

Instead, define contracts such as:

```dart
abstract class NumberTriviaRemoteDataSource {
  Future<NumberTriviaModel> getConcreteNumberTrivia(int number);
  Future<NumberTriviaModel> getRandomNumberTrivia();
}

abstract class NumberTriviaLocalDataSource {
  Future<NumberTriviaModel> getLastNumberTrivia();
  Future<void> cacheNumberTrivia(NumberTriviaModel triviaToCache);
}
```

These abstractions make the repository testable.

During repository tests, you can replace real data sources with mocks.

## Exceptions and failures

A useful distinction is:

```text
Data source
   ↓
throws Exception
   ↓
Repository catches it
   ↓
Repository returns Failure
   ↓
Domain/presentation handles Failure
```

An exception is an implementation-level mechanism. A failure is part of the application's expected result model.

For example:

```dart
class ServerException implements Exception {}

class CacheException implements Exception {}
```

At the domain boundary, these can become:

```dart
class ServerFailure extends Failure {}

class CacheFailure extends Failure {}
```

The repository performs the translation.

## Why not expose exceptions everywhere?

If every layer knows about HTTP exceptions, database exceptions, and storage exceptions, infrastructure details leak through the application.

Instead, the repository can normalize those details into meaningful failures.

## Mocking

The contract is especially valuable during TDD.

A repository test does not need a real internet connection. It can use a mock:

```dart
when(mockRemoteDataSource.getConcreteNumberTrivia(42))
    .thenAnswer((_) async => expectedTrivia);
```

The test can then verify that the repository behaves correctly.

## Summary

Data-source contracts create replaceable boundaries. Exceptions describe infrastructure failures, while domain failures provide a stable way for the rest of the application to understand those problems.
