## What to watch for

Watch the repository tests closely. The important part is not the syntax of Mockito or the exact helper methods; it is how business policy is tested independently of implementation details.

## The repository's responsibility

The repository decides how to obtain data.

For the Number Trivia application, the policy is approximately:

```text
If online:
    request trivia remotely
    cache successful result
    return result

If offline:
    return cached trivia
    or report a cache failure
```

This policy belongs in the repository because it coordinates multiple data sources.

## Testing the online path

A repository test can provide mocked dependencies:

```dart
final repository = NumberTriviaRepositoryImpl(
  remoteDataSource: mockRemote,
  localDataSource: mockLocal,
  networkInfo: mockNetwork,
);
```

Then configure the network status and expected remote response.

The test should verify both the returned result and important side effects, such as caching successful remote data.

## Testing the offline path

When the device is offline, the repository should not attempt to contact the remote source.

Instead it asks the local source for cached data.

A strong test checks both behavior and interaction:

```text
network = offline
        ↓
local source is called
        ↓
remote source is not called
        ↓
cached result is returned
```

This prevents an implementation from accidentally violating the intended policy.

## DRY without destroying readability

The course introduces a shared helper for concrete and random trivia retrieval. Both operations have almost identical behavior.

Refactoring is useful when it removes accidental duplication while preserving meaningful names.

Be careful not to create an abstraction so generic that the code becomes harder to understand.

## Repository as policy

A repository is more than a wrapper around an API.

Compare:

```text
Bad mental model:
Repository = HTTP client wrapper

Better mental model:
Repository = application-facing data policy boundary
```

The repository can combine multiple sources and decide which source should be trusted.

## Summary

Repository TDD verifies the application's data policy. It tests network conditions, source selection, caching behavior, exception translation, and returned failures without requiring real infrastructure.
