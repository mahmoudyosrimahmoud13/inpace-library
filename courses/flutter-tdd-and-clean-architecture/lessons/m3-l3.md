## What to watch for

Use this lesson to connect the previous pieces into one coherent data flow. The important skill is being able to trace a request from the UI-facing application operation all the way to the external API and back.

## Complete data flow

A concrete trivia request travels roughly like this:

```text
User input
    ↓
Presentation
    ↓
Use Case
    ↓
Repository contract
    ↓
Repository implementation
    ↓
NetworkInfo
    ↓
Remote Data Source
    ↓
HTTP client
    ↓
API
```

The response travels back in the opposite direction:

```text
API response
    ↓
Remote Model
    ↓
Repository
    ↓
Entity
    ↓
Use Case result
    ↓
Presentation
```

The local cache introduces another branch:

```text
Repository
├── online  → remote → cache → result
└── offline → cache → result
```

## Why the layers remain separate

Each component has a limited reason to change.

The API URL may change. That should primarily affect the remote data source.

The storage library may change. That should primarily affect the local data source.

The caching policy may change. That belongs in the repository.

The business concept of Number Trivia may change. That belongs in the domain.

The UI may be redesigned. That should not require rewriting the HTTP client.

This separation is the practical value of the architecture.

## TDD as a design tool

Notice that the tests forced the classes to have clear interfaces.

If a class is difficult to test, that is often evidence that its responsibilities or dependencies are poorly separated.

TDD therefore provides feedback about design quality, not only correctness.

## Summary

The completed data layer provides a controlled boundary between application logic and external systems. Remote access, caching, serialization, exceptions, and network detection remain isolated behind contracts that the domain can use safely.
