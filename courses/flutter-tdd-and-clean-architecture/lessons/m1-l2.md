## What to watch for

Watch how the course begins implementing the innermost part of the architecture. Pay particular attention to the Entity, the repository abstraction, the use case, `Either`, and the way tests are written before implementation.

## Entities

An entity represents a concept that matters to the application's business logic.

For the Number Trivia application, the entity can be thought of as:

```dart
class NumberTrivia {
  final String text;
  final int number;

  const NumberTrivia({
    required this.text,
    required this.number,
  });
}
```

The important property of an entity is not its exact fields. It is that the entity does not care where the data came from.

`NumberTrivia` should not know about JSON, HTTP, SharedPreferences, or Flutter widgets.

## Repository contracts

The domain needs data, but it should not know how that data is obtained.

Therefore, the domain defines an abstraction:

```dart
abstract class NumberTriviaRepository {
  Future<Either<Failure, NumberTrivia>> getConcreteNumberTrivia(
    int number,
  );

  Future<Either<Failure, NumberTrivia>> getRandomNumberTrivia();
}
```

The interface describes the capability the domain requires. A later data-layer class will provide the implementation.

This is dependency inversion in practice: the higher-level code depends on an abstraction instead of a concrete data-access class.

## Either for explicit failure handling

The course uses `Either<Failure, NumberTrivia>` to represent two possible outcomes.

```text
Left  -> failure
Right -> successful NumberTrivia
```

This makes failure part of the method's return contract.

Instead of relying entirely on exceptions, a caller can explicitly process the result:

```dart
final result = await repository.getConcreteNumberTrivia(42);

result.fold(
  (failure) => handleFailure(failure),
  (trivia) => displayTrivia(trivia),
);
```

This is particularly useful at architectural boundaries because callers know that failure is an expected possibility.

## Use cases

A use case represents an action the application can perform.

For example:

```dart
class GetConcreteNumberTrivia {
  final NumberTriviaRepository repository;

  GetConcreteNumberTrivia(this.repository);

  Future<Either<Failure, NumberTrivia>> call(int number) {
    return repository.getConcreteNumberTrivia(number);
  }
}
```

The use case is intentionally small. Its value is architectural: the presentation layer asks for an application operation rather than directly manipulating repositories or data sources.

## TDD

The important sequence is:

```text
Write a failing test
        ↓
Write minimum implementation
        ↓
Make the test pass
        ↓
Refactor safely
```

This is more useful than thinking of TDD as simply "writing lots of tests." The test defines the expected behavior before implementation details are chosen.

## Summary

The domain layer contains entities, abstractions, failures, and use cases. These components form the stable center of the application. They should remain independent of Flutter and external data technologies.
