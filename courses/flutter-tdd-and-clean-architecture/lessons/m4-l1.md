## What to watch for

Focus on how the presentation layer is introduced without allowing the UI to communicate directly with repositories. Pay particular attention to events, states, and input validation.

## Presentation logic

The presentation layer needs a component that translates user actions into application operations and converts results into UI states.

In this course that component is a BLoC.

A simplified flow is:

```text
Widget
   ↓
Event
   ↓
BLoC
   ↓
Use Case
   ↓
Result
   ↓
State
   ↓
Widget
```

The widget does not need to understand repository implementation details.

## Events and states

Events describe things that happened:

```dart
GetTriviaForConcreteNumber
GetTriviaForRandomNumber
```

States describe what the UI should currently represent:

```text
Initial
Loading
Loaded
Error
```

This gives the UI a predictable state model.

## Input conversion

User input arrives as a string because it comes from a text field.

The domain operation may require an integer.

Instead of putting conversion logic inside the widget, the presentation logic can use an input converter:

```dart
final result = inputConverter.stringToUnsignedInteger(input);
```

Invalid input becomes a controlled failure rather than an unexpected exception.

## Why validate before calling the use case?

Presentation-specific validation belongs near presentation input handling.

If the user enters:

```text
"abc"
```

the BLoC can detect that this cannot represent the required number before asking the domain to retrieve trivia.

This keeps invalid UI input from unnecessarily reaching lower layers.

## Summary

BLoC becomes the bridge between UI events and application use cases. Input conversion prevents presentation concerns from leaking into the domain, while states give widgets a predictable way to render application progress.
