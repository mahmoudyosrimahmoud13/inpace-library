## What to watch for

Focus on how local persistence is introduced without changing the domain layer. Pay attention to serialization, cache behavior, and testing storage through a mocked dependency.

## Why cache locally?

The application should still be useful when the network is unavailable.

A local data source can store the latest successful trivia:

```text
Remote API
    ↓
Repository
    ↓
Local Data Source
    ↓
Cached JSON
```

Later, when the device is offline:

```text
Repository
    ↓
Local Data Source
    ↓
Cached Model
```

## Serialization

SharedPreferences stores primitive values rather than arbitrary Dart objects. Therefore, the model must be converted into a serializable representation.

For example:

```dart
final jsonString = json.encode(trivia.toJson());
await sharedPreferences.setString(
  cachedKey,
  jsonString,
);
```

Reading reverses the process:

```dart
final jsonString = sharedPreferences.getString(cachedKey);

final jsonMap = json.decode(jsonString!);

return NumberTriviaModel.fromJson(jsonMap);
```

The serialization logic belongs in the model/data boundary.

## Cache failures

A cache miss is different from a successful lookup.

If there is no cached value, the data source should communicate that clearly, usually through a `CacheException` in the architecture used by the course.

The repository can then convert that infrastructure exception into a domain-level `CacheFailure`.

## TDD for persistence

Do not test the real user's persistent storage when unit-testing the data-source behavior.

Instead, mock the storage dependency and verify that the correct key and serialized value are used.

This makes the test fast and predictable.

## Summary

The local data source isolates persistence details. Models handle serialization, the data source handles storage operations, and the repository decides when cached data should be used.
