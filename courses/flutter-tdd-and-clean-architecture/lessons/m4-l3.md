## What to watch for

Focus on completing both concrete and random trivia flows and on keeping event handling consistent. Notice how tests protect behavior while the implementation becomes more complete.

## Handling multiple events

The BLoC now needs to handle different event types.

One event carries a number:

```dart
GetTriviaForConcreteNumber(42)
```

Another requires no number:

```dart
GetTriviaForRandomNumber()
```

Both should produce predictable state transitions.

## The concrete-number flow

A typical flow is:

```text
Event arrives
    ↓
Emit Loading
    ↓
Convert input
    ↓
If invalid → Error
    ↓
Call use case
    ↓
Failure → Error
Success → Loaded
```

Notice that validation occurs before the data operation.

## The random flow

The random operation does not need input conversion:

```text
Random event
    ↓
Loading
    ↓
Random use case
    ↓
Failure → Error
Success → Loaded
```

The shared state model keeps the UI simple even though the events have different requirements.

## Avoiding UI complexity

A poorly designed widget might contain:

```text
validation
HTTP calls
cache logic
error conversion
loading flags
business decisions
```

With BLoC and Clean Architecture, the widget mainly renders state and dispatches events.

## Test coverage

Useful BLoC tests include:

- initial state;
- loading state;
- invalid input;
- successful concrete trivia;
- failed concrete trivia;
- successful random trivia;
- failed random trivia.

These tests describe the externally observable behavior of the presentation logic.

## Summary

The completed BLoC converts user actions into use-case calls and converts use-case results into predictable UI states. The presentation layer is now separated from both the domain implementation and the external data infrastructure.
