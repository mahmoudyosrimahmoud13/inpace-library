# Start here

This course follows **Designing Data-Intensive Applications** by Martin Kleppmann (O'Reilly, 2017), chapter by
chapter. It's the book engineers mean when they say "read DDIA": how databases store and find data, how they
replicate and partition it across machines, what transactions really promise, why distributed systems fail in strange
ways, and how batch and stream processing fit together.

The book explains how things work inside. The best way to understand how something works is to build it. So **every
day ends with a project in which you build a small working version** of what you just read about:

| You read about | You build |
|---|---|
| Load and response times | Twitter's timeline problem, and percentiles with tail latency amplification |
| Data models | The same data as relational tables, JSON documents and a graph with a recursive query |
| Storage engines | A log-structured key-value store with a hash index, crash recovery and compaction; then an LSM-tree with SSTables, Bloom filters and a sparse index |
| Column storage | A row store against a column store, bitmaps, run-length encoding, a data cube |
| Encoding | Your own Protocol Buffers- and Avro-style binary encodings, and schema evolution |
| Replication | Leaders and followers with replication lag, failover, leaderless quorums |
| Partitioning | Hot spots, rebalancing, local and global secondary indexes |
| Transactions | A multi-version store with read committed, snapshot isolation and serializable |
| Distributed trouble | Timeouts, clock skew losing writes, and fencing tokens |
| Consensus | Linearizability, Lamport clocks, two-phase commit, leader election by majority |
| Batch and streams | MapReduce with real parallel processes and joins; a partitioned log with offsets and CDC |
| The future | An "unbundled database": an event log and views you can rebuild and audit |

Every project uses **only Python's standard library**: no installs, no servers, no cloud account. They're small
(100 to 250 lines each), so you can read every line.

## First, get the book

The book is **not inside this course**. Each **Read** lesson opens the right pages of *your own copy*. Buy it from
[O'Reilly](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/) or any
bookshop; many companies and universities give free access through the O'Reilly learning platform.

If you have the PDF: on this course's page, in the box **"This course reads a book you get yourself"**, press **Find it
for me**. inPace looks in your Downloads, Documents and Desktop folders and recognizes the book by its title and number
of pages. If it's somewhere else, choose the folder or the file yourself.

The course expects the 613-page PDF of the first edition. A second edition was in progress when this course was
written; if inPace warns that the page count is different, you have another edition, and the lessons may open other
pages. Trust the chapter and section names in each lesson's title.

## Before you start

- **Python**: classes, dictionaries, files. You'll read more code than you write.
- **SQL**: basic `SELECT` and `JOIN`.
- Some experience building or using a web application helps: the book is written for engineers who've seen a
  database or two in production.

Not there yet? The library has *Python: the full course* and *PostgreSQL for Beginners*.

## How each module works

- **Read** lessons open the book at the right pages, with notes: what to look for, what you can skim.
- **Concept** lessons explain the chapter's hardest ideas again in plain words, with diagrams and tables.
- **Project** lessons show the code with the Copy button, explain it, and show its real output. Every script was run
  before publishing.
- Each module has a **quiz** (pass with 70% to open the next one). Questions can have **more than one right answer**,
  so read every option. There's also a **task** to hand in (always the project, extended) and a short **explanation
  in your own words**.
