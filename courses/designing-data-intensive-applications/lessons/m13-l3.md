# Project 13: a partitioned log, CDC, and a stream-table join

You'll build a small Kafka-like log with partitions and consumer offsets, crash a consumer and count the duplicates,
compare dual writes with change data capture, and join clicks with a changing table.

The code is above this text. Save it as `p13_streams.py`.

## Read the code

- **`Topic`** keeps one append-only file per partition (`p0.log`, `p1.log`, `p2.log`). `produce()` picks the
  partition with `crc32(key) % 3`. A message's **offset** is its line number.
- **`Consumer`** reads each partition from its committed offset, calls `handle()` for each message, and **commits
  offsets only at the end**, to `offsets-<group>.json`. `crash_after` stops it early without committing, like a
  process killed halfway.
- **Part A**: 3,000 page views keyed by user. The naive consumer counts them, crashes after 1,200 messages, and
  restarts. The second consumer **remembers message IDs** (`seq`) and applies each only once.
- **Part B**: 1,000 races between two writes to the same item. With dual writes, each system receives them in its own
  random order. With CDC, the index applies the database's own changelog, in that order.
- **Part C**: a profile changelog (user 7 moves to Morocco at second 95) and 60 clicks over three minutes. Before
  handling each click, the processor applies every profile change up to that click's time, then counts the click in
  a **1-minute tumbling window** under the user's country at that moment.

## Run it

```bash
python p13_streams.py
```

The real output:

```text
A. A topic with 3 partitions; a consumer counts page views and crashes once
   messages per partition: [1045, 1102, 853] (each user's events land in one partition, in order)
   first run : crashed
   restart   : ok
   naive count = 4,200 for 3,000 events: the 1,200 processed before the crash were counted twice
   idempotent count = 3,000: duplicates delivered, but applied once

B. Keeping a search index in sync with a database
   dual writes: database and index disagree in 484 of 1000 races, and nothing ever fixes it
   change data capture: they disagree in 0 of 1000 races

C. Clicks per country per minute: a stream-table join and a tumbling window
   minute 0: {'Egypt': 7, 'Kenya': 9}
   minute 1: {'Egypt': 8, 'Kenya': 6, 'Morocco': 2}
   minute 2: {'Egypt': 12, 'Kenya': 5, 'Morocco': 11}
   user 7 moved to Morocco at second 95: earlier clicks stay with Egypt, later ones go to Morocco.
```

What it shows:

- Each user's events land in one partition, so they stay in order per user.
- After the crash the naive consumer counted **4,200** events for 3,000: at-least-once delivery. The idempotent one
  counted exactly 3,000.
- Dual writes left the database and the index disagreeing in about half of the races; CDC in none.
- Clicks by user 7 count for Egypt before second 95 and for Morocco after it.

## Make it yours

1. **Consumer groups.** Run two consumers in the same group, each owning some partitions. What happens to the
   order of one user's events? And if you assign partitions randomly per message instead?
2. **Log compaction.** Write a `compact(partition)` that keeps only the latest message per key (like project 3's
   compaction). Use it to give a new consumer the current state of every user without replaying everything.
3. **Late events.** Add clicks that arrive late (with an event time in the previous minute). Decide on a watermark,
   and either update the closed window or count the late events separately.
4. Turn part B into **event sourcing**: store the client's *intent* (`"set price to 12"`) in the log, and build both
   the "database" and the "index" from it.

## What to take away

- A partitioned log with offsets is simple, durable and replayable.
- Restarted consumers repeat work; idempotence makes that harmless.
- Change data capture keeps derived systems consistent where dual writes can't.
