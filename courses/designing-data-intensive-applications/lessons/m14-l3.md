# Project 14: an unbundled database for a payments app

The final project puts Chapter 12's ideas together in one small system, **Nilepay**: an event log as the source of
truth, derived views, end-to-end duplicate suppression, a view added later by replay, and an audit that catches
corruption.

The code is above this text. Save it as `p14_unbundled.py`.

## Read the code

- **`client_requests()`** generates 2,000 transfers between 50 accounts. Each has a **request ID** made by the client
  (a UUID). About 15% of requests are retried, with the **same** ID, as if the network had timed out.
- **`EventLog.append_once()`** appends a transfer to `transfers.log` only if its request ID isn't already there:
  duplicate suppression at the point where events enter the system.
- **`View`** is the base of every derived view: `catch_up()` replays the log from the view's own `offset` and calls
  `apply()` for each event.
- Four views: **`Balances`** (debit one account, credit the other), **`Search`** (an inverted index from words in the
  note to request IDs), **`Daily`** (totals per day), and **`FraudAlerts`**, which is created **after** the others and
  built by replaying the whole history.
- The **audit** builds a fresh `Balances` from the log and compares it with the live one, after a bug corrupts one
  balance on purpose.

## Run it

```bash
python p14_unbundled.py
```

The real output:

```text
1. 2,337 requests received (including client retries), 2,000 transfers recorded once each
2. Views built from the log: 50 balances (they sum to 0: money is neither created nor lost), 11 search words, daily totals {1: 84360, 2: 81835, 3: 75225, 4: 76065, 5: 69740, 6: 63325, 7: 73845}
   search 'school' -> 235 transfers
3. New fraud view built by replaying 2,000 events: 219 alerts, e.g. acct-009 sent 950 on day 5 (total 3885)
4. 300 more transfers: every view caught up from its own offset (2,300 events)
5. Audit: recomputed every balance from the log; mismatches: {'acct-007': (-4545, -5045)}
   fixed by rebuilding the view from the log. The log is the truth; views are disposable.
```

What it shows:

1. Over 300 retries arrived, and each transfer was recorded **once**.
2. The balances sum to exactly 0: every debit has its credit, so no money was created or lost.
3. The fraud view, added later, saw the full history with no migration.
4. New traffic flows to every view from its own offset.
5. The audit found the corrupted balance, and the fix was to throw the view away and rebuild it.

## Make it yours

1. **Overdrafts.** Reject transfers that would make a balance negative. Where must that check happen so two
   concurrent transfers can't both pass it? (Hint: in the single ordered step that appends to the log, not in a view.)
2. **Persist offsets.** Save each view's state and offset to disk, kill the process, and restart. Each view should
   continue from where it stopped.
3. **Partition the log** by account, as in project 13. A transfer touches two accounts: how do you keep each
   partition's view correct? Read the book's *Multi-partition request processing* for the answer and implement it.
4. Add a **"right to be forgotten"** request: remove a person's notes from every view. What would you do about the
   immutable log? (Read the book's *Limitations of immutability*.)

## What to take away

- One log, many views: add, rebuild and audit freely.
- Request IDs from the client make retries harmless end to end.
- Integrity is verified, not assumed.
