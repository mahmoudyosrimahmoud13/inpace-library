## SSTables and LSM-trees

A **Sorted String Table** is a segment file whose records are **sorted by key**. That small change brings three wins:

1. **Merging** segments is a merge sort, even when files are bigger than memory (Figure 3-4).
2. You no longer need every key in memory: a **sparse index** (Figure 3-5) with one key every few kilobytes is enough;
   scan the small block between two index entries.
3. Blocks can be **compressed** before writing.

**Constructing and maintaining SSTables**: writes go to an in-memory sorted tree, the **memtable**; when it's big
enough, write it out as a new SSTable; reads check the memtable, then the newest SSTable, then older ones; merge and
compact in the background; and keep a **log** on disk so a crash doesn't lose the memtable. This is the
**Log-Structured Merge-Tree** (LSM-tree), used by LevelDB, RocksDB, Cassandra, HBase and Lucene's term dictionary.

**Performance optimizations**: **Bloom filters** to avoid reading SSTables for keys that don't exist, and
**size-tiered** versus **leveled** compaction.

## B-trees

The standard index of almost every relational database since the 1970s. Fixed-size **pages** (usually 4 KB), a root
page, references to child pages by key range (Figure 3-6), **branching factor**, splitting a full page (Figure 3-7).
A B-tree with n keys has depth O(log n); note the example: four levels of 4 KB pages with a branching factor of 500
store up to 256 TB.

**Making B-trees reliable**: they overwrite pages in place, so a crash mid-split can corrupt the tree; hence the
**write-ahead log** (WAL), and **latches** for concurrency. Skim the optimizations.

## Comparing B-trees and LSM-trees

Read this one carefully; it's a classic interview topic. LSM-trees usually write faster and compress better; B-trees
usually read faster and have more predictable performance. Note **write amplification** (one write to the database
causing several writes to disk over time), and the downside of LSM compaction: it can interfere with reads and writes,
and fall behind under heavy write load.

## Other indexing structures

Secondary indexes; storing values within the index (**heap files**, **clustered** and **covering** indexes);
multi-column indexes (concatenated, and multi-dimensional for things like map searches); full-text and fuzzy indexes;
and **keeping everything in memory**, where the speed comes from not having to encode data for disk, not from avoiding
disk reads.

## What to take away

- Sorting segments by key enables sparse indexes, efficient merges and range queries.
- LSM-trees: memtable plus a WAL, flushed to SSTables, merged in the background, with Bloom filters for misses.
- B-trees: fixed pages updated in place, protected by a WAL. Fast reads; LSM-trees often write faster.
