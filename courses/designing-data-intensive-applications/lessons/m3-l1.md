Why should an application developer care how a database stores data? Because you have to choose a storage engine
that fits your workload, and tune it, and you can only do that if you know roughly what it does inside.

## The world's simplest database

Two Bash functions: `db_set` appends `key,value` to a file; `db_get` scans the file for the last line with that key.
Note why the write is so fast (appending is the cheapest write there is) and why the read is so slow (it scans
everything, O(n)). The rest of the chapter is about **indexes**: extra structures that speed up reads, and always slow
down writes a little. That trade-off is why databases don't index everything by default.

## Hash indexes

The simplest index: an in-memory hash map from each key to the **byte offset** of its latest value in the file
(Figure 3-1). This is how **Bitcask** works. Read the details carefully, because you'll build every one of them today:

- **Segments** and **compaction** (Figures 3-2 and 3-3): break the log into files of a fixed size, then rewrite old
  segments keeping only the latest value of each key, merging several segments at once.
- **File format** (binary, length-prefixed), **deleting records** (tombstones), **crash recovery** (rebuild the
  hash maps by reading the segments; Bitcask saves snapshots to speed this up), **partially written records**
  (checksums), and **concurrency control** (one writer thread).
- **Why append-only?** Sequential writes are fast, concurrency and crash recovery are simpler, and merging avoids
  fragmentation.
- **The limits**: all keys must fit in memory, and range queries are not efficient.

## After reading

Without looking back: list the five problems a real log-structured store must solve beyond "append and index", and the
book's answer to each.

## What to take away

- An append-only log makes writes fast; an index makes reads fast; every index costs some write speed.
- A hash index maps keys to byte offsets, and all the keys must fit in memory.
- Segments, compaction, tombstones, recovery and checksums turn a log into a real storage engine.
