# Project 10: timeouts, a clock that loses a write, and fencing tokens

You'll measure the timeout trade-off, reproduce Figure 8-3's lost write, and replay Figure 8-4's broken lock, then fix
it with fencing tokens.

The code is above this text. Save it as `p10_faults.py`.

## Read the code

- **Part A**: `response_ms()` is a healthy node: about 10 ms, and 0.3% of the time a pause of 0.5 to 8 seconds.
  For each timeout, the script counts healthy checks that would be declared dead, and how long a real crash takes to
  notice (the timeout plus, on average, half of a 1-second check interval).
- **Part B**: two writes with real times 1.5 ms apart, stamped by the clocks of nodes whose skew is 2.5 ms; the store
  keeps the write with the larger timestamp (last write wins).
- **Part C**: a `LockService` hands out leases with increasing tokens; a client pauses past its lease, and a second
  client gets the lease. `Storage` either ignores tokens or rejects writes with an older token than it has seen.

## Run it

```bash
python p10_faults.py
```

The real output:

```text
A. Failure detection with a timeout (100,000 health checks of live nodes, plus real crashes)
     timeout   live nodes declared dead   time to notice a real crash
        20 ms          1,337 ( 1.34%)                    520 ms
        50 ms            328 ( 0.33%)                    550 ms
       200 ms            328 ( 0.33%)                    700 ms
      1000 ms            308 ( 0.31%)                  1,500 ms
     10000 ms              0 ( 0.00%)                 10,500 ms
   There's no right answer, only a trade-off between false alarms and slow detection.

B. Last write wins with clocks less than 3 ms apart (the book's Figure 8-3)
   client A writes x = 1        at real time 42.0040 s, stamped 42.0040 s by node 1's clock
   client B writes x += 1 -> 2  at real time 42.0055 s, stamped 42.0030 s by node 3's clock
   stored x = 1: client B's later write was DROPPED because its timestamp looked older,
   and nobody got an error. Clock skew silently decides which write survives.

C. A lease, a 15-second pause, and fencing tokens
   without fencing tokens: client 2 wrote 'file v2' (token 2); client 1 wrote 'file v1' (token 1)
   with fencing tokens: client 2 wrote 'file v2' (token 2); REJECTED client 1 (token 1 < 2)
   Without tokens, the stale client overwrote the newer data. A node can't trust its own sense of time.
```

What it shows:

- A 20 ms timeout declares healthy nodes dead about 1% of the time; even 1 second still catches the long pauses.
  Only a very long timeout avoids false alarms, and then real crashes take seconds to notice.
- The later write (x = 2) was **silently dropped**, exactly as in Figure 8-3.
- Without fencing tokens, the paused client **overwrote newer data**; with them, storage rejected it.

## Make it yours

1. Make pauses more common (0.3% to 3%). Which timeout would you choose now, and why?
2. Replace the timestamps in part B with a **version counter** that each write reads and increments. Does the
   problem go away? What new problem appears if two clients write at the same moment?
3. Implement the **Phi Accrual** idea simply: keep the last 100 response times, and declare a node suspect only if
   the current wait is longer than, say, 5 standard deviations above their mean.
4. Write down three places in a system you know where a process might pause long enough to matter.

## What to take away

- There's no correct timeout, only one that matches measured behaviour and the cost of mistakes.
- Use logical ordering, not wall clocks, to decide which write wins.
- Protect shared resources with fencing tokens; locks alone aren't enough.
