# Read: Part III introduction and Chapter 10, Batch Processing

Part III is about **derived data**: data made from other data (caches, indexes, views, models). Read the short
**Part III introduction**: **systems of record** (the source of truth) versus **derived data systems** (which can be
rebuilt from it). Keep that distinction in mind for the rest of the book.

Then Chapter 10: services (online), batch processing (offline, big jobs on bounded input) and stream processing
(near-real-time, unbounded input).

## Batch processing with Unix tools

- **Simple log analysis**: the famous pipeline `cat | awk | sort | uniq -c | sort -r -n | head -n 5` for the top 5
  pages. Then the same in Ruby with an in-memory hash table, and when **sorting** beats a hash table (when the data
  doesn't fit in memory, sort can spill to disk).
- **The Unix philosophy**: small tools that do one thing, a **uniform interface** (files and pipes), separating logic
  from wiring, and making experiments easy. These ideas come back in MapReduce and stream processing.

## MapReduce and distributed filesystems

- HDFS: a shared-nothing filesystem with replication.
- **MapReduce job execution** (Figure 10-1): map, partition by key, sort, shuffle, reduce. Read how mappers write
  sorted output files per reducer, and how reducers merge them.
- MapReduce **workflows**: chaining jobs.
- **Reduce-side joins and grouping**: the user activity example (Figures 10-2 and 10-3), the **sort-merge join**,
  bringing related data to the same place, GROUP BY, and handling **skew** (hot keys).
- **Map-side joins**: **broadcast hash joins** (a small input in every mapper's memory), **partitioned hash joins**,
  and map-side merge joins; when each applies.
- **The output of batch workflows**: building search indexes, building key-value stores as job output, and the
  philosophy of batch outputs: immutable inputs, rerunnable jobs ("human fault tolerance").
- **Comparing Hadoop to distributed databases** (MPP): diversity of storage and of processing models, designing for
  frequent faults.

## Beyond MapReduce

**Materialization of intermediate state** and why dataflow engines (Spark, Tez, Flink) avoid writing every step to
disk; fault tolerance by recomputation; **graphs and iterative processing** (Pregel); high-level APIs and declarative
query languages.

## After reading

Your job joins 10 billion click events with a 50,000-row table of countries. Which join would you choose, and why?
What if the second table had 500 million users instead?

## What to take away

- Batch jobs read immutable input and produce new output: rerunnable, so mistakes can be fixed.
- MapReduce = map, partition and sort by key, shuffle, reduce; the shuffle is the expensive part.
- Join big with small by broadcasting the small side; join big with big by partitioning both on the key.
