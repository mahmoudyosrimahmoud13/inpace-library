# Read: Chapter 11, Stream Processing

Batch processing assumes the input is finished. Most data never is: events keep arriving. Stream processing is batch
processing on **unbounded** input, done continuously.

## Transmitting event streams

- Producers, consumers and **topics**; what to do when producers are faster than consumers (drop, buffer, apply
  backpressure); what happens when nodes crash.
- **Direct messaging** (UDP multicast, webhooks) versus **message brokers**; brokers compared to databases.
- **Multiple consumers**: load balancing versus fan-out (Figure 11-1); acknowledgments and **redelivery**, and why load
  balancing plus redelivery reorders messages (Figure 11-2).
- **Partitioned logs** (Figure 11-3): the core of Kafka. Each partition is an append-only log; every message has an
  **offset**; consumers remember their offset; reading doesn't delete. Compare logs with traditional messaging,
  **consumer offsets**, disk space (a circular buffer), and **replaying old messages**.

## Databases and streams

- **Keeping systems in sync**: why **dual writes** (the application writing to the database and the search index)
  cause permanent inconsistency (Figure 11-4).
- **Change data capture** (Figure 11-5): make the database's own log the stream that every derived system follows;
  the initial snapshot, **log compaction**, and API support.
- **Event sourcing**: storing the user's actions as immutable events, and deriving current state from them; commands
  versus events.
- **State, streams and immutability**: the current state is the integral of the stream of changes (Figure 11-6);
  advantages of immutable events (auditing, recovering from bugs); deriving several views from one log; limits of
  immutability (deleting data for privacy).

## Processing streams

- Uses: complex event processing, stream analytics, maintaining materialized views, search on streams.
- **Reasoning about time**: event time versus processing time (Figure 11-7), **stragglers** and knowing when a window
  is complete, whose clock to trust, and the window types: **tumbling, hopping, sliding, session**.
- **Stream joins**: stream-stream (click-through rates), **stream-table** (enrich events with a table kept up to date
  from a changelog), table-table (Twitter timelines as a materialized view), and the time-dependence of joins.
- **Fault tolerance**: microbatching and checkpointing, atomic commit revisited, **idempotence**, rebuilding state.

## After reading

An online shop updates its database and its search index from the application code. Describe a sequence of events
that leaves them permanently different, and how CDC prevents it.

## What to take away

- A partitioned log keeps messages after reading them; consumers track offsets and can replay.
- Dual writes race; deriving every system from one ordered log (CDC, event sourcing) converges.
- Stream processing needs event-time windows, joins against changing tables, and idempotence for exactly-once effects.
