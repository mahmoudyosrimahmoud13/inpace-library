# Project 12: MapReduce from scratch, with real parallel processes

You'll analyze a web server log three ways: the Unix way, with your own MapReduce running mappers and reducers as
separate processes, and with two kinds of join.

The code is above this text. Save it as `p12_mapreduce.py`.

## Read the code

- **`make_inputs()`** writes 8 log files of 25,000 lines in the book's log format, plus a `users.jsonl` table with a
  birth year for each of 5,000 users. A few pages are popular, most are rare.
- **Part A** is the Unix pipeline in one line of Python: a `Counter` of the 7th field.
- **`map_task()`** reads one log file and emits `(url, 1)` (or, for the join, `(user_id, ["view", url])`), puts each
  pair in the bucket `crc32(key) % REDUCERS`, sorts each bucket and writes it as one file: `map-access-3-r2.jsonl`
  means "from mapper 3, for reducer 2".
- **`reduce_task()`** collects every mapper's file for its number, merges them with `heapq.merge` (they're already
  sorted), and uses `groupby` to handle one key at a time.
- **`Pool().map()`** runs the 8 map tasks and then the 4 reduce tasks in separate processes, using all your CPU cores.
  (The `if __name__ == "__main__":` line is required on Windows and macOS for this.)
- **Part C**: `map_users()` emits `(user_id, ["user", birth_year])` with the same partitioning, so the reducer for a
  user receives the user's record and all their views together: a **sort-merge join**. `broadcast_map()` instead
  sends the whole users dictionary to every mapper: a **broadcast hash join**.

## Run it

```bash
python p12_mapreduce.py
```

What it shows:

- MapReduce gives **exactly** the Unix answer, and every URL was reduced by exactly one reducer.
- 8 mappers times 4 reducers = 32 shuffle files: that's the shuffle.
- Both joins give the same age breakdown; the broadcast join needed no shuffle at all.

## Make it yours

1. **A combiner.** Make each mapper sum counts per URL before writing (`("/", 3120)` instead of 3,120 `("/", 1)`
   lines). Measure the shuffle files' total size before and after.
2. **Skew.** Make one user produce half of all events. Time the join's reducers separately: which one is slow, and
   why? Read the book's *Handling skew* and implement one fix.
3. **A two-job workflow.** Chain a second MapReduce job that takes the counts and finds the top 5 (hint: one reducer).
4. Compare the run time with `Pool(1)` and with the default number of processes. Why isn't it N times faster?

## What to take away

- Partitioning by key is what lets many reducers work independently and still be correct.
- The shuffle (sorted files per reducer) is the core, and the cost, of MapReduce.
- Pick the join by the sizes of its inputs.
