# Read: Chapter 12, The Future of Data Systems

The last chapter changes tone: from how things are to how the author thinks they should be. Read it as a set of
arguments, and make up your own mind.

## Data integration

- **Combining specialized tools by deriving data**: no single tool does everything, so data flows from a system of
  record into derived systems. Reasoning about dataflows: decide where the **total order** of writes is established,
  and derive everything else from it (via CDC or event sourcing). **Derived data versus distributed transactions**,
  and the limits of total ordering.
- **Batch and stream processing**: maintaining derived state, **reprocessing** data for application evolution
  (migrating to a new schema by deriving a new view alongside the old), and unifying batch and stream (the lambda
  architecture and its simplification).

## Unbundling databases

- **Composing data storage technologies**: a database's internal features (secondary indexes, materialized views,
  replication logs) can be rebuilt across separate systems connected by logs: "unbundling the database". Federated
  databases (unifying reads) versus unbundled databases (unifying writes). Making unbundling work; what's missing.
- **Designing applications around dataflow**: application code as a derivation function; separating application code
  and state; dataflow (the spreadsheet analogy), stream processors and services.
- **Observing derived state**: the write path and the read path; materialized views and caching; stateful,
  offline-capable clients; pushing state changes to clients; end-to-end event streams; reads are events too.

## Aiming for correctness

- **The end-to-end argument for databases**: exactly-once execution of an operation; **duplicate suppression**;
  operation identifiers (a **request ID** made by the client); the **end-to-end argument** (Saltzer, Reed and Clark):
  some guarantees can only be made fully by the endpoints.
- **Enforcing constraints**: uniqueness via a log; multi-partition request processing.
- **Timeliness and integrity**: the difference between them, and why integrity matters more; loosely interpreted
  constraints (apologies instead of coordination); coordination-avoiding data systems.
- **Trust, but verify**: maintaining integrity in the face of software bugs; **auditing**; designing for auditability.

## Doing the right thing

Predictive analytics, bias and discrimination, responsibility and accountability, feedback loops; privacy and
tracking, surveillance, consent, data as assets and power, legislation and self-regulation. Read this part slowly:
it's about the consequences of the systems you'll build.

## After reading

Pick one argument from this chapter you agree with and one you'd push back on. Write a paragraph on each.

## What to take away

- Establish one total order of writes (a log) and derive everything else from it.
- Exactly-once effects need end-to-end request IDs; integrity matters more than timeliness; audit your data.
- The systems you build affect people: design for their privacy and fairness.
