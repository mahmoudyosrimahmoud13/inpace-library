# Project 2: one dataset, three data models

You'll store the same small set of professional profiles three ways, in SQLite (built into Python) and plain JSON, and
see which questions each model makes easy.

The code is above this text. Save it as `p02_data_models.py` in your `lab` folder.

## Read the code

1. **Relational.** Four tables: `regions`, `users` (with a `region_id`), `positions`, `education`. Showing one profile
   needs three joins, and the answer comes back as several rows, one per position, that the application stitches
   back together.
2. **Document.** The same profile as one JSON document with nested lists. Note that the document copies the region's
   **name**. Then the region is renamed: one `UPDATE` in the relational model, and a rewrite of every document that
   copied it.
3. **Graph.** `vertices` and `edges` tables (a property graph stored in SQL, as in the book's Example 2-2) with
   locations nested by `within` edges and people with `born_in` and `lives_in` edges. The recursive query from the
   book's Example 2-5 finds everyone born in the United States who lives in Europe. `path_up()` does the same walk in
   plain Python.
4. **Schema on write versus on read.** The app wants first names. The relational way migrates every row once. The
   document way leaves old documents alone, and `first_name()` must handle both shapes, forever.

## Run it

```bash
python p02_data_models.py
```

The real output:

```text
1. Relational: profile of user 1 needs 3 joins and comes back as 2 rows to stitch together:
   ('Mona Hassan', 'Greater Cairo', 'Data engineer', 'Inkwell', 'Cairo University')
   ('Mona Hassan', 'Greater Cairo', 'Analyst', 'Nile Bank', 'Cairo University')

2. Document: the same profile is one read of one JSON document:
   {"user_id": 1, "name": "Mona Hassan", "region": "Greater Cairo", "positions": [{"title": "Data engineer", "company": "Inkwell"}, {"title": "Analyst",  ...
   Renaming a region: relational updates 1 row; documents needed 2 rewrites (and a missed one would disagree forever).

3. Graph: born in the United States, living in Europe: ['Lucy']
   Lucy was born in Idaho (1 'within' step below the US) and lives in London (2 steps below Europe).
   The query doesn't know the depth in advance: that's what recursive queries and graph languages are for.
   Walk from Idaho: Idaho -> United States -> North America

4. Schema on write: ['Mona', 'Omar', 'Laila']
   Schema on read:  ['Mona', 'Omar', 'Laila', 'Sara']
```

Only Lucy matches: she was born in Idaho, inside the United States, and lives in London, inside the United Kingdom,
inside Europe. Alain lives in London but was born in France; Sam was born in the US but lives in Cairo.

## Make it yours

1. Add a vertex for Boise, `within` Idaho, and a person born there who lives in Paris (add Paris `within` France).
   Run the graph query again without changing it. Who's found now, and why didn't the query need to change?
2. Write the reverse question: everyone born in **Africa** who lives in **Europe**.
3. Add a `recommendations` relationship to the relational model: users recommend other users (many-to-many). What
   table do you need? How would you store it in the document model, and what goes wrong when a user is deleted?

## What to take away

- The same data favours different questions in different models.
- Copying many-to-one data into documents makes updates a hunt.
- Recursive queries handle paths of unknown length, the heart of graph queries.
