# Project 11: linearizability, Lamport clocks, 2PC and leader election

You'll replay four of Chapter 9's ideas as small simulations: a non-linearizable read, Lamport timestamps, a blocked
two-phase commit, and a Raft-style leader election with a network partition.

The code is above this text. Save it as `p11_consensus.py`.

## Read the code

- **Part A** recreates Figure 9-1 with a leader and a lagging follower.
- **Part B**: `Node` keeps a Lamport counter; `local()` increments it; `receive()` first jumps to the larger of its own
  and the message's counter. The operations are then sorted by `(counter, node id)`.
- **Part C**: three participants vote "yes" (prepared, holding locks); the coordinator dies before phase 2, so
  nothing moves them out of "prepared".
- **Part D**: `election()` runs terms. In each term, the nodes allowed to run draw a random timeout (150 to 300 ms, as
  Raft does); the first, and a second if it times out within 15 ms, become candidates. Each voter grants **one vote
  per term**, to the first request that reaches it (a candidate votes for itself). A candidate needs votes from a
  majority of **all** nodes, not just the ones it can reach. Then a partition: only nodes on the same side can talk.

## Run it

```bash
python p11_consensus.py
```

The real output:

```text
A. Linearizability: the final score
   Alice reads '2-1, FINAL', tells Bob; Bob reads '1-1, playing' AFTER that
   Not linearizable: once anyone has seen the new value, every later read must see it too.

B. Lamport timestamps on three nodes
   (1, node 1)  A: create username 'mona'
   (1, node 3)  C: create username 'mona'
   (2, node 1)  A tells B about it
   (2, node 3)  C: another edit
   (3, node 2)  B: reads A's message, then edits
   The order is total and respects 'A told B'. A's 'mona' sorts before C's, so A wins, but node C couldn't
   know that when its user clicked 'create': it hadn't heard from A yet. Deciding NOW needs consensus.

C. Two-phase commit with a coordinator crash
   after the crash: {'orders db': 'prepared (voted yes, holding locks)', 'payments db': 'prepared (voted yes, holding locks)', 'stock db': 'prepared (voted yes, holding locks)'}
   They can't commit (maybe someone voted no) or abort (maybe the coordinator already told someone to
   commit). They wait, with rows locked, until the coordinator recovers and reads its log.

D. Leader election, 5 nodes (a majority is 3)
   all connected: term 1: node 1: 3 votes, node 4: 2 votes -> node 1 is LEADER
   partition, minority side {1, 2}:
      term 1: node 2: 2 votes -> no majority, new term with new random timeouts
      term 2: node 2: 2 votes -> no majority, new term with new random timeouts
      term 3: node 2: 2 votes -> no majority, new term with new random timeouts
   no leader after 3 terms
   partition, majority side {3, 4, 5}:
   term 1: node 4: 3 votes -> node 4 is LEADER
   At most one side can hold a majority, so there can never be two leaders in the same term.
```

What it shows:

- Bob's read happened after Alice's, and saw an older value: not linearizable.
- The Lamport order is total, puts node 1's 'mona' first, and respects "A told B". Node 3 only learns it lost later.
- After the coordinator crash, every participant is stuck "prepared", holding locks.
- Fully connected, one candidate wins. In a partition, the side with 2 nodes tries term after term and never gets 3
  votes; the side with 3 elects a leader in one term.

## Make it yours

1. **Split votes.** Allow up to 3 candidates per term (those within 15 ms of the first). Run 1,000 elections and
   count how many terms they need on average. Then widen the timeout range to 150 to 600 ms: what happens and why?
   (This is why Raft randomizes timeouts.)
2. **Terms that only go up.** Give each node a `current_term`, and make a node refuse vote requests from a lower
   term. Bring an old leader back from the minority side and show it can't win.
3. **2PC recovery.** Give the coordinator a log. Write the decision before phase 2, crash, restart from the log, and
   finish the commit.
4. Use Lamport timestamps to add **causal order** to project 7's replication, and detect when a follower applies an
   update before the one it depends on.

## What to take away

- You've seen why linearizability needs more than "eventually consistent" replicas.
- Lamport clocks give a consistent order, too late for on-the-spot decisions.
- Majority votes with terms are the core of consensus: a minority can never decide.
