# Project 8: hot spots, rebalancing, and secondary indexes

You'll measure four partitioning decisions: range versus hash on timestamp keys, two rebalancing strategies, local
versus global secondary indexes, and splitting a hot key.

The code is above this text. Save it as `p08_partitioning.py`.

## Read the code

- **`h()`** turns a key into a big integer with MD5. (Python's own `hash()` of a string changes between runs, so it's
  no use for partitioning.)
- **Part A**: 100,000 sensor readings all from the last hour of a day, keyed by timestamp. `by_range()` places them in
  four 6-hour ranges; `h(k) % 4` hashes them.
- **Part B**: 100,000 user keys. **Hash mod N** compares each key's node with 4 nodes and with 5. **Fixed partitions**:
  256 partitions assigned round-robin to 4 nodes; the new node 4 then takes partitions from the others until it has
  its fair share (256 / 5 = 51). Keys never change partition, so a key moves only if its partition does.
- **Part C**: 20,000 cars with a colour, on 8 partitions. The local index is one small index per partition; the global
  index is one index partitioned by colour.
- **Part D**: 50,000 likes on one post, with and without a two-digit random suffix on the key.

## Run it

```bash
python p08_partitioning.py
```

The real output:

```text
A. 100,000 sensor readings written during the last hour, 4 partitions
   key range: [0, 0, 0, 100000] <- one partition takes every write
   hash     : [25331, 23736, 26039, 24894] <- even, but 'all readings from 23:00 to 23:10'
              now has to ask all 4 partitions

B. Adding a 5th node to 4: how many of 100,000 keys must move?
   hash mod N        : 79,942 keys move (80%)
   256 fixed partitions: 19,968 keys move (20%), in 51 whole partitions

C. Secondary index on car colour, 8 partitions, 20,000 cars
   local index : 'find red cars' asks 8 of 8 partitions (scatter/gather; the slowest one decides)
   global index: 'find red cars' asks 1 partition (the one that holds the term 'red', h % P = 2)
   but writing one new red car touches partition 1 (the car) AND partition 2 (the index): usually updated asynchronously, so the index can lag

D. A celebrity's post gets 50,000 likes in a minute, 16 partitions
   one key      : busiest partition takes 50,000 writes
   key + suffix : busiest partition takes 5,507 writes, but counting the likes now reads 100 keys
```

What it shows:

- **Range partitioning on time puts every write on one partition**; hashing spreads them evenly, at the cost of range
  queries.
- **Hash mod N moves 80% of the keys** when one node is added; fixed partitions move 20%, in whole partitions.
- The local index must ask all 8 partitions for "red cars"; the global index asks 1, but a write touches 2.
- A random suffix cuts the hottest partition's load about tenfold, and every read must now gather 100 keys.

## Make it yours

1. **Compound keys.** Key the readings by `sensor_id:timestamp` with 50 sensors, and partition by the hash of
   `sensor_id` only. Show that writes are spread, and that one sensor's readings for an hour are on a single partition.
2. Grow from 4 to 8 nodes, one at a time, with both strategies. Total how many keys moved overall.
3. Implement **consistent hashing** with a ring of 100 virtual points per node, and compare how many keys move when a
   node is added.
4. Make a "trending" key hot only for one minute. Design (in words) how a system would detect it and split it
   automatically, and what reads would need to know.

## What to take away

- Measure partition balance with your real key distribution; time-ordered keys are the classic trap.
- Many fixed partitions make adding nodes cheap.
- There's no free index: local indexes cost reads, global indexes cost writes and freshness.
