# Project 7: replication, simulated

You'll simulate a leader with two followers, measure how often replication lag breaks users' expectations, lose
acknowledged writes in a failover, and compare leaderless quorum settings.

The code is above this text. Save it as `p07_replication.py`.

## Read the code

The simulation uses a **simulated clock**: times are numbers in milliseconds, so every run gives the same results.

- **`Replica`** applies the leader's log **in order**. Messages that arrive early wait in `pending` until every earlier
  position has arrived. Real replication logs work this way, and it's why one slow message delays everything behind it.
- **`LeaderFollower.write()`** applies the write on the leader and puts one message per follower "in flight", arriving
  after `2 + expovariate(1/30)` ms: usually 10 to 50 ms, sometimes 150 ms or more. **`tick()`** delivers everything due.
- **Part A**: 1,000 users write their profile and read it back 100 ms later from a random follower. The fix reads from
  the leader. Then each user reads a frequently updated counter twice, 20 ms apart: from random followers, or always
  from **their own** follower (`u % 2`).
- **Part B**: 500 writes 2 ms apart; then the leader "dies" and the most up-to-date follower is promoted.
- **Part C**: n = 3 replicas, each write reaches only w of them, each read asks r and keeps the highest version. Then a
  small read repair example.

## Run it

```bash
python p07_replication.py
```

The real output:

```text
A. Asynchronous leader-follower replication, 1,000 users each write then read 100 ms later
   read-after-write violated:    59 of 1000 reads (any follower)   -> 0 when users read their own recent writes from the leader
   monotonic reads violated:     18 of 1000 read pairs (random followers) -> 0 when each user sticks to one follower

B. Failover with asynchronous replication
   the old leader had 500 writes; the best follower had 457
   promoting it LOSES 43 acknowledged writes (users were told 'paid'). Synchronous or
   semi-synchronous replication, or a consensus protocol, is what prevents this.

C. Leaderless replication with quorums, n = 3
   w=1, r=1  (w + r <= n): stale reads 1333 of 2000
   w=2, r=2  (w + r > n): stale reads    0 of 2000
   w=3, r=1  (w + r > n): stale reads    0 of 2000
   Read repair: a read that sees an old version on a replica writes the new one back
   read returned '2 books'; replica 0 repaired; replica 2 still stale until anti-entropy: ['2 books', '2 books', '1 book']
```

What it shows:

- Even with a typical lag of 30 ms, **about 6% of users** reading 100 ms after their own write see the old value.
  Reading your own recent writes from the leader fixes it completely.
- Random followers make time go backwards for some users; a fixed follower per user never does.
- A failover after a burst of writes **loses dozens of acknowledged writes**.
- Quorums: w = r = 1 returns a stale value most of the time; w + r > n never did in this simulation.

## Make it yours

1. Change `mean_lag_ms` to 5 and to 200, and the read delay from 100 ms to 1,000 ms. Plot (or tabulate) violations
   against lag.
2. Make follower-1 **synchronous**: the leader acknowledges only after follower-1 has the write. Rerun part B and
   promote follower-1. How many writes are lost now, and what did each write cost in latency?
3. **Consistent prefix reads**: simulate a question and its answer written to two partitions with different lags, and
   count how often an observer sees the answer first.
4. In part C, make one replica **down** for the first 1,000 writes (never written to), then back. With w = 2, r = 2,
   are reads still fresh? Add read repair and count how many of its keys get fixed by reads alone.

## What to take away

- Lag is usually small and occasionally large, and the occasional case is what users notice.
- Simple routing rules (leader for recent writers, sticky followers) restore the guarantees users expect.
- Asynchronous replication plus failover can lose data that users were told was saved.
