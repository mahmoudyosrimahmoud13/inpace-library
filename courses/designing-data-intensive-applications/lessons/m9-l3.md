# Project 9: a multi-version store with three isolation levels

You'll build a tiny MVCC key-value store, about 50 lines, with read committed, snapshot isolation and serializable
snapshot isolation, and replay the book's three anomalies step by step.

The code is above this text. Save it as `p09_transactions.py`.

## Read the code

- **`MVCC.versions`** keeps, for each key, a list of `(commit timestamp, value)`. `clock` is the last commit timestamp.
- **`Tx`** starts with `start = db.clock`: its snapshot. Writes go into `self.writes` (a private buffer) until commit;
  `self.reads` records every key read.
- **`read()`**: a transaction always sees its own writes. Under **read committed** it returns the newest committed
  version; otherwise the newest version committed **at or before its start**.
- **`commit()`**: `changed` is the set of keys with a version committed after my start.
  - **Snapshot isolation**: if I wrote any of them, abort (first committer wins).
  - **Serializable**: also abort if I **read** any of them: my decision was based on stale data.
  - Otherwise, take the next timestamp and add my writes as new versions.
- **`run()`** executes a script of steps from named transactions in the exact interleaving given; a transaction begins
  at its first step. An `Abort` is printed, and the transaction's remaining steps are skipped.
- The three scenarios replay Figures 7-6 (Alice's accounts), 7-1 (two increments) and 7-8 (doctors on call).
  `lost_update()` retries an aborted transaction, as an application would.

## Run it

```bash
python p09_transactions.py
```

The real output:

```text
1. Read skew: Alice reads her two accounts while 100 moves between them
   read committed    : Alice sees 500 + 400 = 900   <- 100 vanished!
   snapshot isolation: Alice sees 500 + 500 = 1000

2. Lost update: two transactions increment the same counter at the same time
   read committed    : two increments -> counter = 1   <- one increment LOST
      B ABORTED: write-write conflict on ['counter']
   snapshot isolation: two increments -> counter = 2 (after 1 retry)

3. Write skew: Alice and Bob both feel unwell and check 'is someone else on call?'
   snapshot isolation: doctors still on call = 0   <- nobody! write skew
      Bob ABORTED: something I read changed: ['alice_on_call']
   serializable      : doctors still on call = 1
```

Each line matches the summary table in the concept lesson: read committed shows read skew and loses an update;
snapshot isolation fixes both (B is aborted and retried); snapshot isolation still lets both doctors go home;
serializable aborts Bob because something he read had changed.

## Make it yours

1. Add **dirty reads**: a level `read uncommitted` that also sees other transactions' uncommitted writes (you'll need
   a shared place for pending writes). Show Alice seeing a transfer that later aborts.
2. **Phantoms.** Add a meeting-room booking scenario: two transactions check "no bookings for room 1 at 12:00", then
   each **inserts** a new booking key. Does your serializable level catch it? Why not, and what would you need to track
   (hint: the *range* that was searched, not only the keys that were read)?
3. **Too many aborts?** Run 1,000 random transactions, each reading 3 and writing 1 of 20 keys, interleaved in pairs.
   Count aborts under snapshot isolation and serializable. That's the price of optimistic concurrency.
4. Implement **actual serial execution**: one queue, one transaction at a time. Show all three anomalies disappear,
   and explain what you gave up.

## What to take away

- MVCC is a list of versions per key and a rule about which one a transaction may see.
- Snapshot isolation detects write-write conflicts; SSI also detects read-write ones.
- You've seen every anomaly happen, so you'll recognize them in production.
