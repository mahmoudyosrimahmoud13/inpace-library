## OLTP versus OLAP

Read Table 3-1 slowly. Online transaction processing (many small reads and writes of a few records, by key, from users)
and online analytic processing (few huge queries that scan millions of rows and aggregate a few columns, from
analysts) want very different storage.

## Data warehousing

Why companies copy data out of OLTP systems into a separate **data warehouse** (Figure 3-8: extract, transform,
load), and how warehouse engines differ from OLTP ones even when both speak SQL.

## Stars and snowflakes

The **star schema** (Figure 3-9): a central **fact table** (one row per event, such as a sale) with foreign keys to
**dimension tables** (who, what, where, when). Fact tables are huge, and often wider than 100 columns. Snowflake
schemas break dimensions down further.

## Column-oriented storage

The core idea (Figure 3-10): store all values of one **column** together, instead of all values of one **row**
together. A query that uses 4 of 100 columns reads 4% of the data.

- **Column compression**: **bitmap encoding** (Figure 3-11), one bitmap per distinct value, run-length encoded when
  sparse; why bitwise AND/OR on bitmaps answers `WHERE ... IN (...)` fast; and **vectorized processing**.
- **Sort order in column storage**: the whole row order is one choice for all columns; sorting by the most-queried
  column groups equal values together, which compresses extremely well with run-length encoding. Note Vertica's
  trick of storing the same data **sorted several ways**.
- **Writing to column-oriented storage**: why in-place updates are hard, and why LSM-tree-style write buffering fits.
- **Aggregation: data cubes and materialized views** (Figure 3-12): precomputed totals. Fast for the questions they
  were built for, useless for others.

## After reading

A table has columns `date, product, store, customer, quantity, price`. Which column would you sort by, and why? Which

## What to take away

- OLTP reads few rows by key; OLAP scans many rows and few columns. Different engines suit each.
- Column storage reads only the columns a query needs, and compresses them well.
- Sort order and data cubes are trade-offs: they speed up some queries and not others.
