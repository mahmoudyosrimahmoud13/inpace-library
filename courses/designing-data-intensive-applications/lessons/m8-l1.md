# Read: Chapter 6, Partitioning

When data or query load is too big for one machine, split it into **partitions** (also called shards, regions,
tablets, vnodes or vBuckets depending on the database). A short chapter; read all of it.

## Partitioning and replication

Each partition is usually replicated too, so one node holds several partitions, some as leader and some as follower
(Figure 6-1).

## Partitioning of key-value data

The goal: spread data and load evenly, avoiding **skew** and **hot spots**.

- **By key range** (Figure 6-2): like volumes of an encyclopedia. Range scans are efficient; the boundaries must
  follow the data. Read the **sensor data** example: keys that start with a timestamp send all of today's writes to
  one partition. The fix: prefix the key with something else, such as the sensor name.
- **By hash of key** (Figure 6-3): even spread, but range queries must ask every partition. Note the comment on
  **consistent hashing** and why the term is confusing. Cassandra's compromise: a **compound primary key**, hashing
  only the first part.
- **Skewed workloads and relieving hot spots**: the celebrity problem, and adding a random number to a hot key, with
  the cost on reads.

## Partitioning and secondary indexes

- **By document** (local index, Figure 6-4): each partition indexes only its own documents, so a query by the
  secondary index must ask **all** partitions: **scatter/gather**, prone to tail latency amplification.
- **By term** (global index, Figure 6-5): the index itself is partitioned by the indexed value. Reads ask one
  partition; writes may touch several, and global indexes are often updated **asynchronously**.

## Rebalancing partitions

Why **hash mod N** is a bad idea, then the strategies: a **fixed number of partitions** (Figure 6-6: many more
partitions than nodes; move whole partitions), **dynamic partitioning** (split and merge by size), and partitioning
**proportionally to nodes**. Then automatic versus manual rebalancing, and why fully automatic rebalancing plus
automatic failure detection can be dangerous.

## Request routing

How a client finds the right node (Figure 6-7): any node forwards, a routing tier, or partition-aware clients; and how

## After reading

## What to take away

- Key ranges keep order and risk hot spots; hashes spread load and lose order.
- Local secondary indexes are cheap to write and expensive to read; global ones the opposite.
- Never rebalance by hash mod N; use many fixed partitions or dynamic splitting.
