# Project 5: a row store against a column store

You'll build a million-row fact table, like the book's sales example, store it as rows and as columns, and measure
the analytics question both ways. Then bitmaps, run-length encoding and a data cube.

The code is above this text. Save it as `p05_columns.py`.

## Read the code

- **`data`** holds the column store: one `array` per column (an array of machine integers or floats, much like a
  column file). `date_key` is **sorted**, as if the table were stored in date order.
- **The row store** packs every row into 40 bytes with `struct` (6 integers and 2 doubles) in one `bytearray`.
  Answering the question means decoding all 8 fields of every row.
- **The column store** answer walks only `product_sk` and `quantity` side by side with `zip`.
- **Bitmaps**: one `bytearray` with a bit per row for each wanted product, then a bytewise OR of the three.
- **`rle()`** run-length encodes a column; then `zlib` compresses three columns to show how much sort order matters.
- **The data cube** is a `Counter` keyed by (date, product).

The script prints "Making 1,000,000 sales..." first: building the data takes a few seconds.

## Run it

```bash
python p05_columns.py
```

The real output:

```text
Making 1,000,000 sales...

Quantity of products 30, 68, 69: 44,871
  row store   : read   40.0 MB  in    122 ms
  column store: read    8.0 MB  in     45 ms

Bitmap encoding: product IN (30, 68, 69) = bitwise OR of 3 bitmaps of 125 KB each -> 14,969 matching rows

Run-length encoding (value, how many times in a row):
  date_key   (sorted)  : 1,000,000 values -> 265 runs   e.g. [(140101, 3761), (140102, 3794)]
  product_sk (unsorted): 1,000,000 values -> 994,933 runs   (almost no gain)
  zlib on date_key    :  4,000 KB ->      5 KB
  zlib on product_sk  :  4,000 KB ->  1,321 KB
  zlib on customer_sk :  4,000 KB ->  2,682 KB

Data cube by (date, product): 53,000 cells instead of 1,000,000 rows, built once in 291 ms
  the same question from the cube: 2.8 ms. But a question about stores can't be answered from it.
```

What it shows:

- The column store reads **a fifth of the bytes** (8 MB against 40 MB) and answers about **3 times faster**, even in
  plain Python. In a real engine, with compressed columns and vectorized processing, the gap is much bigger.
- Bitmaps: three bitmaps of 125 KB each, one OR, and the matching rows are known.
- The **sorted** date column collapses to 265 runs and compresses about 800 times. The unsorted product column barely
  has runs; the random customer column barely compresses.
- The data cube answers in a couple of milliseconds, and can't answer anything about stores.

## Make it yours

1. Sort the whole table by `product_sk` instead of `date_key` (sort all columns by the same row order). Which column
   compresses well now? Which query got cheaper?
2. Add a second query: total revenue (`quantity * net_price`) for store 7. Time it on both stores.
3. Build bitmaps for **every** `promotion_sk` value (there are 4). Answer "sales with promotion 1 or 2 for products
   30, 68, 69" with only bitwise operations on bitmaps.
4. Write your conclusion as a short table: query shape, better layout, why.

## What to take away

- Analytics queries touch few columns of many rows: store columns.
- Sort order is a design decision: it decides what compresses and what's fast.
- Precomputed cubes are fast and narrow.
