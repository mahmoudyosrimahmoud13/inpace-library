# Read: Chapter 4, Encoding and Evolution

Applications change, and in a big system old and new versions of the code run at the same time (a rolling upgrade,
or a mobile app users don't update). So data written by new code must be readable by old code, and the other way
round. This chapter is about how encodings make that possible.

Two words to fix before reading: **backward compatibility** (newer code can read data written by older code) and
**forward compatibility** (older code can read data written by newer code). Forward is the harder one.

## Formats for encoding data

- **Language-specific formats** (Java serialization, Python's pickle): why to avoid them (tied to one language,
  security problems when decoding untrusted data, poor versioning, slow).
- **JSON, XML and binary variants**: their problems with numbers, binary strings and schemas. Read **MessagePack**
  encoding Example 4-1 (Figure 4-1): 66 bytes against JSON's 81.
- **Thrift and Protocol Buffers**: a schema with **field tags** (numbers). BinaryProtocol (59 bytes), CompactProtocol
  (34 bytes, Figure 4-3) and Protocol Buffers (33 bytes, Figure 4-4). The key section is **field tags and schema
  evolution**: you can rename a field but never change its tag; new fields must be optional or have a default; old
  code skips tags it doesn't know.
- **Avro**: no tags at all (Figure 4-5, 32 bytes). The **writer's schema and the reader's schema** are resolved by
  field name (Figure 4-6). Rules for evolution: add or remove only fields with a default. Then: how does the reader
  know the writer's schema? (A file header, a version number in a database, a negotiation over a connection.) And why
  Avro suits **dynamically generated schemas** (dumping a database).
- **The merits of schemas**: documentation, compatibility checks, generated code.

## Modes of dataflow

Who encodes and who decodes:

- **Through databases**: "data outlives code"; the danger of old code dropping a field it doesn't know about
  (Figure 4-7).
- **Through services, REST and RPC**: why remote procedure calls are not like local calls (network failures, timeouts,
  retries and idempotence, latency); compatibility across service versions.
- **Message-passing**: message brokers, and distributed **actor** frameworks.

## After reading

You add a field to a message in a running system where some servers have the new code and some the old. Which
compatibility direction does each kind of server need, and what must the new field have?

## What to take away

- Rolling upgrades need both backward and forward compatibility.
- Thrift and Protocol Buffers: field tags never change; new fields are optional.
- Avro: no tags; the reader resolves the writer's schema against its own by name; only fields with defaults can come
  and go.
