# Project 4: build an LSM-tree

You'll build the design used by RocksDB and Cassandra, in about 200 lines: a write-ahead log, a memtable, SSTables
with a sparse index and a Bloom filter each, range queries, and compaction by merge sort.

The code is above this text. Save it as `p04_lsm.py`.

## Read the code

- **`Bloom`**: a `bytearray` of 65,536 bits and 4 positions per key, taken from a SHA-256 hash.
  `might_contain()` returns False only when a bit is clear: then the key is definitely absent.
- **`SSTable`**: a file of JSON lines `[key, value]`, sorted by key. Opening one reads it once to build the
  **sparse index** (every 16th key and its byte offset) and the **Bloom filter**. `get()` checks the Bloom filter,
  finds the block with `bisect`, seeks there and reads at most 16 lines.
- **`LSM.set()`**: append to `wal.log` first, then update the memtable. When the memtable holds 2,000 keys,
  **`flush()`** writes it sorted to a new SSTable and starts a fresh WAL (the flushed data is safe in the SSTable).
- **`LSM.get()`**: memtable, then SSTables from newest to oldest; the first hit wins. A tombstone means "deleted".
- **`range()`**: possible because every file is sorted. (A real engine merges the sorted streams; ours keeps it simple.)
- **`compact()`**: `heapq.merge` merges the sorted SSTables in one pass. Each record is tagged with its table's age, so
  for a repeated key the newest value comes first and older ones are skipped; tombstones are dropped (safe here,
  because we merge **all** tables).
- The stats count block reads, Bloom skips, and bytes written, for **write amplification**.

A note on `tagged()`: an earlier version wrote the streams as a list of generator expressions,
`((k, -i, v) for k, v in t.items()) for i, t in ...`. Python evaluates `i` inside a generator **when it runs**, not
when it's created, so every stream got the last table's age, and compaction kept the wrong values. The assertion after
`compact()` caught it. Keep assertions like that in your own storage code.

## Run it

```bash
python p04_lsm.py
```

The real output:

```text
30,000 writes, 50 deletes -> 11 SSTables on disk + 1542 keys in the memtable
5,000 reads: 3,445 SSTable block reads, 5,046 files skipped by Bloom filters (a skip = no disk read)
1,000 reads of keys that don't exist: 0 block reads (Bloom false positives), 11,000 skips
range query user:01000 .. user:01005 -> [('user:01000', 'last_seen=885159'), ('user:01001', 'last_seen=803505'), ('user:01002', 'last_seen=576108'), ('user:01003', 'last_seen=68978'), ('user:01004', 'last_seen=254215')]
compaction: 11 SSTables -> 1, every answer unchanged
write amplification: 1.73 bytes on disk per byte written before compaction, 1.90 after it
```

What it shows:

- 30,000 writes became a handful of sorted files plus the keys still in memory.
- Reads of existing keys: Bloom filters let most SSTables be skipped without touching the disk.
- Reads of keys that don't exist: **zero** block reads, every file skipped by its Bloom filter.
- A range query works, which the hash index of project 3 couldn't do.
- Compaction merged everything into one file with identical answers. Write amplification went up, because compaction
  rewrote the data: that's the price of keeping reads fast.

## Make it yours

1. Shrink the Bloom filters to 4,096 bits. How many false positives do the 1,000 missing-key reads cause now?
   Calculate bits per key for both sizes.
2. Change `SSTable.EVERY` to 1, 16 and 256. What happens to the size of the sparse index, and to the lines read per
   lookup?
3. **Crash safety.** Write 1,000 keys, then create a new `LSM` object on the same folder *without* flushing. Add a
   `recover()` method that replays `wal.log` into the memtable, and show no write was lost.
4. Implement a real merging `range()` with `heapq.merge`, so it never loads whole files.

## What to take away

- Sorted files make merges, sparse indexes and range queries cheap.
- Bloom filters turn most lookups of missing keys into zero disk reads.
- Compaction buys read speed and space with extra writes.
