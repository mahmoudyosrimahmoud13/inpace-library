# Read: Chapter 7, Transactions

Transactions let an application pretend that some problems (crashes halfway, concurrent users) don't exist. This
chapter explains exactly which problems each isolation level hides, and which it doesn't. It's long and dense; give it
two days if you need, stopping after *Weak Isolation Levels*.

## The slippery concept of a transaction

**The meaning of ACID**, one letter at a time. Note the author's points: **atomicity** is really "abortability" (all
or nothing on error, Figure 7-3), not about concurrency; **consistency** is the application's invariants, which the
database can only partly help with; **isolation** is about concurrent transactions (Figure 7-1: two increments race);
**durability** is never absolute. Then single-object versus multi-object operations, and why retrying an aborted
transaction isn't as simple as it looks.

## Weak isolation levels

The most important section. For each level, learn what it **prevents** and what it **doesn't**:

- **Read committed**: no dirty reads (Figure 7-4) and no dirty writes (Figure 7-5). How it's implemented (row locks for
  writes; old committed values kept for reads).
- **Snapshot isolation and repeatable read**: the **read skew** example (Figure 7-6: Alice's two bank accounts seem to
  have lost 100). **Multi-version concurrency control** (MVCC, Figure 7-7) and the **visibility rules**. Why "repeatable
  read" means different things in different databases.
- **Preventing lost updates**: atomic write operations, explicit locking (`SELECT ... FOR UPDATE`), automatic
  detection, compare-and-set, and conflict resolution in replicated databases.
- **Write skew and phantoms**: the **doctors on call** example (Figure 7-8), the pattern behind it (read, decide,
  write something else), more examples (meeting rooms, usernames, double spending), **phantoms**, and materializing
  conflicts.

## Serializability

Three ways to get it:

- **Actual serial execution**: one thread, stored procedures (Figure 7-9), partitioning; when it's viable.
- **Two-phase locking (2PL)**: shared and exclusive locks held to the end; predicate and index-range locks; why it's
  slow.
- **Serializable snapshot isolation (SSI)**: snapshot isolation plus detection of stale premises (Figures 7-10 and
  7-11); optimistic versus pessimistic concurrency control.

## After reading

For each anomaly (dirty read, dirty write, read skew, lost update, write skew, phantom), write the weakest isolation
level that prevents it.

## What to take away

- Read committed stops dirty reads and writes; snapshot isolation also stops read skew.
- Lost updates need atomic operations, locks, or automatic detection.
- Write skew needs serializability: serial execution, two-phase locking, or SSI.
