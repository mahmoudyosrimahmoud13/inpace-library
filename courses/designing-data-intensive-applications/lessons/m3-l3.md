# Project 3: build a Bitcask-style key-value store

Today you build a real storage engine in about 150 lines: append-only segment files, an in-memory hash index,
tombstones, compaction, and crash recovery with checksums.

The code is above this text. Save it as `p03_logkv.py` in your `lab` folder.

## Read the code

- **`HEADER`** is a `struct` format: a 4-byte checksum, a 2-byte key length and a 4-byte value length, big-endian.
  A value length of `0xFFFFFFFF` means tombstone.
- **`_append()`** always writes at the end of the active segment and records `(segment, offset)` in `self.index`. The
  checksum mixes in the value length, so a tombstone's checksum differs from an empty value's.
- **`active()`** starts a new segment file when the current one reaches `segment_bytes` (64 KB here, small on purpose
  so you get several files).
- **`get()`** looks up the index, seeks to the offset, reads one header and one record. One disk read per lookup.
- **`scan()`** walks a segment record by record and **stops at the first record whose checksum doesn't match**: a
  torn write at the end of the file.
- **`recover()`** rebuilds the index by scanning every segment, oldest first, so newer values overwrite older ones and
  tombstones remove keys.
- **`compact()`** merges all closed segments into one, keeping the latest value of each key, and skipping keys that are
  deleted or that have a newer value in the active segment. It writes to a temporary file and renames it into place,
  so a crash during compaction never loses data.
- **`simplest_get()`** is the "world's simplest database" read: scan everything, keep the last match.
- The main part simulates a video site counting plays: 20,000 writes over 500 keys, so most writes overwrite an old
  value (the workload Bitcask is good at). It then compares read speed, compacts, and simulates a crash by appending
  half a record by hand before "restarting".

## Run it

```bash
python p03_logkv.py
```

The real output (your timings will differ):

```text
20,000 writes over 500 keys -> 8 segment files, 453 KB, 499 live keys
read by scanning the log:   7.627 ms per key
read with the hash index:   0.012 ms per key  (616x faster)
video:7 after delete: None
compaction: old segments 448 KB -> 7 KB; now 2 segment files, every value unchanged
after a crash mid-write and a restart: video:1 = 42 | 499 keys recovered | the torn record was skipped by its checksum
```

What it shows:

- The index makes reads **hundreds of times faster** than scanning, and both give the same answers (the script checks).
- Compaction shrinks the closed segments from about 450 KB to a few KB: almost every record was an old value of a
  key. And every value is unchanged afterwards (checked).
- After the simulated crash, the store restarts, rebuilds its index from the files, and skips the half-written record.

## Make it yours

1. **Hint files.** After compaction, save the index of segment 0 to `000000.hint` (key, offset pairs). Make
   `recover()` load the hint file instead of scanning segment 0. Time a restart with and without it on 200,000
   writes.
2. **Range queries.** Try writing `keys_between("video:100", "video:200")`. Why does the hash index not help? (Day 4's
   LSM-tree will.)
3. **Many keys.** Change the workload to 200,000 *different* keys. How much memory does `self.index` use
   (`sys.getsizeof` is a rough start)? This is the limit the book warns about.
4. Break the checksum check (make `scan()` ignore it) and rerun. What does recovery do with the torn record now?

## What to take away

- You've built the core of a real storage engine: log, index, segments, compaction, recovery.
- Checksums are what make "the last write may be half-done" a safe assumption.
- The design is great for many updates to a set of keys that fits in memory, and weak at range queries.
