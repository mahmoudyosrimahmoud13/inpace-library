# Latency, bandwidth, loss and MTU

| Term | Means | Measure with |
|---|---|---|
| **Latency** | Time for one packet to get there (RTT = there and back) | `ping` |
| **Bandwidth** | How much data per second the link can carry | `iperf3` |
| **Throughput** | How much you actually get | file transfer, `iperf3` |
| **Jitter** | How much latency varies | `ping`, `mtr` |
| **Packet loss** | Packets that never arrive | `ping`, `mtr` |

## Why latency often matters more than bandwidth

Loading a web page is many round trips: DNS, TCP handshake, TLS handshake, then requests. At 150 ms RTT, the handshakes alone cost half a second before the first byte, whatever your bandwidth. That's why CDNs put servers near users and why HTTP/2, HTTP/3 and connection reuse exist.

TCP's speed is also limited by RTT and loss: a single connection over a long, slightly lossy link can't fill a fast pipe. Small loss (1%) can cut throughput dramatically.

## MTU and fragmentation

The **MTU** is the biggest packet a link carries (1500 bytes on Ethernet). VPNs and tunnels add headers, so the usable size inside shrinks. Packets that are too big must be fragmented, or dropped with an ICMP "too big" message.

The classic symptom: **small things work, big things hang**. SSH logs in, but `ls` on a big directory freezes; a web page loads half-way. Often a firewall is blocking those ICMP messages, so the sender never learns to send smaller packets.

```bash
ping -M do -s 1472 8.8.8.8     # 1472 + 28 bytes of headers = 1500: should work
ping -M do -s 1473 8.8.8.8     # one byte too big: "message too long"
ip link show eth0 | grep mtu
```

## Measure, don't guess

```bash
ping -c 20 host                 # RTT min/avg/max, loss
mtr -rwc 50 host                # per-hop loss and latency, as a report
iperf3 -s                       # on one machine
iperf3 -c server-ip -t 10       # on the other: real throughput
```
