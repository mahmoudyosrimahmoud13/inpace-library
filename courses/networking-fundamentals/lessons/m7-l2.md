# Reading packets with tcpdump

When logs disagree, packets tell the truth. `tcpdump` captures what actually crosses an interface.

```bash
sudo tcpdump -i any -n port 53                 # DNS queries and answers
sudo tcpdump -i eth0 -n host 10.0.0.5          # everything to/from one host
sudo tcpdump -i any -n 'tcp port 443 and tcp[tcpflags] & tcp-syn != 0'   # only new TLS connections
sudo tcpdump -i any -n -w capture.pcap port 8080   # save for Wireshark
```

| Option | Means |
|---|---|
| `-i any` | All interfaces |
| `-n` | Don't resolve names (faster, clearer) |
| `-w file` | Write to a file instead of printing |
| `-A` / `-X` | Show payload as text / hex |
| `-c 100` | Stop after 100 packets |

## Reading a TCP line

```text
10:02:31.112 IP 10.0.0.12.51234 > 10.0.0.5.5432: Flags [S], seq 1234, win 64240, length 0
10:02:31.113 IP 10.0.0.5.5432 > 10.0.0.12.51234: Flags [S.], seq 9876, ack 1235, length 0
10:02:31.113 IP 10.0.0.12.51234 > 10.0.0.5.5432: Flags [.], ack 9877, length 0
```

Flags: `S` SYN, `.` ACK, `P` push (data), `F` FIN, `R` reset.

## What captures tell you

| You see | Means |
|---|---|
| SYN, SYN again, SYN again, no reply | Packets dropped: firewall or routing; the server never saw it, or its reply got lost |
| SYN, then **R** (reset) | Nothing listening on that port (connection refused) |
| SYN, SYN-ACK, ACK, then nothing from the app | TCP is fine; the application is stuck |
| Repeated identical data packets | Retransmissions: loss on the path |
| DNS query with no answer | Resolver unreachable or blocked |

Capture on **both** ends when you can: "the packet left A but never reached B" pins the problem to the path in between.

Wireshark (desktop) opens the same `.pcap` files with colours, decoding and "follow TCP stream".
