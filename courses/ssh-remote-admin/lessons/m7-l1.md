# Troubleshooting SSH

## Read the client's story first

```bash
ssh -vvv app01 2>&1 | less
```

| Message | Usually means |
|---|---|
| `Connection timed out` | Network or firewall/security group blocks port 22; wrong IP |
| `Connection refused` | sshd isn't running, or listens on another port |
| `Permission denied (publickey)` | The key offered isn't in `authorized_keys`, wrong user, or bad permissions on the server's `~/.ssh` |
| `Too many authentication failures` | The agent offered many keys first: use `IdentitiesOnly yes` |
| `Host key verification failed` | The server's key changed (rebuilt server, or something worse) |
| Hangs after `debug1: SSH2_MSG_KEXINIT sent` | MTU or a middlebox dropping big packets |
| Very slow to show the password/key prompt | Server does reverse DNS on you (`UseDNS no`) or GSSAPI (`GSSAPIAuthentication no`) |

## Then the server's

```bash
sudo journalctl -u ssh -f              # watch while you try to connect
sudo sshd -T | grep -Ei 'passwordauth|pubkeyauth|allow|permitroot'
ls -ld ~ ~/.ssh; ls -l ~/.ssh/authorized_keys   # home not group-writable, .ssh 700, file 600
```

The server log tells you exactly why: `Authentication refused: bad ownership or modes for directory /home/sara`, `User deploy from 10.0.0.5 not allowed because not listed in AllowUsers`.

## Locked out?

- Cloud: use the provider's serial console or Session Manager; or detach the disk, attach it to a rescue VM, fix `sshd_config` or `authorized_keys`.
- Physical: the console, or boot into rescue mode (System Administration, Day 1).
- Prevention: always test config changes in a **second** session while the first stays open.
