# Capstone: secure remote access for a small team

Three VMs (or cloud instances): **bastion**, **app01** (private), **files01** (private).

## Build

1. **Network**: only the bastion accepts SSH from outside (from your IP); app01 and files01 accept SSH only from the bastion's address.
2. **Your client config**: `Host bastion`, and `ProxyJump bastion` for the private hosts; `IdentitiesOnly`; keep-alives; multiplexing.
3. **Keys**: a passphrase-protected ed25519 key in your agent. No agent forwarding anywhere.
4. **Bastion hardening**: keys only, `AllowGroups ssh-users`, fail2ban, nothing else installed.
5. **A partner upload account** on files01: SFTP-only, chrooted to its own folder.
6. **A tunnel**: reach a web dashboard or database that listens only on app01's localhost, with `ssh -L` through the bastion.
7. **Certificates (stretch)**: an SSH user CA; app01 trusts it; issue yourself an 8-hour certificate and log in without `authorized_keys`.
8. **Long job**: run a 10-minute script on app01 inside tmux, disconnect your Wi-Fi, reconnect and re-attach.

## Prove it

```bash
ssh -G app01 | grep -E 'proxyjump|identitiesonly|user '
ssh app01 hostname
nc -zv -w3 <app01-public-ip-if-any> 22        # should time out from outside
sftp partner1@files01 ; ssh partner1@files01   # sftp works, ssh doesn't
ssh-keygen -L -f ~/.ssh/id_ed25519-cert.pub    # (stretch) valid window and principals
```

## Write the team's one-pager

How to get access (who issues keys or certificates), the config snippet everyone pastes, how to reach private services (tunnel recipes), and what to do when a laptop is lost.
