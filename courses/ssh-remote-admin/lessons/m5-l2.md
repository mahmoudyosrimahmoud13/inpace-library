# Agent forwarding risks, and alternatives

## The old way: `ssh -A`

Agent forwarding lets the next hop use the keys in your laptop's agent:

```bash
ssh -A bastion        # then, from the bastion:
ssh app01             # the bastion asks YOUR agent to sign
```

The danger: while you're connected, **anyone with root on the bastion** can use your agent to log in anywhere your keys work. One compromised jump host becomes access to everything.

| Instead of `-A` for... | Use |
|---|---|
| Reaching servers behind a bastion | `ProxyJump` (keys never leave your laptop) |
| `git pull` on a server from a private repo | A **deploy key** for that repo on the server (read-only) |
| CI deploying to servers | A dedicated, restricted key or OIDC/short-lived credentials |

If you truly must forward, confirm each use: `ssh-add -c` makes the agent ask before every signature.

## No SSH port at all

Cloud session managers (AWS Systems Manager Session Manager, Google IAP, Azure Bastion) give you a shell through the cloud's API:

- No inbound port 22, no bastion to maintain.
- Access controlled by cloud IAM, sessions recorded.
- Still works with `ssh`/`scp` via a ProxyCommand.

Tailscale SSH and similar tools do the same over a private overlay network. The Cloud Linux Administration course sets up Session Manager.
