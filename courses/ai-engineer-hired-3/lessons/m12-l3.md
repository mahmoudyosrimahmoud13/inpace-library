# Fine-tuning in practice: LoRA, QLoRA and preference tuning

The field guide found fine-tuning in 30.8% of AI-first postings but as a *primary* responsibility in only 4%. So you need to explain it well and know when not to do it, more often than you need to run it.

## LoRA in one picture

Full fine-tuning updates every weight. **LoRA** (Low-Rank Adaptation, 2021) freezes the original weight matrix `W` and learns a small update made of two thin matrices: `W' = W + B·A`, where `B` is d×r and `A` is r×k, with a small rank r (often 8 to 64).

```python
import numpy as np
d, k, r = 4096, 4096, 16              # one attention matrix of a 7B-size model, rank 16
full = d * k
lora = d * r + r * k
print(full, lora, f"{lora / full:.2%}")  # 16777216 131072 0.78%

W = np.random.randn(d, k).astype(np.float32)
A = np.random.randn(r, k).astype(np.float32) * 0.01
B = np.zeros((d, r), dtype=np.float32)     # B starts at zero, so training starts from the original model
x = np.random.randn(k).astype(np.float32)
assert np.allclose(W @ x, (W + B @ A) @ x)
```

Training under 1% of the parameters means far less GPU memory, and the result is a small **adapter** file you can swap per customer or task, or merge into the weights for serving.

**QLoRA** (2023) goes further: load the frozen base model in 4-bit precision and train LoRA adapters on top. That's how people fine-tune 7B to 70B models on a single GPU. In code, this is usually the Hugging Face `peft` library (a `LoraConfig` with `r`, `lora_alpha` and `target_modules`), with `trl` or Unsloth for the training loop.

## The kinds of tuning

| Kind | Data | Teaches |
|---|---|---|
| **SFT** (supervised fine-tuning) | prompt → ideal answer pairs | a format, a style, a narrow task |
| **Preference tuning: DPO** | prompt, a better answer, a worse answer | which of two answers to prefer, without training a separate reward model |
| **RL with verifiable rewards** | problems with checkable answers | reasoning (as in reasoning models) |
| **Distillation** | a big model's outputs on your inputs | the big model's quality in a small, cheap model |

## The workflow that avoids wasted GPU money

1. Prove the task with **prompting and an eval set** first; that eval set is how you'll judge the tuned model.
2. Collect **hundreds to thousands of clean examples**; quality beats quantity, and a few bad examples teach bad habits.
3. Hold out a test split; fine-tune a small model with LoRA.
4. Compare against the prompted big model on **quality, cost and latency**, and check it didn't forget general skills you need.
5. Plan for maintenance: a new base model means re-tuning.
