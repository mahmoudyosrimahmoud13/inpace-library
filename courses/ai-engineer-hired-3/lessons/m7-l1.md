# Cost, latency and reliability

**Cost per request = input tokens × input price + output tokens × output price** (plus embeddings and retrieval). Output tokens usually cost several times more than input. Levers, roughly in the order to try them:

1. **Shorter context:** fewer, better chunks; trimmed history.
2. **Model tiering / routing:** a small model for easy or classified cases, a big one for the hard rest.
3. **Caching:** exact-match caching for repeated requests, prompt caching for long shared prefixes (many APIs offer it), semantic caching where safe.
4. **Batching** for offline jobs.
5. **Fine-tune or distil** a small model when volume is high and the task is narrow.

## Latency and reliability

- **TTFT** is what users feel: stream tokens, start retrieval and the model call early, run independent calls in parallel.
- Measure **p50 and p95** per step (retrieval, each LLM call, tools); fix the biggest.
- Every external call gets a **timeout, retries with backoff, and a fallback** (another model, a cached answer, or a clear "try again").
- Respect **rate limits**; queue bursts.

## Caching and batching in detail

| Lever | How it works | Typical saving | Watch out |
|---|---|---|---|
| **Prompt caching** | the provider reuses the processed prefix of a prompt that repeats | large discount on cached input tokens, lower time to first token | stable content first; caches expire after minutes of no use |
| **Exact cache** (yours) | store answers by a hash of the full request | 100% of the call | only for truly repeated requests |
| **Semantic cache** (yours) | reuse an answer when a new question's embedding is very close | most of the call | wrong answers when the answer depends on the user, date or a small word ("not") |
| **Batch API** | send thousands of requests as one job; results come back within hours | providers usually charge about half price | only for work that can wait: evals, backfills, nightly labelling |

**Reasoning models** change the maths: they produce many hidden "thinking" tokens billed as output, so one hard question can cost what dozens of simple ones do. Route only the hard cases to them, and cap the thinking budget where the API allows it.
