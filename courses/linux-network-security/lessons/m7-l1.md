# Logging and auditing for security

## What to watch

| Source | Shows |
|---|---|
| `journalctl -u ssh`, `/var/log/auth.log` (`/var/log/secure`) | Logins, sudo, su, key use |
| `journalctl -k` | Firewall log lines (`nft-drop:`), kernel warnings |
| nginx / app access logs | Scans (`/wp-admin`, `/.env`, `/phpmyadmin`), bursts of 401/403/404 |
| `last`, `lastb`, `lastlog` | Login history |
| **auditd** | Precise records of chosen system calls and file access |

## auditd: who touched what

```bash
sudo apt install auditd
sudo auditctl -w /etc/passwd -p wa -k identity        # watch writes and attribute changes
sudo auditctl -w /etc/ssh/sshd_config -p wa -k sshd
sudo auditctl -a always,exit -F arch=b64 -S execve -F euid=0 -k rootcmd   # every command run as root
sudo ausearch -k identity --interpret | tail
sudo aureport --summary
```

Make rules permanent in `/etc/audit/rules.d/*.rules`. Start small: auditing every `execve` on a busy server produces a lot of data.

## Logs leave the box

An attacker with root edits local logs first. Ship logs elsewhere as they're written: `rsyslog` forwarding, `systemd-journal-remote`, or an agent (Vector, Fluent Bit, the cloud's logging agent) into a central system the server can't delete from. The Observability course builds this.

## Time matters

Logs from several machines only line up if clocks agree. Keep NTP on (`timedatectl` should say `System clock synchronized: yes`; `chronyc tracking` for detail).
