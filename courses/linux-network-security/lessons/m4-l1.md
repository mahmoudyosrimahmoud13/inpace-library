# SSH hardening beyond the basics

You set keys-only and no root login in System Administration. Now the rest.

## Strong keys

```bash
ssh-keygen -t ed25519 -a 100 -C "sara@laptop"      # modern, small, fast; -a = harder to brute-force the passphrase
```

- Always protect private keys with a **passphrase**, and use `ssh-agent` so you type it once.
- Even better: keys on a hardware token (`ssh-keygen -t ed25519-sk` with a YubiKey). The key can't be copied off the device.

## A hardened sshd

`/etc/ssh/sshd_config.d/10-hardening.conf`:

```text
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
AuthenticationMethods publickey
AllowGroups ssh-users                 # only members of this group may log in
MaxAuthTries 3
LoginGraceTime 20
X11Forwarding no
AllowAgentForwarding no               # agent forwarding lets a compromised server use your keys
ClientAliveInterval 300
ClientAliveCountMax 2
```

```bash
sudo sshd -t && sudo systemctl reload ssh    # test, then reload. Keep a session open!
ssh-audit your.server                        # checks algorithms and settings (pip install ssh-audit)
```

## Where to reach SSH from

| Option | Exposure |
|---|---|
| Open to the internet | Constant guessing (harmless with keys only, but noisy) |
| Only from the office IP / VPN | Much smaller |
| Through a **bastion** (jump host) only | One hardened, well-watched entry point |
| No SSH port at all: cloud session managers (AWS SSM), Tailscale | The smallest |

The SSH course covers bastions, `ProxyJump` and tunnels in depth.

## SSH certificates

For teams, signing short-lived **user certificates** with an SSH certificate authority beats copying public keys to every server: access expires automatically, and revoking someone doesn't mean editing hundreds of `authorized_keys` files (`TrustedUserCAKeys` in sshd).
