# Permissions in depth: ACLs, special bits and capabilities

## The special bits

| Bit | On a file | On a directory | Set with |
|---|---|---|---|
| **SUID** (4) | Runs as the file's owner | (ignored) | `chmod u+s` |
| **SGID** (2) | Runs as the file's group | New files inherit the directory's group | `chmod g+s` |
| **Sticky** (1) | (ignored) | Only a file's owner can delete it | `chmod +t` |

```bash
ls -ld /tmp              # drwxrwxrwt: sticky, so users can't delete each other's files
ls -l /usr/bin/passwd    # -rwsr-xr-x: SUID root
chmod 2775 /srv/shared   # SGID directory: team files keep the team's group
```

A shared team folder done right: owner `root`, group `team`, mode `2770`, plus a default ACL (below) so new files are group-writable.

## ACLs: more than one user and one group

```bash
setfacl -m u:alice:rw report.xlsx          # give alice read/write
setfacl -m g:auditors:r -R /srv/finance    # group read, recursively
setfacl -d -m g:team:rwX /srv/shared       # DEFAULT ACL: applies to new files created inside
getfacl /srv/shared
setfacl -x u:alice report.xlsx             # remove
```

A `+` at the end of `ls -l` permissions (`-rw-rw-r--+`) means an ACL is present: check `getfacl` before assuming the rwx tell the whole story.

## Capabilities instead of root

From the Advanced Linux course: give a program just the power it needs.

```bash
sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/myserver
getcap -r /usr/bin /usr/sbin /usr/local 2>/dev/null       # audit file capabilities
```

## Hardening sudo

```text
Defaults use_pty                       # sudo sessions can't leave background processes on your terminal
Defaults logfile="/var/log/sudo.log"
Defaults timestamp_timeout=5
%deploy ALL=(root) /usr/bin/systemctl restart myapp, /usr/bin/journalctl -u myapp
```

Never allow sudo on editors, `less`, `find`, `tar`, scripts users can edit, or anything with a shell escape: `sudo vim` lets you run `:!bash` as root. GTFOBins (gtfobins.github.io) lists which programs can escape.
