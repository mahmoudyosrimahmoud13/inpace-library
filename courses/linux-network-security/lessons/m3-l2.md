# NAT, port forwarding, and the Docker gotcha

## Masquerade: share an internet connection

Make a Linux box the gateway for a private network:

```text
table ip nat {
  chain postrouting {
    type nat hook postrouting priority 100;
    oifname "eth0" ip saddr 10.0.0.0/24 masquerade     # private -> public address
  }
}
```

Plus `net.ipv4.ip_forward=1` and forward-chain rules allowing the traffic. That's exactly what a home router, a cloud NAT gateway, and Docker's default network do.

## Port forwarding (DNAT)

Send public port 8443 to an internal server's 443:

```text
table ip nat {
  chain prerouting {
    type nat hook prerouting priority -100;
    iifname "eth0" tcp dport 8443 dnat to 10.0.0.20:443
  }
}
```

The forward chain must also allow it: `ct state established,related accept` plus `ip daddr 10.0.0.20 tcp dport 443 accept`.

## The Docker gotcha

`docker run -p 5432:5432 postgres` inserts its **own** NAT and forward rules. Traffic to published ports goes through the **forward** path, not **input**, so your input-chain rules (and ufw!) **don't apply**. People firewall port 5432 with ufw, publish it with Docker, and their database is open to the internet.

Fixes:

- Publish only on localhost: `-p 127.0.0.1:5432:5432`, and put a reverse proxy in front if it must be public.
- Or add rules to Docker's `DOCKER-USER` chain, which Docker leaves for you.
- Check from **outside** with `nmap`, always. What you think the firewall does and what it does can differ.

## Host firewall vs cloud firewall

| | Host (nftables) | Cloud (security groups, NACLs) |
|---|---|---|
| Lives | On the server | In the provider's network |
| Survives a compromised server? | No, root can change it | Yes |
| Sees | Everything, including localhost and containers | Traffic entering and leaving the VM |

Use both: cloud rules as the outer wall, host rules for defence in depth.
