# fail2ban and watching authentication

## What attacks on SSH look like

```bash
sudo journalctl -u ssh --since today | grep -E 'Invalid user|Failed password|Disconnected' | tail
sudo journalctl -u ssh --since today | grep -oP 'Invalid user \K\S+' | sort | uniq -c | sort -nr | head
```

Typical: thousands of attempts a day for `root`, `admin`, `ubuntu`, `oracle`, `test`, from rotating IPs. With keys only they can't succeed, but they fill logs and use CPU.

## fail2ban

fail2ban watches logs and temporarily bans IPs that fail too often, by adding firewall rules.

```bash
sudo apt install fail2ban
```

`/etc/fail2ban/jail.local`:

```ini
[DEFAULT]
bantime  = 1h
findtime = 10m
maxretry = 5
banaction = nftables
backend = systemd

[sshd]
enabled = true

[nginx-http-auth]
enabled = true
```

```bash
sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd        # banned IPs
sudo fail2ban-client set sshd unbanip 203.0.113.9
```

Add your own IP to `ignoreip` so a typo-filled morning doesn't lock you out.

## Watch successful logins too

Failed logins are noise. A **successful** login from somewhere unexpected is the real alarm.

```bash
last -n 20 -a                     # recent logins with their source
sudo journalctl -u ssh | grep 'Accepted'
lastlog | grep -v 'Never'         # last login per account
```

Send `Accepted publickey for ... from <unknown IP>` to your alerting (the Bash course's notify function, or the Observability course's log alerts).
