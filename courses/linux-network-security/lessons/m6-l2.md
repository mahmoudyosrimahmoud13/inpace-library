# Authentication: PAM, passwords and MFA

## PAM: the plug-in system for logins

**PAM** (Pluggable Authentication Modules) decides how `login`, `sshd`, `sudo` and others check who you are. Each service has a file in `/etc/pam.d/` listing modules in order:

```text
# /etc/pam.d/sshd (simplified)
auth       required   pam_faillock.so preauth
auth       required   pam_unix.so          # check /etc/shadow
auth       required   pam_google_authenticator.so    # + a one-time code (if you add MFA)
account    required   pam_nologin.so       # /etc/nologin blocks non-root logins
session    required   pam_limits.so        # apply /etc/security/limits.conf
```

| Control | Means |
|---|---|
| `required` | Must pass; keep checking the rest anyway |
| `requisite` | Must pass; stop immediately if not |
| `sufficient` | Passing is enough (if nothing required failed) |
| `optional` | Doesn't decide on its own |

**Edit PAM with great care and an open root session**: a mistake can lock out every login, including sudo.

## Passwords that remain

Even with SSH keys, accounts have passwords for `sudo` and consoles.

```bash
sudo apt install libpam-pwquality     # /etc/security/pwquality.conf: minlen = 14, etc.
sudo chage -l sara                     # ageing (modern guidance: long passphrases, no forced rotation)
sudo faillock --user sara              # failed attempts and lockouts
```

Password hashes in `/etc/shadow` start with an algorithm ID: `$y$` is yescrypt (modern default), `$6$` SHA-512. Anything older should be reset.

## MFA for SSH

Keys are "something you have". Add "something you have, separately" with TOTP codes (`libpam-google-authenticator`) and in sshd:

```text
AuthenticationMethods publickey,keyboard-interactive
KbdInteractiveAuthentication yes
```

Hardware-backed SSH keys (`ed25519-sk`) give the same protection more simply: the key can't be used without touching the token.
