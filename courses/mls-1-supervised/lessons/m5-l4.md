# Project 3: many features, vectorized and scaled

You'll use eight features at once, written as matrix operations, and see why feature scaling isn't optional.

The code is above this text. Save it as `p3_many_features.py`.

## Read the code

- **`gd(X, y, alpha, steps)`** is yesterday's gradient descent for any number of features: `X @ w + b` predicts every
  district at once, and `X.T @ err / m` is every partial derivative at once.
- It runs first on the raw features, then on z-scored ones (`homes.scale`: the training set's mean and standard
  deviation, applied to both sets).
- **`ENGINEERED`** adds four features: rooms and people per household, log of population, income squared.
- Last, it predicts every training district with Python loops and with one matrix product, and times both.

## Run it

```bash
python p3_many_features.py
```

What it shows:

- **The features differ by a factor of thousands** (income up to 15, rooms up to 39,320). On raw features, any
  learning rate big enough to move income's weight blows up the rooms weight; at 1e-7 the model is still poor ($124k)
  after 500 steps.
- **Scaled, the same 500 steps reach $61k.** Scaling makes one learning rate suit every feature.
- The biggest weights are location (latitude, longitude) and income.
- **The engineered features don't help this linear model** ($61k either way): a straight-line model can only use them
  in straight lines. Not every good idea helps every model; measure it.
- **Vectorized code is hundreds of times faster** than loops, with the same answers.
