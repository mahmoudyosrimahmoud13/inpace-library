# Running FastAPI in production

## The command

```bash
fastapi run app/main.py --port 8000 --workers 4
```

or with Uvicorn directly:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
```

- **No `--reload`** in production.
- **Workers** are separate processes. Each one has its own event loop and memory, so more workers use more CPU
  cores. A common start is about one worker per core, then measure.
- Gunicorn with Uvicorn workers (`gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 4`) is an older but
  still common setup. Uvicorn's own `--workers` now restarts dead workers too.
- In Kubernetes or similar, it's often better to run **one worker per container** and let the platform run more
  containers.

## Behind a proxy

Usually a proxy (Nginx, Traefik, Caddy, a cloud load balancer) handles HTTPS and forwards requests to your app.
Tell Uvicorn to trust the proxy's headers, so `request.url` and client IPs are right:

```bash
uvicorn app.main:app --proxy-headers --forwarded-allow-ips="10.0.0.0/8"
```

If the proxy serves your API under a sub-path like `/api`, set `root_path="/api"` (or `--root-path /api`) so
`/docs` and links still work.

## Health checks

```python
@app.get("/health", include_in_schema=False)
def health():
    return {"status": "ok"}

@app.get("/ready", include_in_schema=False)
async def ready(db: DB):
    await db.execute(text("SELECT 1"))      # can we reach the database?
    return {"status": "ready"}
```

Load balancers and orchestrators use these to decide where to send traffic and when to restart.
