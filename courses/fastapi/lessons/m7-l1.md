# async def vs def: don't block the event loop

FastAPI runs on an **event loop**: one thread that switches between many requests whenever one of them is waiting.

## The rule

| You write | FastAPI does | Use it when |
|---|---|---|
| `async def` | runs it **on the event loop** | everything slow inside is `await`ed (async DB driver, `httpx.AsyncClient`, `asyncio.sleep`) |
| `def` | runs it **in a thread pool** | you call normal blocking code (`requests`, sync DB drivers, file I/O, heavy libraries) |

## The classic mistake

```python
import time, requests

@app.get("/slow")
async def slow():
    time.sleep(2)                       # BLOCKS the whole event loop
    r = requests.get("https://...")     # also blocks
    return r.json()
```

While this runs, **every other request on that worker waits**. Fix it either way:

```python
import asyncio, httpx

@app.get("/slow")
async def slow():
    await asyncio.sleep(2)
    async with httpx.AsyncClient() as client:
        r = await client.get("https://...")
    return r.json()

# or simply make it a normal def, and FastAPI runs it in a thread:
@app.get("/slow-sync")
def slow_sync():
    time.sleep(2)
    return requests.get("https://...").json()
```

## Calling blocking code from async code

```python
from fastapi.concurrency import run_in_threadpool

@app.post("/resize")
async def resize(file: UploadFile):
    data = await file.read()
    small = await run_in_threadpool(make_thumbnail, data)   # CPU work off the loop
    ...
```

## Doing things in parallel

```python
import asyncio

async def dashboard():
    weather, news = await asyncio.gather(get_weather(), get_news())
```

Heavy CPU work (image processing, ML models) still competes for the CPU. For a lot of it, use more worker
processes or a job queue.
