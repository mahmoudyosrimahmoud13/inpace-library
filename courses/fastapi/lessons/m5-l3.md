# Migrations with Alembic

`Base.metadata.create_all(engine)` creates tables, but it **never changes** tables that already exist. As soon as you
have real data, you need **migrations**: small, versioned scripts that change the schema step by step.

## Set up

```bash
pip install alembic
alembic init migrations
```

In `migrations/env.py`, point Alembic at your models:

```python
from app.db import Base
target_metadata = Base.metadata
```

and set the database URL in `alembic.ini` (or read it from your settings in `env.py`).

## Daily workflow

```bash
# 1. Change a model, e.g. add a column
#    published: Mapped[bool] = mapped_column(default=False)

# 2. Generate a migration from the difference
alembic revision --autogenerate -m "add published to books"

# 3. READ the generated file in migrations/versions/ and fix it if needed

# 4. Apply it
alembic upgrade head

# Undo the last one
alembic downgrade -1
```

## Rules that save you pain

- **Always read autogenerated migrations.** Alembic can't detect everything (renamed columns look like drop + add,
  which would delete data). Edit the script to use `op.alter_column(..., new_column_name=...)` instead.
- **Adding a NOT NULL column to a table with rows** needs a `server_default`, or a two-step migration (add as
  nullable, fill values, then make it NOT NULL).
- **Commit migrations to git** with the code that needs them.
- **Run `alembic upgrade head` when you deploy**, before the new code starts serving traffic.
- Never edit a migration that has already run in production. Write a new one.
