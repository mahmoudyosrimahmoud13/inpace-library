# Final project: the Library API

Time to put everything together in one app you can show in a portfolio.

## What to build

A **Library API** where readers borrow books and librarians manage the catalogue.

**Must have**

1. **Auth:** sign up, log in with OAuth2 password flow, JWT access tokens, `/me`.
2. **Roles:** `reader` and `librarian`. Only librarians add, edit or remove books.
3. **Books and authors** in PostgreSQL (or SQLite to start) with SQLAlchemy and **Alembic migrations**.
4. **Search** with filters (title, author, year) and **cursor pagination**.
5. **Loans:** a reader borrows a book (409 if it's already out), returns it, and sees their own loans only.
6. **Separate input and output models** everywhere; no password hashes ever leave the API.
7. **Consistent errors** with custom exception handlers.
8. **Background task:** an email (or log line) when a loan is due soon.
9. **Tests:** at least 15, with a test database and overridden auth, running in GitHub Actions.
10. **Docker** + compose with PostgreSQL, `/health`, `/ready`, JSON logs with request ids.

**Nice to have**

- SSE or WebSocket notifications when a reserved book comes back.
- Rate limiting on `/token`.
- `/v2` of one endpoint with a breaking change, while `/v1` keeps working.
- A small front end, or a generated TypeScript client from `/openapi.json`.

## Suggested order

1. Models, migrations and CRUD for books and authors.
2. Users, hashing, tokens and roles.
3. Loans with ownership checks.
4. Tests (write them as you go, not at the end).
5. Search and pagination.
6. Error handling, background task, logging.
7. Docker, CI, and a README with how to run it.

## How to know you're done

- Someone else can clone your repo, run `docker compose up`, open `/docs`, log in and borrow a book.
- `pytest` passes locally and in CI.
- Your README explains the design choices you made and why.
