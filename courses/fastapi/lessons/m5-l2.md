# Async databases and the N+1 problem

## Going async

With an async driver (`asyncpg` for PostgreSQL, `aiosqlite` for SQLite), the event loop can serve other requests
while waiting on the database.

```python
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

engine = create_async_engine("postgresql+asyncpg://user:pass@localhost/app", pool_size=10)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)

async def get_db():
    async with SessionLocal() as db:
        yield db

DB = Annotated[AsyncSession, Depends(get_db)]

@app.get("/books/{book_id}")
async def get_book(book_id: int, db: DB):
    book = await db.get(Book, book_id)
    ...

@app.get("/books")
async def list_books(db: DB):
    result = await db.scalars(select(Book).limit(20))
    return result.all()
```

## The lazy-loading trap

In async code, touching a relationship that wasn't loaded (`book.author.name`) raises an error, because loading it
would need a hidden database call. **Load what you need up front:**

```python
from sqlalchemy.orm import selectinload

stmt = select(Book).options(selectinload(Book.author)).limit(20)
books = (await db.scalars(stmt)).all()
```

## The N+1 problem (sync or async)

This looks innocent:

```python
books = db.scalars(select(Book)).all()          # 1 query
return [{"title": b.title, "author": b.author.name} for b in books]   # +1 query PER book
```

100 books means 101 queries. Fix it with eager loading:

| Option | What it does | Good for |
|---|---|---|
| `selectinload(Book.author)` | one extra query with `WHERE id IN (...)` | collections and most cases |
| `joinedload(Book.author)` | a JOIN in the same query | single related objects |

Turn on `echo=True` on the engine while developing to see every SQL query, and watch for repeats.

## Transactions

Group changes that must succeed or fail together:

```python
async with db.begin():
    db.add(order)
    product.stock -= 1
# committed here, or rolled back if anything raised
```
