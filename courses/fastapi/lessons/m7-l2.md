# Background tasks and job queues

Some work shouldn't make the user wait: sending an email, writing an audit log, warming a cache.

## BackgroundTasks

```python
from fastapi import BackgroundTasks

def send_welcome_email(email: str):
    ...   # talks to your email provider


@app.post("/signup", status_code=201)
def signup(data: UserCreate, background: BackgroundTasks, db: DB):
    user = create_user(db, data)
    background.add_task(send_welcome_email, user.email)
    return user          # the response is sent first, then the task runs
```

Tasks run **after the response is sent**, in the same process. You can also use `BackgroundTasks` inside a
dependency.

## When it's not enough

`BackgroundTasks` is great for small, quick jobs. It is **not** a job system:

- If the server restarts, queued tasks are lost.
- There are no retries, no schedule, and no way to see progress.
- Long CPU work still slows the same server.

For anything important or heavy, use a **task queue** with a separate worker process:

| Tool | Notes |
|---|---|
| **Celery** | the classic, many features, Redis or RabbitMQ |
| **RQ** | simple, Redis |
| **arq**, **Dramatiq**, **Taskiq** | lighter options, some async-native |

The pattern: the endpoint saves a job and returns `202 Accepted` with a job id; a worker does the work; the client
checks `GET /jobs/{id}` or gets a webhook/WebSocket message when it's done.
