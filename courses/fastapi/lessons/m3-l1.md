# Response models: control what goes out

Validating input is half the job. You also want to control **output**: never leak a password hash, always return
the same shape.

```python
from pydantic import BaseModel, EmailStr

class UserIn(BaseModel):
    email: EmailStr
    password: str

class UserOut(BaseModel):
    id: int
    email: EmailStr


@app.post("/users", response_model=UserOut, status_code=201)
def create_user(user: UserIn):
    saved = save_to_db(user)        # returns an object with id, email, password_hash...
    return saved                    # FastAPI keeps only id and email
```

Or use the return type, which does the same thing:

```python
@app.post("/users", status_code=201)
def create_user(user: UserIn) -> UserOut:
    ...
```

`response_model` (or the return annotation) makes FastAPI:

- **Filter** the data to the fields of `UserOut`. Extra fields are dropped.
- **Validate** the output, so a bug that returns a wrong shape is caught.
- **Document** the response in `/docs`.

## Returning database objects

ORM objects (module 5) aren't dicts. Tell Pydantic to read attributes:

```python
from pydantic import ConfigDict

class UserOut(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    email: str
```

## Useful options

| Option | Effect |
|---|---|
| `response_model_exclude_unset=True` | leave out fields that were never set |
| `response_model_exclude_none=True` | leave out fields that are `None` |
| `response_model=list[UserOut]` | a list of users |

## A common pattern

Keep separate models for each direction: `UserCreate` (input), `UserUpdate` (partial input), `UserOut` (output),
and your database model. It feels like more code at first but prevents whole classes of security bugs.
