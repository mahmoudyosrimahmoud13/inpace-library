# Mobile system design

A frequent senior round: "Design the mobile app for X." Use a structure:

1. **Clarify:** users, main flows, offline needs, scale, platforms.
2. **High-level design:** screens, modules, data flow.
3. **Data:** local storage, API shape (REST/GraphQL), pagination, caching.
4. **State:** what lives where; source of truth.
5. **Offline and sync:** queue writes, retries with backoff, conflict rules.
6. **Real-time:** WebSockets, push.
7. **Performance:** images, lists, start-up.
8. **Security:** token storage (Keychain/Keystore via `flutter_secure_storage`), certificate pinning if needed, no
   secrets in the app.
9. **Observability and release:** crashes, analytics, flags, staged rollout.

## Worked example: "Design a learning app like inPace for phones"

- **Offline-first:** everything local (SQLite). No accounts; identity is an on-device key pair.
- **Trust without servers:** milestones signed and hash-chained; mentors verify files sent over chat apps.
- **Sharing:** links that carry compressed data in the URL fragment; App Links to open them in the app.
- **Notifications:** scheduled locally; a chronometer notification for focus sessions; exact alarms when allowed.
- **Content:** courses as signed packs from a static, CDN-hosted library verified by SHA-256.
- **Trade-off you'd mention:** no cross-device sync without a server; the answer is encrypted backups now, and an
  optional end-to-end encrypted relay later.

Practice with: a chat app, a ride-hailing driver app, an offline notes app with sync, a news feed with images.
