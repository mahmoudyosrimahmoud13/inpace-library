# Reading EXPLAIN and EXPLAIN ANALYZE

## The two commands

- `EXPLAIN query`: the **plan** and **estimated** costs. The query doesn't run.
- `EXPLAIN (ANALYZE, BUFFERS) query`: **runs** the query and shows **actual** rows, time and pages. Careful with `UPDATE` or `DELETE`: wrap them in `BEGIN; ... ROLLBACK;`.

## Reading a node

```
Index Scan using idx_orders_cust on orders
  (cost=0.43..8.45 rows=1 width=40)
  (actual time=0.020..0.021 rows=3 loops=1)
  Buffers: shared hit=4
```

| Field | Meaning |
|---|---|
| cost=a..b | Startup cost..total cost, in arbitrary units (`seq_page_cost` = 1) |
| rows | **Estimated** rows |
| actual rows | Real rows **per loop** |
| loops | How many times the node ran (multiply!) |
| shared hit / read | Pages found in cache / read from disk |

Read plans **inside out**: the deepest nodes run first.

## The number one signal: estimate vs actual

If the planner expected `rows=10` and got `rows=500000`, every choice above that node may be wrong (for example, a nested loop that should have been a hash join). Fixes:
- `ANALYZE table;`
- Raise the statistics target on that column: `ALTER TABLE t ALTER COLUMN c SET STATISTICS 1000;`
- For correlated columns: `CREATE STATISTICS ... (dependencies) ON a, b FROM t;`

## Join methods

| Method | Best when |
|---|---|
| Nested Loop | Outer side is small and the inner side has an index |
| Hash Join | Medium to large inputs, equality join, the hash fits in `work_mem` |
| Merge Join | Both inputs already sorted on the join key |

## Other warning signs

- `Sort Method: external merge  Disk: ...` means `work_mem` is too small for this sort.
- `Rows Removed by Filter` is large: you need an index or a better one.
- A Seq Scan on a big table inside a loop.

> **Key idea:** first compare estimated with actual rows. Most bad plans come from bad estimates, not from missing indexes.
