# VACUUM, bloat and autovacuum

## Why vacuum exists

MVCC leaves **dead tuples** behind after every `UPDATE` and `DELETE`. VACUUM:

1. Marks dead tuple space as **reusable** (recorded in the free space map).
2. Updates the **visibility map**, which makes **index-only scans** possible.
3. **Freezes** old transaction IDs to prevent **XID wraparound**.

Plain `VACUUM` doesn't return space to the OS and doesn't block reads or writes. `VACUUM FULL` rewrites the table and **takes an ACCESS EXCLUSIVE lock**.

## Transaction ID wraparound

Transaction IDs are 32-bit, about 4 billion. If old rows aren't frozen, Postgres eventually **stops accepting writes** to protect your data. Autovacuum's anti-wraparound runs prevent this, so never disable autovacuum.

## Tuning autovacuum

The defaults trigger a vacuum after about 20% of a table changes. On a 100M-row table, that means waiting for 20M dead rows.

```sql
ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_cost_limit = 2000
);
```

## Index bloat

Indexes also hold pointers to dead tuples. Heavy update workloads bloat indexes. Fix it online with:

```sql
REINDEX INDEX CONCURRENTLY idx_orders_customer;
```

## HOT updates

If an `UPDATE` changes **no indexed column** and the page has free space, Postgres makes a **heap-only tuple (HOT)** update and **no index entry is written**. Lowering `fillfactor` (for example to 90) leaves room for HOT updates.

## Watch it

```sql
SELECT relname, n_dead_tup, n_live_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

> **Key idea:** vacuum isn't optional maintenance. It's part of how MVCC works. Tune it per table on big, busy tables.
