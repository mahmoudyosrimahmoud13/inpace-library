# Partitioning

## What it is

**Declarative partitioning** splits one logical table into child tables by a key:

```sql
CREATE TABLE events (
  id bigint, created_at timestamptz NOT NULL, payload jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_11 PARTITION OF events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
```

| Type | Use |
|---|---|
| RANGE | Time series (by month or day) |
| LIST | Region, tenant or category |
| HASH | Spreading writes evenly |

## Why partition

- **Partition pruning**: `WHERE created_at >= '2026-11-01'` reads only the matching partitions.
- **Cheap retention**: `DROP TABLE events_2025_01` (or `DETACH PARTITION ... CONCURRENTLY`) instead of a huge `DELETE` plus vacuum.
- Smaller indexes per partition, and vacuum works per partition.

## Rules and limits

- **The partition key must be in every primary key or unique constraint.**
- Queries that don't filter on the key scan **all** partitions.
- Thousands of partitions slow down planning. Aim for tens to low hundreds.
- Create future partitions ahead of time (with a cron job or `pg_partman`), or inserts fail. A `DEFAULT` partition catches stray rows.

## Partitioning vs sharding

| | Partitioning | Sharding |
|---|---|---|
| Where | One server | Many servers |
| Handled by | Postgres | Your app or a tool (Citus) |
| Solves | Big tables, retention, pruning | Write throughput and storage beyond one machine |

> **Key idea:** partition when a table is huge **and** most queries filter on the same key, usually time. It's not a general speed-up.
