# Query patterns that scale

## Avoid SELECT *

- It breaks **index-only scans**, because you ask for columns that aren't in the index.
- It fetches **TOASTed** large columns (big `text` or `jsonb`) that you don't use, which costs extra reads and decompression.
- It sends more bytes over the network.

## Avoid OFFSET for deep pages

`OFFSET 100000` still reads and throws away 100,000 rows. Use **keyset pagination** instead:

```sql
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < ($last_created_at, $last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

With an index on `(created_at, id)`, every page costs the same.

## COUNT(*) is slow on big tables

MVCC means Postgres must check that each row is visible to you, so there's no stored row count. Options:
- Use an estimate: `SELECT reltuples FROM pg_class WHERE relname = 'orders';`
- Or use `EXPLAIN` row estimates for a filtered count.
- Or keep a counter table up to date.

## Batch your writes

- Use one `INSERT ... VALUES (...), (...), ...` or `COPY` instead of thousands of single-row inserts.
- Upsert: `INSERT ... ON CONFLICT (key) DO UPDATE SET ...`.
- Delete in batches of a few thousand rows to keep locks and WAL spikes small.

## Use connection pooling

Each connection is a process. Put **PgBouncer** in transaction mode in front of Postgres, and keep `max_connections` modest (a few hundred at most).

## Find your worst queries

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Optimize by **total time**, not by the slowest single run.

> **Key idea:** ask for less (fewer columns, no OFFSET, estimates over exact counts) and do work in batches.
