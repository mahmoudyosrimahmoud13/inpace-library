# Isolation levels and read phenomena

## The phenomena

| Phenomenon | What happens |
|---|---|
| Dirty read | You see another transaction's uncommitted change |
| Non-repeatable read | You read a row twice and get different values |
| Phantom read | You run a range query twice and new rows appear |
| Serialization anomaly | The result can't be produced by any serial order (for example, write skew) |

## Postgres levels

| Level | Dirty | Non-repeatable | Phantom | Anomaly |
|---|---|---|---|---|
| Read Committed (**default**) | No | Possible | Possible | Possible |
| Repeatable Read | No | No | **No in Postgres** | Possible |
| Serializable | No | No | No | No |

- **Read Uncommitted** behaves like Read Committed in Postgres, so dirty reads never happen.
- **Read Committed** takes a new snapshot **for each statement**.
- **Repeatable Read** takes **one snapshot for the whole transaction** (snapshot isolation). Unlike the SQL standard minimum, it **also prevents phantoms**.
- **Serializable** uses **SSI** (serializable snapshot isolation). It tracks read/write dependencies and aborts one transaction with `could not serialize access`.

## Write skew: why Serializable exists

Two doctors are on call. Each checks "is someone else on call?", sees yes, and goes off call. Under Repeatable Read, both commit and nobody is on call. Under Serializable, one of them gets an error.

## The rule when you use Repeatable Read or Serializable

**Your app must retry** on serialization failures (`SQLSTATE 40001`). Without a retry loop, these levels just produce errors.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;  -- may fail with 40001, so retry the whole transaction
```

> **Key idea:** Read Committed is fine for most work. Use Serializable for invariants that span several rows, and always retry.
