# B-tree indexes and how Postgres uses them

## What an index is

A separate structure (by default a **B-tree**) that maps key values to **ctids** (row addresses in the heap). It turns "scan every page" into "walk a few tree levels".

## Scan types

| Scan | What happens | When |
|---|---|---|
| Seq Scan | Read every page | Large share of rows, or a small table |
| Index Scan | Walk the index, then fetch each row from the heap | Few rows |
| **Index Only Scan** | Answer from the index alone | All needed columns are in the index **and** the visibility map is up to date |
| Bitmap Index/Heap Scan | Collect ctids, sort them by page, read each page once | Medium share of rows, or combining indexes with AND/OR |

## Composite indexes: order matters

An index on `(customer_id, created_at)` helps:
- `WHERE customer_id = 7`
- `WHERE customer_id = 7 AND created_at > now() - interval '7 days'`
- `WHERE customer_id = 7 ORDER BY created_at DESC`

It **doesn't** help much with `WHERE created_at > ...` alone. **Put equality columns first and range or sort columns last.**

## Covering indexes

```sql
CREATE INDEX idx_orders_cust ON orders (customer_id) INCLUDE (total);
-- SELECT total FROM orders WHERE customer_id = 7  -> Index Only Scan
```

## Other index types

| Type | Good for |
|---|---|
| B-tree | `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'` |
| Hash | `=` only |
| GIN | `jsonb`, arrays, full-text search |
| GiST | Geometry, ranges, nearest neighbor |
| BRIN | Huge tables whose values follow physical order (timestamps on append-only logs) |

## Partial and expression indexes

```sql
CREATE INDEX ON orders (created_at) WHERE status = 'pending';  -- small, hot subset
CREATE INDEX ON users (lower(email));                          -- matches WHERE lower(email) = ...
```

> **Key idea:** an index helps only if the planner thinks it's cheaper than a seq scan. When the query needs a large share of the table, a seq scan is correct, not a bug.
