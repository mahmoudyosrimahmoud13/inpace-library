# Replication, sharding and scaling out

## Streaming (physical) replication

- Replicas receive and replay the primary's **WAL**, giving an exact byte copy.
- **Hot standby**: replicas serve **read-only** queries.
- **Asynchronous** (the default): fast, but the replica lags slightly, and a failover can lose the last few commits.
- **Synchronous** (`synchronous_standby_names`): a commit waits for the replica, so no data loss, but writes are slower.

Watch the lag:

```sql
SELECT client_addr, state, replay_lag FROM pg_stat_replication;
```

**Read-your-writes problem:** a user saves a change, then reads from a lagging replica and doesn't see it. Route those reads to the primary.

## Logical replication

- Publishes **row changes** for chosen tables (`CREATE PUBLICATION` / `CREATE SUBSCRIPTION`).
- Works across major versions, which makes it good for **zero-downtime upgrades** and feeding other systems.
- Doesn't replicate DDL or sequences automatically.

## Failover

Postgres doesn't fail over by itself. Use **Patroni** (with etcd or Consul) or a managed service.

## Sharding

You split data across servers by a **shard key** (for example `tenant_id`).
- Pick a key that keeps related data together and spreads load evenly.
- Cross-shard joins and transactions are hard.
- Tools: Citus, or app-level routing.

## Scaling order: don't shard too early

1. Fix queries and indexes.
2. Add connection pooling.
3. Scale up the machine.
4. Add read replicas.
5. Partition big tables.
6. **Only then** shard.

> **Key idea:** replicas scale reads, sharding scales writes, and both add complexity. Use the simpler steps first.
