# How Postgres works under the hood

Watch the video first, then use this page as your notes.

## One process per connection

Postgres uses **processes, not threads**:

- **Postmaster**: the main process. It listens on port 5432 and forks a new **backend process** for every client connection.
- **Backend**: runs your queries for that one connection. Each backend costs memory (a few MB plus `work_mem` per sort or hash).
- **Background workers**: the checkpointer, background writer, WAL writer, autovacuum launcher and stats collector.

This is why **thousands of open connections hurt Postgres**, and why connection poolers like PgBouncer exist.

## Shared memory

| Area | What it holds |
|---|---|
| `shared_buffers` | Cached 8 KB data pages shared by all backends |
| WAL buffers | Write-ahead log records not yet flushed to disk |
| Lock table | Who holds which lock |

A read first looks in `shared_buffers`. On a miss, Postgres reads the page from the OS, which has its own file cache. That's why Postgres is often given only about 25% of RAM for `shared_buffers`.

## Pages and tuples

- A table is stored in **heap files**, split into **8 KB pages**.
- Each row is a **tuple** with a hidden header: `xmin` (the transaction that created it) and `xmax` (the transaction that deleted or updated it).
- Each row's physical address is its **ctid** (page number, slot).

```sql
SELECT ctid, xmin, xmax, * FROM orders LIMIT 3;
```

## MVCC in one paragraph

An `UPDATE` never changes a row in place. It writes a **new tuple version** and marks the old one dead by setting `xmax`. Readers see the version that fits their snapshot, so **readers never block writers, and writers never block readers**. The cost is **dead tuples**, which **VACUUM** cleans up later.

> **Key idea:** most advanced Postgres behavior (bloat, vacuum, HOT updates, index-only scans) follows from MVCC creating new row versions.
