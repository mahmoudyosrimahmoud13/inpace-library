# Indexes in production: cost, locking and bloat

## Every index has a price

- Each `INSERT` writes to **every index**. Each non-HOT `UPDATE` does too.
- More indexes mean more WAL, slower writes, more disk use and less cache for the data.
- Unused indexes are pure cost. Find them:

```sql
SELECT relname, indexrelname, idx_scan,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

## CREATE INDEX blocks writes

A plain `CREATE INDEX` takes a **SHARE** lock: reads continue, but **all inserts, updates and deletes wait** until the build finishes. On a big table that can take minutes of downtime.

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer ON orders (customer_id);
```

- It takes two table scans and waits for old transactions to finish, so it's slower but doesn't block.
- **It can't run inside a transaction block.**
- If it fails, it leaves an **INVALID** index. Drop it and retry:

```sql
SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
```

## When the planner ignores your index

- **Low selectivity**: `WHERE is_active = true` matches 95% of rows.
- **Functions on the column**: `WHERE date(created_at) = ...`. Use a range instead, or an expression index.
- **Type mismatch**: comparing a `text` column to a number.
- **Stale statistics**: run `ANALYZE` after big loads.
- **Leading wildcard**: `LIKE '%abc'`. Use the `pg_trgm` extension with a GIN index.

## Bloat

Indexes fill up with pointers to dead tuples. Check index size against table size, and rebuild online:

```sql
REINDEX INDEX CONCURRENTLY idx_orders_customer;
```

> **Key idea:** in production, every index needs a reason (a real query), the `CONCURRENTLY` keyword, and regular checks for unused or bloated ones.
