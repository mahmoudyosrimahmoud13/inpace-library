# Locks in Postgres

## Two families

- **Table-level locks**: eight modes, from `ACCESS SHARE` (taken by `SELECT`) to `ACCESS EXCLUSIVE` (taken by `DROP`, most `ALTER TABLE`, and `VACUUM FULL`).
- **Row-level locks**: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`. They're stored **in the tuple header**, not in memory, so locking millions of rows is fine.

## What blocks what (the ones that matter)

| Statement | Table lock | Blocks reads? | Blocks writes? |
|---|---|---|---|
| `SELECT` | ACCESS SHARE | No | No |
| `INSERT/UPDATE/DELETE` | ROW EXCLUSIVE | No | Only on the same rows |
| `CREATE INDEX` | SHARE | No | **Yes** |
| `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | No | No |
| `ALTER TABLE ... ADD COLUMN` | ACCESS EXCLUSIVE | **Yes** | **Yes** |

## The lock queue trap

`ALTER TABLE` waits for a long-running `SELECT` to finish. Meanwhile **every new query queues behind the `ALTER`**, and your site goes down even though the `ALTER` itself is instant.

Fix it with a lock timeout and a retry:

```sql
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;
```

## Row locks for app logic

```sql
-- Job queue: each worker grabs a different row, no waiting
SELECT id FROM jobs
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
```

## Deadlocks

T1 locks row A then wants B, while T2 locks B then wants A. Postgres detects this after `deadlock_timeout` (1s) and aborts one of them. **Prevent it by always locking rows in the same order.**

## See who blocks whom

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

> **Key idea:** the biggest risk is not a slow lock but the queue that forms behind a waiting `ACCESS EXCLUSIVE`. Always set `lock_timeout` for migrations.
