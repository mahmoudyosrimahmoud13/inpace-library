# WAL, redo and undo

## The problem

Writing a full 8 KB page to disk on every change is slow and unsafe. If the power dies halfway through, the page is torn.

## Write-ahead logging (WAL)

**Rule: log the change first, then change the data page later.**

1. A transaction changes a page in `shared_buffers`. The page is now **dirty**.
2. A small **WAL record** describing the change is written to the WAL buffer.
3. On `COMMIT`, the WAL is flushed to disk with `fsync`. **That's the moment the commit is durable.**
4. Later, the **checkpointer** writes the dirty pages to the data files.

After a crash, Postgres **replays the WAL from the last checkpoint**. That's **redo**.

## Postgres has no undo log

| | Postgres | MySQL InnoDB / Oracle |
|---|---|---|
| Old row versions | Stay in the table (dead tuples) | Kept in a separate undo log |
| Rollback | Cheap: just mark the transaction aborted | Must apply the undo |
| Cost | Bloat, so it needs VACUUM | Undo grows with long transactions |

## Checkpoints and full-page writes

- A **checkpoint** flushes all dirty pages, so recovery only replays WAL written after it.
- The first change to a page after a checkpoint writes the **full page image** into the WAL, which protects against torn pages. Frequent checkpoints mean more WAL.
- Settings: `checkpoint_timeout`, `max_wal_size`.

## The WAL powers more than recovery

- **Streaming replication**: replicas replay the primary's WAL.
- **Point-in-time recovery**: a base backup plus archived WAL.
- **Logical decoding / CDC**: tools like Debezium read the WAL.

> **Key idea:** a commit is durable once its WAL is on disk, not once the table file is updated.
