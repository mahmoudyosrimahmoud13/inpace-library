# ACID transactions, explained by example

## The four guarantees

| Letter | Meaning | How Postgres delivers it |
|---|---|---|
| **A**tomicity | All or nothing | Abort marks the transaction ID as aborted, so its tuples are never visible |
| **C**onsistency | Constraints always hold | `CHECK`, `FOREIGN KEY`, `UNIQUE`, plus your app logic |
| **I**solation | Concurrent transactions don't see each other's mess | MVCC snapshots plus isolation levels |
| **D**urability | Committed means it survives a crash | WAL flushed on commit |

## A transfer

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

If the server crashes between the two updates, neither change is visible after restart.

## Durability trade-offs

- `synchronous_commit = off`: the commit returns before the WAL flush. That's faster, but you can lose the last fraction of a second of commits after a crash. The data stays consistent, just not fully durable.
- **Never turn off `fsync`** in production. That risks corruption, not just losing recent commits.

## Long transactions are dangerous

An open transaction holds a snapshot. Any row version it might still need **can't be vacuumed**, even in other tables. One forgotten `BEGIN` in a session that sits **idle in transaction** can bloat the whole database.

```sql
SELECT pid, state, xact_start, query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start;
```

Set `idle_in_transaction_session_timeout` to guard against this.

> **Key idea:** in Postgres, atomicity is cheap (rollback is instant), but long transactions are expensive because they block cleanup.
