# Finding the slow part: profiling and debugging

Traces tell you **which service and span** is slow. Then you need to know **why**.

## On a Linux host (from the internals course)

```bash
top / htop                       # CPU or memory bound?
vmstat 1                         # run queue (r), swapping (si/so), I/O wait (wa)
iostat -xz 1                     # disk saturation (%util, await)
ss -s; ss -tanp state established | wc -l    # connection counts
pidstat -p <pid> 1               # one process over time
perf top -p <pid>                # hottest functions right now
strace -c -p <pid>               # which system calls, how many, how long
```

## In the application

| Tool | Language | Shows |
|---|---|---|
| `py-spy top --pid <pid>` / `py-spy record` | Python | Live view and flame graph, no restart |
| `pprof` | Go | CPU, heap, goroutines |
| async-profiler | Java | CPU, allocations, locks |
| `EXPLAIN (ANALYZE, BUFFERS)` | PostgreSQL | Why a query is slow (Postgres courses) |

**Flame graphs**: the x-axis is share of samples (not time order), the y-axis is the call stack. Wide boxes are where time goes.

**Continuous profiling** (Grafana Pyroscope, Parca) keeps low-overhead profiles all the time, so you can compare "before and after the deploy".

## A method

1. Confirm the symptom with metrics (which route, since when, which version).
2. Find the slow span in a trace from that period.
3. Profile that service or `EXPLAIN` that query.
4. Fix, deploy, **compare the same metric** before and after.
