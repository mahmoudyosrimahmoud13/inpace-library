# Blameless postmortems

After every significant incident, write a **postmortem**. Blameless means: assume everyone acted reasonably with what they knew; fix the **system** that let a mistake hurt users. People hide problems when they fear blame, and hidden problems repeat.

## Template

```markdown
# Postmortem: checkout errors, 2026-11-17

## Summary
Two sentences: what users saw, how long, how many affected.

## Impact
23% of checkout requests failed from 14:03 to 14:41 (38 min). ~1,900 failed orders; 31% of the monthly error budget used.

## Timeline (UTC)
14:02 Deploy sha-3f2c1ab to prod
14:03 Error rate rises
14:09 Burn-rate alert pages on-call
14:21 IC declared Sev 2; deploy suspected
14:38 Rolled back to sha-9e81d02
14:41 Error rate normal

## Root cause and trigger
The new code opened a DB connection per request; under peak load the pool was exhausted.

## What went well / what went badly / where we got lucky

## Action items
| Action | Type | Owner | Due |
| Load test checkout in CI with production-like traffic | prevent | Sara | 12-01 |
| Alert on DB connection pool saturation | detect | Omar | 11-24 |
| Automatic canary analysis with rollback | mitigate | Lina | 12-15 |
```

## Making them count

- Look for **contributing factors**, not one root cause: the bug, the missing test, the alert that took 6 minutes, the rollback that needed a manual step.
- Action items have **owners and dates**, and are tracked like features.
- Share them widely; review recurring themes every quarter.
- Ask "**how did this make sense to the person at the time?**" instead of "who did this?".

The Google SRE book chapter "Postmortem Culture: Learning from Failure" has examples.
