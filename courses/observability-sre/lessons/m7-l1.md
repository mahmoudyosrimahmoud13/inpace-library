# Capacity, toil and resilience testing

## Capacity planning

- Know your **headroom**: at today's peak, how close are CPU, memory, DB connections and queue depth to their limits?
- Forecast from trends (`predict_linear`, growth per month) and known events (sales, launches).
- **Load test** before big events (k6, Locust): find the breaking point in staging, not in production.

```bash
k6 run --vus 200 --duration 10m checkout.js
```

## Toil

**Toil** is manual, repetitive, automatable work that grows with the service: restarting a stuck process every week, hand-rotating certificates, copying logs for someone. SRE aims to keep toil under ~50% of time and **automate it away** with the skills from the Bash, Ansible and CI/CD courses.

## Resilience testing

Prove your system survives failures you designed for, on purpose, before they happen at 3 a.m.:

| Test | Example |
|---|---|
| Kill an instance | Does the ASG replace it with no user impact? |
| Fail a dependency | Payment API slow: do timeouts and retries behave, or does everything back up? |
| Lose a zone | Does traffic shift? Does RDS fail over? |
| Restore a backup | How long does it really take (your real RTO)? |
| **Game day** | The team practices an incident end to end, including comms |

Start in staging, with a clear hypothesis, a way to stop, and someone watching dashboards. Tools like AWS Fault Injection Service or Chaos Mesh help later; a manual `systemctl stop` is a fine first experiment.

## Design patterns that survive

Timeouts on every network call, retries with backoff and jitter (and a limit), circuit breakers, bulkheads (separate pools), graceful degradation (show cached data when a dependency is down), and idempotent operations so retries are safe.
