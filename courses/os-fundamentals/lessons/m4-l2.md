# Locks: mutual exclusion

A **lock** (also called a **mutex**) makes sure only one thread is inside a critical section at a time.

```c
pthread_mutex_lock(&m);
counter = counter + 1;      // critical section
pthread_mutex_unlock(&m);
```

## Building a lock needs hardware help

A naive lock fails:

```c
while (flag == 1) ;   // wait
flag = 1;             // take it   <- another thread can sneak in between these lines
```

CPUs provide **atomic** instructions that read and write in one unbreakable step:

- **Test-and-set**: set a value and return the old one, atomically.
- **Compare-and-swap (CAS)**: "if the value is still X, make it Y", atomically.

```c
while (test_and_set(&flag, 1) == 1) ;   // spin until we were the one who changed 0 -> 1
```

## Spin or sleep?

| Kind | While waiting | Good when |
|---|---|---|
| **Spin lock** | Burns CPU checking again and again | The wait is tiny, and on another core (kernels use these a lot) |
| **Sleeping mutex** | The thread blocks; the OS runs something else | The wait might be long |

Linux mutexes (built on **futexes**) do both: spin briefly, then sleep.

## Judging a lock

1. **Correct**: mutual exclusion actually holds.
2. **Fair**: a waiting thread eventually gets it. A **ticket lock** (take a number, wait to be called) is fair; plain test-and-set isn't.
3. **Fast**: little overhead when nobody else wants it.

## Coarse vs fine locks

- One big lock around everything: simple, safe, but threads queue up (no parallelism).
- Many small locks (one per hash bucket, say): more parallelism, more chances for bugs.
- Start coarse, measure, then split where it hurts.

Locks also slow things down when many cores fight over one: every CPU's cache keeps losing the line holding the lock. That's why the kernel uses tricks like per-CPU counters and RCU (MIT lecture 23 if you're curious).
