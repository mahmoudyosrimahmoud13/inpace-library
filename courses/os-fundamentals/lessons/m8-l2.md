# Inside a file system: blocks, caching and crash consistency

## A simple file system on disk

```text
| super block | inode bitmap | data bitmap | inode table ......... | data blocks ...................... |
```

- **Super block**: the file system's own description (size, how many inodes, where things are).
- **Bitmaps**: which inodes and which data blocks are free.
- **Inode table**: all the inodes.
- **Data blocks**: file contents and directory contents.

Reading `/home/sara/notes.txt` means: read the root directory's inode, read its data to find `home`, read that inode, and so on down the path. That's many small reads, which is why the kernel caches directory lookups (the **dentry cache**) and inodes.

## Big files

An inode has room for a dozen direct block pointers. Bigger files use **indirect blocks** (a block full of pointers), double-indirect, and so on. Modern file systems like ext4 use **extents** instead: "blocks 5,000 to 9,000 belong to this file", which is much smaller for big contiguous files.

## Crash consistency

Appending one block to a file means updating **three** things on disk: the data block, the inode (size and pointer), and the data bitmap. If the power fails between those writes, the file system is inconsistent: an inode pointing at garbage, or a block marked used that no file owns.

Two fixes:

| Approach | How | Cost |
|---|---|---|
| **fsck** | After a crash, scan the whole disk and repair | Hours on big disks |
| **Journaling** (write-ahead logging) | First write what you're about to do to a log, then do it. After a crash, replay the log | A little extra writing; recovery in seconds |

```mermaid
flowchart LR
  A["1. Write intent to journal"] --> B["2. Write commit record"]
  B --> C["3. Write the real blocks in place"]
  C --> D["4. Mark journal entry done"]
```

ext4 by default journals **metadata only** (inodes, bitmaps, directories) and writes data first, so after a crash the structure is always valid. That's the same idea as a database's write-ahead log.

## Other designs

- **Copy-on-write** file systems (Btrfs, ZFS) never overwrite in place: they write new blocks and switch a pointer at the top. Snapshots are almost free.
- **Log-structured** file systems turn all writes into big sequential writes, which also suits SSDs.

## Mounting and virtual file systems

`mount /dev/sdb1 /data` attaches a file system at `/data`. Some file systems have no disk at all:

| Mount | What's in it |
|---|---|
| `/proc` | Processes and kernel state, generated when you read it |
| `/sys` | Devices and drivers |
| `/dev` | Device files (from devtmpfs) |
| `/tmp` (often tmpfs) | Files kept in RAM, gone at reboot |
