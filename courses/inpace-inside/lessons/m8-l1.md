# Speaking 14 languages, and keeping updates honest

Day 7 ended at version 1.22. Since then inPace grew a lot. Today walks through the new parts as **engineering
decisions**: what the problem was, what we chose, and what it cost. These make good interview stories.

## 1. Fourteen languages without a translation framework

**Problem:** the app had English and Arabic written inline. Adding 12 more languages that way doesn't scale.

**Choice:** one JSON file per language in `inpace/locales/` (`ar.json`, `es.json`...), mapping the **English
sentence** to its translation. Templates use Jinja's i18n extension: `{% trans %}...{% endtrans %}` and `_()`.

```python
def gettext(text: str) -> str:
    table = LOCALES.get(CURRENT["lang"])
    if not table or not text:
        return text
    return table.get(text) or text   # a missing line falls back to English
```

- **Fallback to English, never a crash:** a language is useful from its first translated line.
- **The device language is used on the first open** (`Accept-Language` on desktop, the phone's locale on Android).
- **Right to left** comes from the language, and each paragraph also sets `dir` from its own words, so an English
  line inside an Arabic lesson reads correctly.
- **Tests guard it:** every locale file must be valid JSON, keep `{placeholders}` identical, and never translate
  the name *inPace*.

**Trade-off:** English sentences as keys are easy to read and to translate, but changing an English sentence
"orphans" its translations. The fallback makes that a cosmetic problem, not a broken page.

## 2. "A new version is out" (and making sure it's true)

The app checks GitHub's latest release at most twice a day and compares version numbers.

A real bug from this project: releases **v1.28.1** and **v1.28.2** were tagged while the code still said
`__version__ = "1.28.0"`. Every copy, even the newest, kept saying "1.28.2 is out". The comparison code was
right; the **data it compared** was wrong.

**The fix was in the pipeline, not the app:** the release workflow now writes the tag's number into
`inpace/__init__.py` and `pyproject.toml` **before** building, so the label and the code can't disagree:

```yaml
- name: Use the tag as the version number
  if: startsWith(github.ref, 'refs/tags/v')
  run: python3 - "${GITHUB_REF_NAME#v}" <<'PY'
       ... re.sub(r'__version__ = "[^"]*"', f'__version__ = "{v}"', ...)
       PY
```

And a second lesson in the same week: the Android job runs its steps in `mobile/` (`defaults.run.working-directory`),
so the new step couldn't find `inpace/__init__.py` there. One line fixed it: `working-directory: ${{ github.workspace }}`.
**Interview point:** when you add a step to a job, check the job's defaults.

## 3. Caching: the bug that hid three releases

Static files are served with `Cache-Control: public, max-age=31536000, immutable` when the link has `?v=`. That's
right, **if the `v` changes when the file changes**. It was written by hand (`app.js?v=30`) and nobody bumped it,
so after updates the app window kept the old script: new features "didn't appear".

**Fix:** a fingerprint of the file's bytes.

```python
def _static_stamp(name: str) -> str:
    return hashlib.sha256((HERE / "static" / name).read_bytes()).hexdigest()[:10]

env.globals["static_v"] = {n: _static_stamp(n) for n in ("app.js", "style.css", "builder.js")}
```

```html
<script src="/static/app.js?v={{ static_v['app.js'] }}"></script>
```

The **same bug existed twice more**: the website's `style.css?v=8` (fixed by stamping the commit id at publish time
in `pages.yml`) and the library covers (`covers/fmaa-prc.jpg`, fixed with `?v=` + the image's hash).

**Interview point:** long cache lifetimes are only safe with **content-addressed** URLs. Hand-numbered versions
always drift.
