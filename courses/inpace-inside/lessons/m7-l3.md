# Explaining inPace in an interview

## The 60-second version

"inPace is a local-first learning app. Everything runs on the user's device: a Python Starlette server on
127.0.0.1, SQLite, and Jinja pages in a native window, on desktop and Android. There are no accounts; instead,
each user has an Ed25519 key, and milestones are signed and hash-chained, so a mentor can verify progress from a
file sent over WhatsApp. I built course import from folders, PDFs and AI, a public course library on GitHub with
signed submissions, spaced review, and a gamified focus mode. It's tested on three OSes in CI and ships with
verified auto-updates."

## System design: questions to expect

> **How would you add sync between a phone and a laptop?**
Events are append-only and signed, which is close to a CRDT-friendly log: merge by union of events, recompute
state. You'd need per-device ids, a transport (file, LAN, or an optional relay that only sees encrypted blobs),
and conflict rules for the few mutable settings in `meta`.

> **What if a learner edits vault.db by hand?**
They can add fake events locally, but milestones they send are signed and chained; the checker verifies the
chain and still reviews the work, explain answers and verified exams. Trust comes from the checker's review,
backed by tamper-evidence, not from DRM.

> **Why SQLite and not files of JSON?**
Transactions, triggers for append-only rules, indexes, one file to back up, and it's built into Python.

> **How does it scale?**
Per user it doesn't need to: each device holds one person's data. The shared part (the library) is static files on
GitHub Pages, which scale for free.

> **What would you do differently?**
Split `app.py` into routers per area; add type-checked models for files; consider a small optional relay for
sync with end-to-end encryption.

## Behavioural angle

Pick one story with a measurable result: the navigation bug that looked like many bugs, the false CI failure, or
the decision to keep everything local. Use **situation, task, action, result**.
