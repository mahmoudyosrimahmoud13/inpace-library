# Keys, canonical JSON and fingerprints

## Your identity is a key pair

`identity.py` wraps an **Ed25519** signing key from PyNaCl. Your **id is your public key in hex**. The private
key is saved in `identity.key` (permissions 0600 where the OS allows) and never leaves the device.

```python
class Identity:
    @property
    def id(self) -> str:
        return self._sk.verify_key.encode().hex()

    def sign(self, data) -> str:
        return self._sk.sign(canonical_bytes(data)).signature.hex()
```

## Why "canonical" JSON

To sign data, both sides must turn it into **exactly the same bytes**. `{"a":1,"b":2}` and `{"b": 2, "a": 1}`
mean the same thing but are different bytes. `canon.py` fixes one way to write it:

```python
json.dumps(data, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")
```

Sorted keys, no spaces, UTF-8, non-ASCII kept. The **fingerprint** is the SHA-256 of those bytes.

## Signed vs unsigned parts

A contact card signs `{inpace, id, name, color, created_at}`. Newer fields (your turtle, your island) travel
**next to** the signed part, not inside it. Old versions still verify the card, and the new fields are cleaned
(`clean_avatar`, `clean_snapshot`) because nobody vouched for them. This "signed core plus unsigned extras"
pattern is a neat answer to "how do you evolve a signed format without breaking old clients?"
