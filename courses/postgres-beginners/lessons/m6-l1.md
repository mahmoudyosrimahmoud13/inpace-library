# UPDATE, DELETE and transactions

```sql
UPDATE orders SET status = 'shipped' WHERE id = 42;
UPDATE customers SET country_code = 'EG', last_name = 'Ali' WHERE email = 'sara@example.com';
UPDATE orders SET total = total * 0.9 WHERE status = 'new' RETURNING id, total;

DELETE FROM orders WHERE status = 'cancelled' AND ordered_at < now() - interval '1 year';
```

## The most expensive mistake in SQL

An `UPDATE` or `DELETE` **without a WHERE** changes **every row**. Habits that prevent it:

1. Write the `WHERE` first. Run it as a `SELECT` to see exactly which rows match.
2. Then change `SELECT *` to `UPDATE ... SET` or `DELETE`.
3. Do it inside a **transaction**, and check before committing.

## Transactions

A transaction groups statements so they all happen, or none do.

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
SELECT id, balance FROM accounts WHERE id IN (1, 2);   -- looks right?
COMMIT;      -- make it permanent
-- or
ROLLBACK;    -- undo everything since BEGIN
```

```sql
BEGIN;
DELETE FROM orders WHERE status = 'cancelled';
-- DELETE 1250   <- expected ~50? Something's wrong:
ROLLBACK;
```

- Any error inside a transaction aborts it: everything after fails until you `ROLLBACK`.
- Other sessions don't see your changes until you `COMMIT`.
- The advanced course explains how Postgres does this (MVCC) and the isolation levels.

## TRUNCATE

`TRUNCATE orders;` empties a table instantly (much faster than DELETE). It can be rolled back inside a transaction in Postgres, but treat it like `DROP`: rarely, carefully.
