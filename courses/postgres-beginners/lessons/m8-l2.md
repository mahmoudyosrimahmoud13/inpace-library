# Capstone: design and query a small library database

Design, build and query a lending library, from an empty database to useful answers.

## The brief

- **Members**: name, unique email, joined date.
- **Books**: title, ISBN (unique), year, and one or more **authors**.
- **Copies**: a library can own several copies of a book.
- **Loans**: a member borrows a copy on a date, must return it by a due date, and returns it (or hasn't yet).

## Your design should have

- A primary key on every table, identity or UUID.
- Foreign keys between them, with sensible `ON DELETE` rules.
- A many-to-many `book_authors` join table.
- Constraints: `due_on > borrowed_on`, `returned_on` NULL or `>= borrowed_on`, a copy can't be on two open loans at once (hint: a unique index `ON loans (copy_id) WHERE returned_on IS NULL`).

## Fill it

Use `generate_series` or Mockaroo for 200 members, 500 books, 1,000 copies and 5,000 loans.

## Answer with SQL

1. Which books are out right now, and who has them?
2. Overdue loans, with days overdue, worst first.
3. The 10 most borrowed books this year.
4. Members who joined this year but never borrowed.
5. Loans per month for the last 12 months.
6. Each author's number of loans (careful with the join multiplication!).
7. Mark loan 123 as returned today, inside a transaction.
8. Export the overdue list to CSV.

## Ready for the advanced course?

Run question 3 with `EXPLAIN ANALYZE` in front. If the plan and its numbers look mysterious, that's exactly where **Advanced PostgreSQL: how Postgres really works** starts: how Postgres stores rows, why indexes help, how to read plans, and what happens when many users write at once.
