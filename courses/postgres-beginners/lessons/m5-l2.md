# Keys and constraints: letting the database protect your data

Constraints are rules the database **enforces on every write**, from every app, forever. They're far more reliable than checks in application code.

| Constraint | Guarantees | Example |
|---|---|---|
| `PRIMARY KEY` | Unique and not NULL; identifies each row | `id` |
| `NOT NULL` | A value is always there | `email text NOT NULL` |
| `UNIQUE` | No duplicates | `email text UNIQUE` |
| `CHECK` | A condition holds | `CHECK (total >= 0)` |
| `FOREIGN KEY` | The referenced row exists | Day 7 |
| `DEFAULT` | A value when none is given (not really a rule) | `DEFAULT now()` |

```sql
ALTER TABLE customers ADD CONSTRAINT customers_email_lower CHECK (email = lower(email));
ALTER TABLE orders ADD CONSTRAINT orders_status_valid
    CHECK (status IN ('new', 'paid', 'shipped', 'cancelled'));

-- a unique pair: one review per customer per product
CREATE TABLE reviews (
    customer_id bigint NOT NULL,
    product_id  bigint NOT NULL,
    stars       int NOT NULL CHECK (stars BETWEEN 1 AND 5),
    PRIMARY KEY (customer_id, product_id)
);
```

## What happens on a violation

```text
ERROR:  duplicate key value violates unique constraint "customers_email_key"
DETAIL:  Key (email)=(sara@example.com) already exists.
```

The statement is rejected; nothing is half-written. Your app catches the error and shows a friendly message.

## Adding a constraint to a table that already has bad data

It fails, telling you a row breaks it. Find and fix those rows first:

```sql
SELECT email, count(*) FROM customers GROUP BY email HAVING count(*) > 1;   -- duplicates
```

## Natural vs surrogate keys

- A **surrogate key** (`id`, an identity or UUID) never changes and means nothing. Use it as the primary key.
- **Natural** identifiers (email, national ID, SKU) can change: give them a `UNIQUE` constraint instead.
