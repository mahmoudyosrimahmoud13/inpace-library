# Project 3: embeddings two ways, and a vector index

You'll build LSA embeddings from scratch, then use a small trained embedding model, put the vectors in a simple vector
index, and compare both with BM25.

The code is above this text. Save it as `p03_embeddings.py`. It needs `pip install numpy model2vec`. The first run
downloads the 30 MB model from Hugging Face; later runs use the saved copy.

## Read the code

- **`LSA`**:
  - Keeps every word that appears in at least 2 chunks (`self.vocab`).
  - `_tfidf()` fills a table: one row per chunk, one column per word, with `1 + log(count)` times the word's idf.
  - `np.linalg.svd` splits the table into three; the first 256 rows of `vt` are 256 "topics", each a mix of words
    that tend to appear together. `encode()` turns any text into its 256 topic scores.
- **`normalize()`** scales each vector to length 1, so a dot product is the cosine similarity.
- **`VectorIndex`**: every chunk's vector in one matrix (`self.vecs`). `search()` is one matrix-vector product, then
  `argpartition` to get the top k without sorting all 2,042 scores. `doc_search()` turns chunks into documents, like
  project 2. `save()` writes the matrix to a `.npy` file: that's a vector database at its simplest.
- **`pretrained()`** loads model2vec's `potion-base-8M`. It has the same `encode()` method as `LSA`, so `VectorIndex`
  works with either.

What it shows:

- **LSA learned from 1,517 short docstrings isn't enough**: it does worse than BM25. It knows only the word pairs this
  corpus uses.
- The **trained model** knows that "folder" and "directory" are related (cosine 0.52, against 0.10 for "banana"), and
  embeds 2,042 chunks in about a second. But on its own it still finds fewer right documents than BM25.
- Look at the misses: "copy a file and keep its modification time" goes to the `copy` module, which is about copying
  Python objects. Meaning search matched the word "copy" in the wrong sense. And "Delete a folder" finds temporary
  directories, but not `rmtree`, whose docstring is one short line.
- A search over every vector takes well under a millisecond. You don't need a vector database product for a few
  thousand chunks.

Neither search wins on every question, and they fail on *different* questions. Tomorrow you combine them.

## Make it yours

1. Change LSA's `dim` to 64 and 512. Does recall move? Why does more dimensions not mean more meaning here?
2. Embed only each chunk's **title** with the trained model, and compare. What does the title carry that the text
   doesn't?
3. Load `chunk_vectors.npy` in a new script with `np.load`, and search it without re-embedding the corpus. Time the
   load against the embedding.
4. Try a bigger model: `minishlab/potion-base-32M` (or, with Ollama, `nomic-embed-text` through its
   `/api/embeddings` endpoint). Is the gain worth the size?

## What to take away

- Embeddings find meaning, not words, and they blur exact names.
- Brute-force vector search is exact and fast enough for thousands of chunks.
- Measure before you believe: on this corpus, embeddings alone don't beat BM25.
