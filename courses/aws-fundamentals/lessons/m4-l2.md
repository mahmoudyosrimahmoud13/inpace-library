# Security groups and network ACLs

## Security groups: a firewall on each instance

```text
sg-web (attached to the load balancer):  allow TCP 443 from 0.0.0.0/0
sg-app (attached to app instances):      allow TCP 8000 from sg-web
sg-db  (attached to the database):       allow TCP 5432 from sg-app
```

- **Stateful**: replies are allowed automatically (like `ct state established` in nftables).
- **Allow rules only**; everything else is denied.
- Rules can reference **other security groups** instead of IP ranges: "anything in sg-app may reach me". When the app scales to 20 instances, nothing needs updating.

## Network ACLs: a firewall on each subnet

| | Security group | Network ACL |
|---|---|---|
| Applies to | An instance's network interface | A whole subnet |
| State | Stateful | **Stateless**: allow the return traffic yourself (ephemeral ports 1024-65535) |
| Rules | Allow only | Allow and deny, numbered, first match wins |
| Typical use | The main control | Rare: blocking an IP range at the subnet edge |

Most teams leave NACLs at their default (allow all) and do everything with security groups.

## "I can't reach my instance": the checklist

1. Is it running, and does it have a public IP (or are you coming through a bastion/VPN/Session Manager)?
2. Subnet route table: route to the internet gateway?
3. Security group: inbound rule for that port **from your IP**?
4. Network ACL: allows both directions?
5. The OS: service listening (`ss -tlnp`), host firewall?

**Reachability Analyzer** in the VPC console traces a path between two points and names the blocking rule.
