# Managed databases: RDS, Aurora and DynamoDB

## RDS: PostgreSQL, MySQL and friends, run for you

AWS handles installs, patching, backups, failover and monitoring; you still design the schema, tune queries and pay for the size you choose.

| Feature | Means |
|---|---|
| **Multi-AZ** | A standby copy in another AZ; automatic failover in about a minute. Production must-have |
| **Read replicas** | Copies for read traffic (and reporting) |
| **Automated backups** | Daily snapshot + transaction logs: restore to any second in the retention window (up to 35 days) |
| **Parameter groups** | Where `postgresql.conf` settings live |
| **Subnet group** | Which private subnets it lives in |

```bash
aws rds describe-db-instances --query 'DBInstances[].[DBInstanceIdentifier,Engine,DBInstanceStatus,MultiAZ]' --output table
```

Put databases in **private** subnets, reachable only from the app's security group. Never "publicly accessible".

## Aurora

AWS's own engine compatible with PostgreSQL and MySQL: storage spread over 3 AZs, faster failover, up to 15 replicas, and a serverless option that scales with load. Costs more per hour; often worth it for bigger systems.

## DynamoDB

A key-value and document database: no servers, single-digit-millisecond reads at any scale, pay per request. You design tables around your **access patterns** (which queries you'll run) rather than normalising. Great for sessions, carts, IoT and high-scale lookups; awkward for ad-hoc reporting and complex joins.

| Need | Pick |
|---|---|
| Relational data, joins, reports, most apps | RDS PostgreSQL / Aurora |
| Huge scale, simple known lookups | DynamoDB |
| Caching | ElastiCache (Redis/Valkey) |
