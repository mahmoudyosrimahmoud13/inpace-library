# Disks: EBS, instance store and snapshots

| Storage | Is | Survives stop? | Use |
|---|---|---|---|
| **EBS volume** | A network disk in one AZ | Yes | Root disks, databases, anything you keep |
| **Instance store** | Disk physically in the host | **No** (lost on stop or host failure) | Caches, scratch space |
| **EFS** | Shared NFS file system, many instances, many AZs | Yes | Shared files |
| **S3** | Object storage over HTTP | n/a | Backups, static files, data lakes (Day 5) |

## EBS volume types

| Type | For |
|---|---|
| `gp3` | General purpose SSD; the default. Set IOPS and throughput separately from size |
| `io2` | High, guaranteed IOPS for big databases |
| `st1` / `sc1` | Cheap throughput-oriented HDD for big sequential data |

A volume lives in **one AZ** and attaches to instances in that AZ. To move it, snapshot it and create a new volume elsewhere.

## Snapshots

Point-in-time, incremental backups of a volume, stored in S3 behind the scenes:

```bash
aws ec2 create-snapshot --volume-id vol-0abc --description "web01 before upgrade"
aws ec2 describe-snapshots --owner-ids self --query 'Snapshots[].[SnapshotId,StartTime,VolumeSize]' --output table
```

Automate them with **Data Lifecycle Manager** or **AWS Backup**, and delete old ones: forgotten snapshots are a classic slow cost leak.

Encrypt volumes by default (EC2 settings → "Always encrypt new EBS volumes"): no performance cost, and it closes a whole category of mistakes.
